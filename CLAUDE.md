# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**There is exactly ONE CLAUDE.md in this repo — this file, at the repo root. Never create a second one.** Two copies diverge silently and the agent then follows whichever it happened to read. Two things make a duplicate appear even when nobody wrote one:
- **macOS/APFS is case-insensitive**, so `claude.md` and `CLAUDE.md` are the *same* file. A reference to either resolves here; that is not a duplicate and needs no action.
- **A nested git worktree is a real duplicate.** `.claude/worktrees/<branch>/CLAUDE.md` is a second checkout living *inside* the primary working tree, so every repo-wide `find`/`grep` sees two. `.claude/worktrees/` is in `.git/info/exclude`, so git stays quiet about it. Check with `git worktree list`; if the branch is fully pushed (`git branch -r --contains <sha>`), `git worktree remove` it — the commits survive on the remote and can be checked out again *outside* the repo tree, which is where a worktree belongs.

## What this is

A local, chat-driven, CapCut-class video editor. Python/FastAPI backend + React/TS frontend, packaged as a native macOS app via pywebview. Everything runs on-device; only Claude API calls leave the machine. The backend also exposes an MCP server so external agents (Claude Code / Cursor / Codex) can drive the timeline.

Notes:
- `uv sync` alone does **not** install `pytest` — it lives under `[project.optional-dependencies].dev`. Use `uv sync --all-extras --group dev` (or `uv sync --frozen --extra dev`, as CI does). `pip` is not seeded in uv venvs; install it (`uv pip install pip`) only if a tool like the VS Code Python extension needs to enumerate packages.
- Playwright's frontend smoke test needs a browser binary: `uv run playwright install chromium`.
- Tests requiring local AI binaries/models skip cleanly by default; opt in with `VAI_RUN_CLIP_TESTS` / `VAI_RUN_CAPTION_TESTS`.
- Ports differ by entry point: desktop binds `VAE_PORT` (default **8765**); raw `uvicorn ...:app` defaults to **8000**; Vite dev server is **5173** and proxies `/api` → `:8000`. They are not interchangeable.
- **`npx tsc --noEmit` type-checks ZERO files. Always use `npx tsc -b`.** `frontend/tsconfig.json` is a *solution* file (`"files": []` plus only `references`), so plain `tsc` builds an empty program and exits 0 — verified with `npx tsc --noEmit --listFiles`, which prints 0 lines. Only build mode (`tsc -b`) descends into `tsconfig.app.json` / `tsconfig.node.json`. This was a silent hole for a long time: 4 real type errors sat on main while CI stayed green, and `npm run build` — which `desktop.py`'s dev auto-build **and** `build_win.ps1` both invoke — failed on them, so a fresh clone could not launch. Those 4 are fixed and **CI, `build_app.sh` and the docs now all use `tsc -b --force`.** Never "simplify" a gate back to `--noEmit`.
- **Lint (`npm run lint`) has 64 pre-existing problems (60 errors, 4 warnings) that are NOT part of the CI gate.** Measured on 2026-08-17 (was 32 on 2026-07-30); only 1 is `--fix`-able. When checking whether your change added lint issues, compare against this baseline (e.g. `git stash` / a worktree at the pre-change commit) rather than treating a nonzero exit as your regression — most are pre-existing `no-empty`/`react-hooks/*` debt in files you didn't touch. **Re-measure the baseline rather than trusting this number**: the jump from 32 to 64 is almost entirely **`react-hooks/refs` in `Preview.tsx` (4 → 36)**, from the render-time ref-latch pattern the live-transform/live-filter/source-preview work leans on (`if (ref.current?.hash !== previewHash) ref.current = …`). Reading and writing a ref during render is what the rule objects to, and the objection is real in general — a discarded concurrent render leaves the mutation behind. It is tolerated **here** because every one of those latches is keyed on `previewHash` + `clipId` and is therefore **idempotent**: re-running the render with the same inputs recomputes the same value, so a double-render (StrictMode, or a discarded concurrent one) cannot produce a state the next render disagrees with. Do not "clean these up" by moving them into effects — the latch has to be settled *before* paint or the preview shows the pre-gesture pose for a frame, which is the exact class of flicker `liveTransform`/`resolveLiveOverride` exist to remove.

## Launching on macOS — the hidden-`.pth` gotcha (use `run.sh`)

`uv run video-ai-editor` (and any bare import of the package) can fail with `ModuleNotFoundError: No module named 'video_ai_editor'` **even when the venv is correctly synced.** Root cause: macOS Spotlight's metadata daemon `com.apple.metadata.mdflagwriter` marks Python `.pth` files with the hidden flag (`UF_HIDDEN`) within ~1s of creation, and Python 3.13+ `site.py` **skips hidden `.pth` files** — so the editable install's `.pth` (which puts `src/` on `sys.path`) is never processed. It recurs system-wide (even in `/tmp`), so `chflags nohidden` does not hold, and rebuilding the venv only fixes it transiently.

**Always launch with `bash run.sh`**, which runs `PYTHONPATH="$PWD/src" .venv/bin/python -m video_ai_editor.desktop` and bypasses the `.pth` mechanism entirely. (The README used to document `uv run video-ai-editor` as *the* launch command with no mention of `run.sh` — i.e. it handed every Mac user the one command this section exists to warn about. Fixed; keep the two in agreement.)

**`bash verify_mac.sh` is the post-pull check on a Mac** — toolchain, `tsc -b` + `vite build`, every backend module imported together, an actual server boot (`/api/health`, then `/readyz`, which is 503 when the app can't find ffmpeg), and the optional-feature report; `--no-tests` skips pytest. It deliberately does **not** `set -e`: every check runs so one pass lists all failures instead of one relaunch per failure. Kept to **bash 3.2** constructs because macOS still ships that as `/bin/bash` — no associative arrays, no `mapfile`, and never expand a possibly-empty array (`"${arr[@]}"` under `set -u` is an "unbound variable" error there, while `${#arr[@]}` is fine). It also runs under Git Bash on Windows, which is how it was smoke-tested before ever reaching a Mac. Diagnose the flag with `ls -lO <file>.pth` (shows `hidden`); confirm the culprit with `launchctl list | grep mdflagwriter`. Do **not** fight the Spotlight daemon directly. (`pytest` is unaffected — it uses `pythonpath = ["src"]` in `pyproject.toml`.)

### Running on Windows

- Setup: `winget install Gyan.FFmpeg` (the **full** variant — includes libvidstab + libass + the nvenc/qsv/amf encoders). Then `uv sync --python 3.13 --all-extras --group dev` and `cd frontend && npm install`.

- Encoder: on Windows the render pipeline probes `h264_nvenc` → `h264_qsv` → `h264_amf` → `libx264` (a real null-encode probe, since `ffmpeg -encoders` lists HW encoders even without the GPU).
- Native AI binaries (optional features): `whisper-cli.exe` from whisper.cpp `whisper-bin-x64.zip`, `realesrgan-ncnn-vulkan.exe` from `realesrgan-ncnn-vulkan-*-windows.zip` — drop into `%APPDATA%\Video AI Editor\...` or `models\`. TTS (Piper) works from the pure-Python wheel with no extra binary.
- Packaging: `powershell -ExecutionPolicy Bypass -File build_win.ps1` → `dist\Video AI Editor\` (wrap in Inno Setup/WiX for distribution).

## Cross-platform layer — `platformutil.py` (the ONE place OS differences live)

The app runs on both macOS and Windows from one codebase. **All OS-conditional logic routes through `src/video_ai_editor/platformutil.py`** — no raw inline `sys.platform` checks elsewhere (design rule; a test enforces the encoding side). On macOS every Windows branch is dead code (`IS_WINDOWS` is False, `exe_name()` is a no-op), so macOS behavior is preserved byte-for-byte. Helpers: `IS_WINDOWS`/`IS_MAC`, `exe_name(name)` (adds `.exe` on Windows), `find_binary(name, extra_dirs)`, `user_data_dir`/`user_cache_dir` (per-OS `%APPDATA%`/`%LOCALAPPDATA%` vs `~/Library`), `read_text_utf8`/`write_text_utf8`, `replace_with_retry`/`unlink_with_retry`, `FFMPEG`/`FFPROBE` constants, `ffmpeg_filter_path(path)`.

Four Windows footguns are non-obvious and were only caught by the `windows-latest` CI job — respect them when touching render/AI/subprocess code:

1. **ffmpeg *filtergraph* paths ≠ *argv* paths.** A path passed as an `-i` argv element needs NO escaping. But a path embedded INSIDE a `-vf`/`-filter_complex` option value (`vidstabdetect=result=…`, `sendcmd=f=…`, `lut3d=…`, `movie=filename=…`) hits ffmpeg's filtergraph parser, where `:` separates options and `\` escapes — so a raw Windows `C:\Users\x.trf` is mangled. **Always wrap such paths in `_pu.ffmpeg_filter_path()`** (converts `\`→`/` and escapes the drive colon as `\\:` — the only form that survives ffmpeg's two-pass parser; single-backslash and single-quoting both fail, verified empirically).
2. **`subprocess(..., text=True)` MUST pass `encoding="utf-8", errors="replace"`.** Windows defaults to cp1252-strict, so decoding ffmpeg stderr that echoes a Devanagari media path raises `UnicodeDecodeError` and crashes — even on a *successful* ffmpeg run (the decode happens in `communicate()` before the returncode check). `-hide_banner`/`-v error` do NOT suppress the input-filename line. Byte-mode captures (no `text=`) are exempt.
3. **Bare exe name + `cwd=` fails on Windows.** `CreateProcess` resolves argv[0] against PATH + the *parent* cwd, not the passed `cwd=`. rife/realesrgan (`ncnn-vulkan` binaries that need `cwd` for their `models/` dir) use the **absolute** binary path (`RIFE_BIN`/`ESRGAN_BIN`) on Windows; the `./exe` form only works on POSIX (child chdir's before exec).
4. **Windows-illegal filename chars** (`< > : " | ? *`) can't exist on NTFS — tests that create on-disk fixtures must use Windows-legal names (`_safe_filename` handles user uploads; `repair_media_paths` sanitizes only the leaf stem, which is already Windows-safe).
5. **A hand-editable config file on Windows can start with a UTF-8 BOM — read it with `_pu.read_text_config()`, never `read_text(encoding="utf-8")`.** Notepad and PowerShell **5.1**'s `Set-Content -Encoding utf8` both prepend `EF BB BF` (PS **7** does not, so this depends on which shell ran the script — and `powershell -File …`, the documented launch form, *is* 5.1). A BOM is **not whitespace**, so `.strip()` does not remove it and the `﻿` lands inside the first value. Two live instances, both Windows-only and both silent: `.env`'s first key parsed as `﻿ANTHROPIC_API_KEY`, so the key never loaded and the app reported it missing **while the file plainly contained it**; and `BUILD_ID` made `/api/version` report a sha matching no git object, defeating the one mechanism that exists to answer "which build?" (found by actually running the packaged exe — see Release identity). `read_text_config` is `utf-8-sig`, which decodes BOM-less UTF-8 byte-for-byte identically, so it is a strict widening. It is deliberately **separate from `read_text_utf8`**, which stays strict for media/EDL/sidecar reads where eating a leading `﻿` would be a content change rather than a fix. `build_win.ps1` also writes `BUILD_ID` through a BOM-less `UTF8Encoding $false` (a test guards the writer, since the reader fix alone would hide a regression); macOS `echo >` never had the problem.

Windows launch/build: `run.ps1` (parallel of `run.sh`, uses `PYTHONPATH=src`) and `build_win.ps1` (drives the `.spec` directly via `pyinstaller "Video AI Editor.spec"`). See "Running on Windows" above.

## The one idea that unlocks the codebase

**The EDL is the program; `dispatch()` is the only way to change it.** Every feature is a variation on one loop: something produces a tool call → `dispatch(store, tool, args)` mutates the EDL Pydantic tree in place → `store.commit()` persists it → the render pipeline re-derives video/audio from the EDL. There is no diff/patch layer and no inverse-op undo — the EDL tree *is* the timeline, on-disk snapshots *are* the history, and render output is a pure function of `edl.hash()`.

### EDL data model — `edl/schema.py`
- A Pydantic v2 model tree (`EDL_VERSION = 2`); **the model classes are the schema** (no separate JSON-Schema file). An `EDL` has a `Canvas` (default 1080×1920@30 vertical), `Track`s, optional `BrandKit`/`show_template`, `Markers`. `empty_edl()` (schema.py:220) pre-creates the standard tracks; compositing order is the track `z` index.
- **Timeline time ≠ source time.** On a `Clip`, `in_`/`out` index into the source file (trim); `start` places it on the timeline. `duration` is computed (`out - in_`). `in_` serializes as `"in"` (Pydantic alias).
- **A `TextClip`/`Sticker` stores an ABSOLUTE `end`, so anything that moves one in TIME must move `start` and `end` together.** A media `Clip` derives its span from `in_`/`out` and is immune; an overlay is not. `move_clip` assigned `start` alone, so dragging a text clip from 2–5s to 20s produced `start=20, end=5` — a negative span that validated and persisted. It compounds: `_ripple_overlays` remaps `start` and `end` *independently* (correct for a clip straddling a cut), so the next ripple collapsed the inverted pair to that function's 0.1s minimum-span floor and stranded it far out on the timeline. Since `edl.duration` is a **max over EVERY track**, a 0.1s sliver at 56s held the whole timeline open: delete a long video, add a short one, and the timeline still ran to the OLD length, playing black past the new clip — and every re-render encoded ~56s of black, which is why the stale preview also took so long to clear (`Preview.tsx` only shows its empty-state placeholder when `duration` is 0). Reconstructed from a real session's `ops.json`; the two symptoms had one cause. `set_clip_timing` already floors an inverted span, and `_ripple_close_gap`/`close_gap` only touch media clips — `move_clip` was the sole writer that could invert one. The fix is **forward-only**: an EDL already carrying stranded slivers keeps them (same stance as the stacked-text-overlay fix), because a silent load-time mutation of someone's timeline is worse than a visible leftover.
- Transform props (`x/y/scale/rotation/opacity`) are each `KFNum = float | Keyframe` — any can be keyframed. `keyframes.to_ffmpeg_expr()` emits **linear interpolation only** server-side; ease/curve modes animate in the browser preview but export as linear.
- **Every model inherits `_EDLModel`, whose only job is `validate_assignment=True`. Do not add a model to this tree without it** (a test enforces it). Constructing a Pydantic model always validated, which is why `add_mask`/`add_super_text`/`add_keyframe`/`set_aspect_ratio` were always safe — they build a new model. But **Pydantic v2 does not validate on assignment by default**, and the handlers mutate the tree by assignment: `cap.config.style = style` in `add_caption_track`, `setattr(obj, key, value)` in `set_property`. So `style='karaoke'` landed in the tree, was written to `edl.json`, and only surfaced as a ValidationError on the **next load** — by which point `MAX_UNDO` further edits had rotated every retained snapshot past the poisoning and the session opened with **zero clips** (QA round 5, VAI-01: total loss after 32 ordinary edits). Cost is ~0.5 µs vs ~0.14 µs per assignment.
- **Domain bounds live on the model, not in the handler**, for the same reason: `set_clip_transform` is not the only writer (`add_keyframe`, `motion_track`, `set_property` all reach `Transform`). `Transform` clamps opacity to [0,1], scale to [0.01,100], rotation to ±3600 and rejects non-finite; `Canvas` clamps w/h to [16,7680] **snapped even** (H.264 chroma subsampling + the round-4 letterbox parity math) and fps to [1,240]. Bounds are expressed as `field_validator`s, **not** `Field(ge=…, le=…)` — pydantic cannot attach a numeric constraint to a `float | Keyframe` union, and the validator handles both shapes. Out-of-range **clamps**, non-finite **raises**: rejecting on load would make an EDL that already holds a bad value unloadable, which is the exact failure class this all exists to prevent. Handlers that want a crisp 400 (`set_canvas`) reject *before* the clamp.
- **`TextClip`/`Sticker` transform x/y are ABSOLUTE CANVAS PIXELS, not relative to duration/track.** Two consequences enforced in `dispatch.py`, both easy to regress: (1) `cut_range`/`ripple_delete`/`trim_clip` — which only re-time the video track they operate on — additionally call `_ripple_overlays(edl, removed_start, removed_end)` to shift every text/sticker/caption clip's `start`/`end` by the same left-shift, only when the affected track is `v1` (a v2/PIP cut must not ripple the primary overlay timeline) and only for the actual clip kind removed (deleting a sticker itself must not ripple *other* overlays). The removed-interval math genuinely differs between trimming from the front (`in_` grows: removes `[old_start, old_start+delta_in)`, the head of the old slot) vs. the back (`out` shrinks: removes `[old_start+new_duration, old_start+old_duration)`, the tail) — don't try to unify these into one formula, verify with a written-out numeric trace first. (2) `set_canvas`/`set_aspect_ratio` call `_rescale_overlays_for_canvas_change()` to proportionally rescale every clip/sticker/text transform's x/y (handles both scalar and `Keyframe`-list values) — otherwise a sticker positioned near the bottom of a 1080×1920 canvas ends up off-screen after switching to 1920×1080.

### State + persistence — `edl/snapshot.py`, `edl/ops_log.py`
- `EDLStore(session_dir)` is the per-session state manager; `store.commit(tool, args, summary)` is the **single durability point**: recomputes duration, hashes the EDL, writes a numbered snapshot (last `MAX_UNDO = 30`), atomically writes `edl.json`, appends an `Op` (before/after hashes, tool, args, `by=user|claude`) to the append-only ops log, and **clears the redo stack**. Undo/redo restores snapshot files — **not** inverse-op replay. Read-only tools (`get_timeline`, `diarize`, `generate_hook`) deliberately skip `commit()`.
- **The redo stack (`EDLStore._redo_stack`) is persisted to `redo_stack.json`** (`_save_redo_stack()`/`_load_redo_stack()`), not just held in-process — it used to be a plain Python list, so it silently emptied whenever the store object was recreated (a real restart, or eviction from `main.py`'s `_STORES` LRU cache below), which read as "Redo does nothing" with no explanation even though the session's own `edl.json`/`ops.json` persisted fine. `store.redo_available` is surfaced through `undo_op`/`redo_op`'s return dict and `GET /api/sessions/{sid}`'s `redo_available` field so the frontend can disable the Redo button correctly instead of dispatching a guaranteed no-op.
- **`commit()` re-validates before it writes** (`_assert_reloadable`, using the exact `EDL.model_validate_json` call `_load_edl` uses, so the check means precisely "would a reload survive?"). An invalid tree raises `ValueError` → 400 to the caller that caused it, and **nothing is written** — instead of succeeding, staying fine in-memory for the rest of the process, and surfacing to whoever opens the project next. ~0.65 ms on a 130-clip timeline, and it reuses the one `to_json()` the snapshot + `edl.json` writes already needed.
- **`store.load_state`** records how this store got its EDL: `new` / `clean` / `recovered` (fell back to a snapshot) / `corrupt` (nothing parsed → empty timeline). `corrupt` and `new` both *present* as an empty timeline, which is why `save_project` used to write a valid `.vae` with `manifest.media == []` over a user's only other copy (VAI-02). `store.is_data_loss_state` is `corrupt AND still has no media clips` — deliberately AND-ed, so once the user adds footage the session is a real project again and a permanent latch doesn't trap them. `save_project` refuses in that state, warns on `recovered`, and bundles `store.edl.to_json()` rather than the on-disk `edl.json` (after a recovery the file on disk is still the unreadable one).
- `main.py` holds a process-global LRU cache of `EDLStore`s (`_STORES`, cap `VAI_STORES_CACHE_MAX=64`, guarded by `_STORES_LOCK`) — the lock matters because FastAPI runs sync endpoints in a threadpool. Eviction needs no flush; the cache is a rebuildable read cache. A separate per-session `threading.Lock` (`_session_lock(sid)`) serialises `/dispatch`, because `dispatch()` read-modify-writes that shared store and background jobs can hold a session for minutes.

### Dispatch engine — `agent/dispatch.py` (~2700 lines, the whole editing engine)
- A tool is a plain module-level function `fn(store: EDLStore, args: dict) -> dict`, callable **only** by being a literal entry in the `DISPATCH` dict at the bottom of the file. No decorators, no class framework — `dispatch()` just does `DISPATCH.get(tool)()`.
- **Adding a tool is a two-file edit with no shared source of truth:** (1) write the handler and add its `"name": fn` line to `DISPATCH`; (2) add a matching schema in `agent/tools.py` via the `_t(...)` helper and append it to `ALL_TOOLS`. The name string must match by hand — nothing enforces it. Not every dispatch tool is advertised to Claude: `DISPATCH` holds **102** unique tools, `tools.py`/`ALL_TOOLS` schematizes **96** for the chat LLM, and every advertised name resolves to a live handler (verified); the remaining 6 are reachable via `/dispatch` and MCP but invisible to Claude. **`tests/test_wave3_correctness.py` now enforces the registry by AST**: no duplicated module-level handler name and no duplicated `DISPATCH` key. Both had regressed — `set_track_muted`, `vocal_isolate` and `instrumental_isolate` were each defined twice with *different bodies* (Python keeps the last, so the earlier body was unreachable and any edit to it would be silently ignored) and were also listed twice as dict keys.
- Three callers share this **single mutation path**, all getting identical undo/ops-log/persistence: (1) Claude chat via `agent/loop.py`, (2) UI gestures via `POST /api/sessions/{sid}/dispatch`, (3) external agents via the MCP server.
- Many handlers are **composites** that call other handlers (`remove_silences` loops `cut_range` back-to-front so timeline coords stay valid; `apply_template` → `apply_hook_stack` → `generate_hook` + `add_super_text`), so one tool call can produce multiple commits/ops.
- Handlers defensively accept **arg aliases** (`index|idx`, `src|lut_path`, `target_lang|to`, `ratio|aspect`, `fit|mode`) because the same fn is reached from Claude, UI, MCP, and docs. User path args funnel through `_safe_src()` → `assert_path_allowed()`.
- **Any tool that DUPLICATES a clip must go through `_clone_clip()`** (`dispatch.py`) — `model_copy(update=…)` is **shallow** in Pydantic v2, so a bare copy hands both clips the SAME `Transform`, the SAME `effects` list and the SAME `ClipAudio`. Editing one then edits both, silently, with no error anywhere. Measured on a clip split at 4s: `a.transform is b.transform` was True, so `set_clip_transform scale=1.75` on the right half also scaled the left and `add_effect vignette` on one put a vignette on both. Reported as a **keyframe** bug with three symptoms that are all this one cause: a key added to the second half "also appeared on first half at the same place"; a key on the first half showed "at the starting of the video AND at the end of the first half" (one key at t=0, drawn on both halves at `c.start + 0` = 0.0s and 4.0s); and one "didn't show up in the video layer" on the half it was added to. Keyframe times are **clip-local** and `Timeline.tsx` draws them at `c.start + t`, so an aliased transform puts the same key at a *different absolute position* on each half — which is why it read as the keyframe moving rather than being duplicated. **The frontend was innocent** — `Properties.tsx` sends `time: playhead - clip.start` correctly and the diamond math is right; don't go looking there. It also **persisted to disk**: the aliased object is serialised once per clip, so both clips genuinely carry the duplicated state, and a reload only stops them tracking each other going forward — which made it look intermittent. Four sites were affected (`split_at` ×2, `cut_range` ×2, `duplicate_clip`, the batch duplicate) and `test_no_bare_shallow_model_copy_survives_in_dispatch` fails on any `model_copy` in that file without `deep=True`.
- **`dispatch()` validates args against the tool's advertised JSON schema** (`_validate_tool_args`) before calling the handler, so `apply_lut {src: true}` is a 400 instead of `Path(True)` → TypeError → 500 (VAI-03) and `add_sticker {position:'center'}` no longer reaches `float('c')` (VAI-04). **Four non-goals, all load-bearing — do not "tighten" them:**
  - **`additionalProperties` is NOT enforced** — it would break the arg aliases above and older UI builds.
  - **`required` is NOT enforced.** The round-5 plan assumed it was safe; the suite disproved it in one run. `split_at` declares `track` required but its handler defaults to `v1`, so the schema's `required` is advice to Claude, not a contract callers have honoured. Instead, `dispatch()` converts a handler's `KeyError` into a `ValueError` **only when the key is schema-declared and genuinely absent from `args`** — an internal KeyError still surfaces as the 500 it is.
  - **Coercible values are accepted** (`"3.5"` for a number), matching `_num()`'s long-standing tolerance. A `bool` never satisfies a numeric or string field (`isinstance(True, int)` is True in Python — that's the trap).
  - **Enum matching is case-insensitive and rewrites `args[key]` to the canonical spelling**, because `add_text` and `set_clip_fit` deliberately normalise case at storage; rejecting `'Pop'` broke them on day one.
  - A property may set **`"x-validated-by-handler": True`** to opt out of the generic enum check where the handler answers better (`add_transition` gives a did-you-mean over ~88 names). `loop.py::_strip_internal_keys` projects every `x-*` key out before the tool list goes to Claude, the same way `category` is dropped.
- Enum-constrained values come from **one source**: `add_effect` validates against `render.effects.EFFECT_BUILDERS` (the same registry `list_filters` reports, and `tools.py` now generates its enum from it via `_effect_names()` — the hardcoded list had already drifted, missing `color_grade`); caption `style`/`position` come from the `CaptionsConfig` Literal via `_literal_values()`.
- **A path argument is checked for EXISTENCE at dispatch time, not deferred to render.** `apply_lut` resolved a bundled *name* strictly (`list_luts` → `presets/luts/<name>.cube`, error if absent) but accepted any *path* unchecked, so a typo was stored on the clip as an `Effect(type="lut")` and only failed inside the ffmpeg filtergraph — where `_render_failure_message` saw "No such file or directory" and blamed the clip's SOURCE, sending the user hunting through footage that was fine. Same defect family as VAI-07, found by the round-5 end-to-end sweep rather than by the tester. That message now distinguishes a `.cube`/`lut3d` failure from a missing media file.
- **Normalised bboxes are enforced, not assumed** (`_norm_bbox`, used by `motion_track` and `object_erase`). Every bbox arg is documented 0..1 and nothing checked it, so a pixel bbox (`[10,10,100,100]`) made `ai/tracker.py` hand OpenCV MIL an init box ~100× the frame per axis; MIL sizes its feature buffers from the box area, so the **whole process was OOM-killed** — exit 137, no traceback, every session in it gone (VAI-06, and the likeliest contributor to the VAI-11 instability report). `tracker.track_object` clamps and floors independently: a library that can kill the process must defend itself, not trust its caller.
- Heavy-AI handlers **lazy-import** their deps (librosa, demucs, rembg, open_clip, pyannote, Real-ESRGAN) inside the function body and raise `RuntimeError` when missing, which `main.py` maps to **HTTP 422** — keeping core dispatch importable without the AI extras.

### Chat loop — `agent/loop.py`
Sends tool schemas (projected from `tools.py`, dropping the internal `category` field) + `SYSTEM_PROMPT`, runs the Anthropic tool-use loop (bounded `max_turns=8`, tool_result JSON truncated to 8000 chars), calls `dispatch()` per `tool_use` block, and streams SSE events: `text_delta`, `tool_use`, `tool_result`, `op`, `done`, `error`. The `op` event is how the UI learns the EDL changed.

**Every turn's `system` prompt is `SYSTEM_PROMPT + _live_context_block(store)`, recomputed each iteration of the tool-use loop** — a fresh `get_timeline(summary=True)` snapshot (duration + per-track clip counts/ids), never persisted into `history`. Without this, Claude answers purely from prior conversation text, including about footage from an earlier upload that's no longer on the timeline (confirmed live: a user uploaded a yoga video and asked to remove hand-raising moments; Claude replied "this is a screen recording, there is no woman" — describing a *previous* upload's stale transcript). `main.py`'s `upload()` also resets `chat.json` to `[]` when a video lands on a genuinely empty timeline (not on every upload — a mid-project upload, e.g. b-roll into existing footage, intentionally keeps history since it's still relevant). Relatedly, `get_transcript`/`add_caption_track`/`auto_caption` resolve `ingest.json` from `_current_v1_ingest_json()` — the CURRENT v1 clip's own `uploads/<stem>/` directory (siblings by construction, see `ingest_upload()`) — never `glob("uploads/**/ingest.json")[0]`, which has no ordering guarantee and can silently return a different upload's transcript in a session with more than one.

### Render pipeline — `render/` (one ffmpeg `filter_complex`, keyed by EDL hash)
- `render/compositor.py` compiles the **entire** EDL into a single `filter_complex` and one ffmpeg invocation: per-clip chains (seek → scale/pad → transform → effects → chromakey → speed) → timeline assembly (`concat`, or chained `xfade`/`acrossfade` when transitions exist) → V2 PIP overlays → text/sticker PNG overlays → audio fold.
- **A PIP is placed in TIME by `-itsoffset` on its input, and on the CANVAS by an x/y its lane must supply.** Reported as "PIP/overlay not working properly, instead of adding a layer on the video, it just applies a black box on the top left" — one sentence covering two independent defects, either of which produces that description:
  - **No time offset.** `enable='between(t,start,…)'` gates *when the overlay is drawn*, but the PIP's own frames entered the filtergraph at t=0, so by the time the window opened the stream had already ENDED and `overlay`'s default `eof_action=repeat` held the **last decoded frame** for the whole appearance. A PIP anywhere but t=0 was a still image of its own final frame — literally a black box whenever the clip ends dark, which is most clips. Measured with a 4s source of 1s colour blocks at `start=5`: the window showed YELLOW (source second 3) throughout where RED (second 0) was due; after the fix the walk is red→green→blue→yellow across 5.5–8.5s and empty either side. The **PIP audio path had the offset all along** (`adelay` in compositor.py), so the sound played in the right place while the picture was frozen — that asymmetry is the tell. Same defect the text-overlay path already fixed for animated overlays. Use **`-t <duration>`, never `-to <abs end>`**, alongside it: `-to` is an absolute input timestamp and `-itsoffset` shifts what it is compared against, so together they can truncate the input to nothing.
  - **No placement.** `add_clip` sets `x=w/2, y=h/2, scale=0.6` when it *places* a clip on a PIP lane, but a clip that arrives by being **dragged** kept `Transform`'s plain `x=0, y=0` — which `pip.py` reads as "centre this element on the canvas ORIGIN", emitting `overlay=x='(0.00)-overlay_w/2'`. Three-quarters off-screen, only the bottom-right corner visible, in the top-left of the frame: on a 720×1280 preview it occupied x0-223/y0-167 instead of x136-583/y472-807. `move_clip` now re-bases through `_rebase_transform_for_lane()` whenever a clip crosses **between v1 and a PIP lane** — in both directions, because those three fields mean different things on the two lanes (a v1 crop-pan/zoom vs. an on-canvas centre/size), so carrying the numbers across is not preservation. Skipped entirely when any of x/y/scale is **keyframed**, the same rule and reason as `set_clip_fit`'s reset. A move between two PIP lanes (v2→v3) changes nothing — same meaning, same numbers.
- **A PIP's PICTURE is drawn by the BROWSER in preview and baked only on export** (`build_pip_overlay_chain(..., preview=True)`), the same split — and for the same unavoidable reason — that text and stickers already use: a client cannot erase a baked pixel, so smooth direct manipulation requires client pixel ownership. `frontend/src/lib/pipDraw.ts` is therefore the preview's PIP renderer and **must mirror `pip.py` stage for stage** (box → framing → shape → rotate/opacity → overlay); export has no client, so any divergence surfaces as "the preview lied" the moment you export. Four things this drags along, each of which was a bug on the wrong side of it:
  - **The predicate `pipIsClientDrawn` must hold in THREE places** — `pip.py`'s preview branch (bakes or doesn't), `StickerLayer`'s paint loop (draws or doesn't), and `Preview.tsx`'s `videoFingerprint` (a *baked* PIP's placement must still trigger a re-render, since nothing else will show the change). Disagree one way and the PIP is drawn twice; the other way and it is drawn never. **A chromakey'd PIP is the one exception and keeps being baked** — a per-pixel key is the only picture stage a 2D canvas can't do at 60 Hz — so it trades live dragging for staying visually true. Reachable, not hypothetical: `remove_background` sets a key by itself.
  - **The preview stream-copy fast path is gated on `not pip_audio_clips`, NOT `not pip_chain`.** That path returns *before* the audio fold, and `pip_chain` was only ever a proxy for "this timeline has a PIP" — a proxy that held right up until a preview PIP stopped emitting video filters. It then admitted PIP timelines and stream-copied the chunks with the PIP's audio never mixed. Caught by `test_pip_clip_gain_is_honored` measuring −74.2 dB, i.e. silence.
  - **The hidden `<video>` elements must be IN the document** (`pipDraw`'s offscreen host). Detached is fine to *seek* and `drawImage` from, which is all this file originally did; it is not fine to **play**, which the flicker fix changed them to do. Blink runs a detached element, WebKit makes no such promise, and WKWebView is what the packaged macOS app renders in — so this is a defect that cannot appear on a Windows dev machine and lands on a Mac as "the PIP freezes on one frame during playback". The host is deliberately **not** `display:none` (an unlaid-out element may stop being fed frames) but 1×1/transparent/`pointer-events:none`. FrameScrubber's fallback `<video>` *is* `display:none`, correctly — it is only ever seeked.
  - **While PLAYING, play the element; do not seek it.** The playhead advances ~1/fps per frame against a max(1/fps, 0.03) tolerance, so every single frame re-assigned `currentTime`; each assignment starts an async seek, `readyState` dips below HAVE_CURRENT_DATA while it runs, and the loop painted its no-frame placeholder — 30 seeks/sec that never settle, which is exactly "the pip video keeps flickering when the video is played and sometimes it gets vanished". Seeks stay for scrubbing; playback corrects only real drift (`PIP_RESYNC_TOL`).
- **A PIP's box, shape and inner framing are ONE decision, and the crop order is load-bearing.** `circle` forces a **square** box (a circular mask over a 16:9 element is an ellipse — "when i chose circle it gave me ellipse"); `fit='cover'` takes the canvas aspect, which is what finally makes the Fill-frame checkbox do anything on a PIP lane (`pip.py` ignored `fit` entirely before, so the control was inert). Shapes are cut procedurally with **`geq`** in the stream's own `W`/`H` rather than by alphamerging `effects.render_mask_png`'s canvas-sized PNG — the element's pixel size depends on a source aspect this module never probes, so a canvas-sized mask would be the wrong size and off-centre. `Framing.rotation` turns the picture *inside* the shape while the shape stays put (distinct from `Transform.rotation`, which turns the whole element); it must be applied **before** the crop and the cover **grown first** to `w·|cos| + h·|sin|` by `w·|sin| + h·|cos|`, or the rotation drags transparent corners into the shape. Rotating therefore costs magnification — inherent to rotate-and-fill, not a choice. Contrast v1, which rotates **in place** and accepts cut corners because the canvas *is* the frame. The mask is applied before the rotate, so the shape turns with the element.
- **`Transform.opacity` on v1 is a fade toward BLACK, not an alpha channel — and until 2026-08-17 it was not implemented at all.** `compositor.py`'s per-clip chain had no opacity handling, so the value committed to the EDL, survived a reload, and changed nothing in the preview or the export. It was honoured for PIPs (`pip.py`), text and stickers, which is precisely why it looked implemented. It did worse than nothing: `Preview.tsx` applies its live CSS opacity **relative to what the visible render has baked in** (`liveCssTransform` divides by the baked value) and reads that baked value from the **EDL** — so the EDL said 0.3 while the frame was still at full brightness, dragging further down dimmed by the wrong amount, and dragging back **up** did nothing at all, since CSS opacity cannot exceed 1 and the "restore" it counts on never existed. Three things to keep straight:
  - **Not `pip.py`'s line.** A PIP is OVERLAID, so `format=yuva420p,colorchannelmixer=aa=` lets the layer beneath show through. v1 is the **base**: nothing is beneath it, so alpha there is discarded at yuv420p conversion. Multiplying RGB toward black is what the canvas already does (the letterbox is black) and what the browser does fading the element over the black preview pane — which is what makes the live preview and the bake agree.
  - **The multiply must happen in `gbrp`.** `colorchannelmixer` on YUV input scales the chroma **offsets** as well as luma, dragging 128/128 toward 0/0 — the picture tints hard green as it dims. The filter string looks identical either way; only pixels catch it, which is why `test_dimming_does_not_TINT_the_picture` measures RGB spread.
  - **A keyframed opacity uses `geq` with `T`, never the chain's lowercase `tvar`.** geq's expression namespace is its own (X/Y/W/H/N/T); lowercase `t` is not in it, so a `tvar`-built expression fails the WHOLE graph with `Unknown function in 't-0.0000)…'` — the render dies rather than animating wrong. `rotate` on the line above legitimately uses `t`, which is exactly why reusing `tvar` here looks right and isn't. `text_overlay.py`'s animated-opacity geq already had this right.
  - The source-preview canvas (`Preview.tsx`) applies the same fade via `globalAlpha` over its black fill. It REPLACES the `<video>` while up, so anything it does not reproduce simply vanishes from the preview — it ignored opacity entirely, so a dimmed clip jumped to full brightness the moment a rotation drag took over.
- **The source preview gets its OWN `<video>` pool (`sourcePreviewVideo`), never `pipVideo`'s.** `pipVideo` keys on `src` alone, so the instant the same file sits on v1 *and* on a PIP lane, `StickerLayer`'s paint loop and `Preview`'s source-preview loop hold the SAME element — and each calls `syncPipVideo` on it every frame with a **different clip trim**. The seeks never settle, `readyState` never reaches HAVE_CURRENT_DATA, and the source canvas paints only its black fill: **the main video goes black for the whole rotation drag while the PIP keeps drawing** (the PIP survives on `drawPipVideoFrame`'s `LAST_FRAME` fallback, which this path had no equivalent of), and releasing the pointer fixes it because the source preview unmounts and the PIP regains sole ownership. Reported as "when i rotate the video up to certain angle, after rendering, when i change or rotate the video, the video gets blacked out… when i leave the cursor, it works fine". Three things worth keeping:
  - **It only bites when the two clips point at DIFFERENT SOURCE TIMES.** At the same in-point both loops want the same instant and `syncPipVideo`'s tolerance suppresses the seek entirely, so nothing thrashes. The first repro used `in=0` on both and proved nothing; the live session had v1 at `in=0` and a circle PIP of the same file at `in=4.0125` (past the end of a 4.01s source). If you cannot reproduce a "two loops, one element" bug, check whether both loops actually *want different values* before concluding the mechanism is wrong.
  - **The pools must also be separate for `pausePipVideosExcept`**, which pauses every element it owns that is not a currently-active PIP — a v1 source is not a PIP at all.
  - **An armed-but-blank source canvas must not take the picture away.** The `<video>` is now hidden only once the canvas has actually PAINTED a frame (`srcDrawnRef`), and a decoder dip after that leaves the last painted frame rather than clearing to black — the same "stale frame beats a hole" rule the PIP follows. This is what turned the failure from "black rectangle" into "worst case, the old CSS stand-in".
- **`edl.hash()` (sha256[:16] of canonical JSON) drives the render cache.** Preview keys output by hash and returns instantly on a hit; an `_INFLIGHT` dict collapses concurrent identical renders.
- **Chunk cache** (`render/chunks.py`): with no V1 transitions, each clip renders once to a content-fingerprinted mp4 and the timeline becomes a fast `concat` — editing one clip re-renders only that chunk. Disabled under transitions (xfade needs both streams in one graph).
- **Audio-only remux fast path**: a `_video_only_fingerprint` lets a music/vo/gain-only change re-mux a cached video-only mp4 with `-c:v copy` instead of re-encoding.
- Encoder selection is a **probe-based ladder** (`compositor._usable_encoder`, `@lru_cache`): VideoToolbox → NVENC → QSV → AMF → libx264, picking the first that passes a real ~0.1s null-encode (a *listing* grep of `ffmpeg -encoders` is not enough — it lists `h264_nvenc`/`qsv`/`amf` even with no matching GPU). On a Mac this still resolves to VideoToolbox with byte-identical args as before. Preview vs export is a quality/resolution split, not a different pipeline. `loudnorm` runs **export-only** (its 192k internal rate yields 96k AAC that Safari rejects in mp4). Renders write to a PID/thread-scoped `.part.mp4` then swap in via `_pu.replace_with_retry()` (retries on Windows `PermissionError` when a Starlette `FileResponse` still holds the preview open; first-try-succeeds on macOS), so a polling `<video>` never sees a torn file.
- **Text/stickers are NOT ffmpeg drawtext.** Brew ffmpeg 8 lacks libass/libfreetype, so `render/text_overlay.py` rasterizes each `TextClip`/`Sticker` to an RGBA PNG via Pillow (role fonts, Noto fallback for non-Latin), caches by content hash, and composites via `overlay=` gated on `enable='between(t,start,end)'`. `ass_writer.py` is a dormant alternate path. **Cache writes are atomic** (`_save_png_atomic`: save-to-temp, `_pu.replace_with_retry()` — the same pattern as the mp4 `.part` swap above) and reuse is gated by `_png_is_valid()` (size check + `Image.open().verify()`), not a bare `exists()` — a killed render or two concurrent renders racing the same content-hash path used to leave a 0-byte/torn PNG that a later render fed straight to ffmpeg as `-i`, crashing with "Invalid data" (surfaced to users as a spurious "upload failed" toast). `effects.py`'s mask-PNG cache follows the identical atomic-write + validity-check pattern (`mask_png_is_valid`). **`build_overlay_chain(..., preview=True)` skips baking TEXT/caption clips AND stickers** — the browser draws both live with no ffmpeg round-trip (`TextLayer.tsx` for text/captions, `StickerLayer.tsx` for stickers). Export always bakes both (no client layers there), so this flag only changes the in-app preview. **Baking either one in preview double-draws it**: for text that was "big and small captions simultaneously" (server + client copies at different sizing math); for stickers it was a GHOST — the baked copy sat frozen at the pre-drag position for the whole gesture *and* the commit→re-render gap, so a drag showed two stickers and, on release, the live one vanished while the stale one lingered at the old spot ("it disappears and leaves a trail"). A client cannot erase a baked pixel, so smooth direct manipulation requires client pixel ownership — stickers reached the same conclusion text did. Two consequences that must move together: `Preview.tsx`'s `videoFingerprint` excludes sticker tracks (re-baking them is what created the gap), and `StickerLayer` draws the **artwork PNG**, never the OS emoji glyph — the glyph is a different design from the Twemoji the export bakes, so painting it made a sticker visibly change appearance the moment you let go. `add_sticker` therefore copies fetched emoji art into `<session>/uploads/stickers/`, and `GET /api/sessions/{sid}/sticker/{clip_id}` serves any sticker's artwork by resolving the path through that session's own EDL — `GET /files/{kind}/{name}` is (correctly) confined to the session dir, so a brand-kit end-card or any absolute-path sticker would otherwise 404 and draw as an empty box while exporting perfectly.
- **Emoji INSIDE a text clip are composited as images, not glyphs.** The role fonts (Anton, Bebas, Inter, Montserrat) carry no emoji, so `render_text_png` used to push text through `_strip_emoji` first — typing "🔥 SALE" exported "SALE" and a pure-emoji clip exported a blank PNG ("I was unable to apply the emojis through the text section"). Both `render_text_png` and `TextLayer.tsx` now tokenize the string and paste the same Fluent 3D artwork a sticker uses, each emoji occupying a square of `EMOJI_BOX_RATIO × font size` that participates in wrapping — **that constant, and `_emoji_clusters`/`emojiClusters`, are duplicated on both sides and must move together or the preview wraps differently from the bake.** Two traps: `_EMOJI_RE` ends in `+`, so a match is a RUN and must be split into renderable clusters ("😍🤩" was looked up as `1f60d-1f929`, found nothing and drew nothing) while genuine multi-codepoint emoji — ZWJ sequences, flag pairs, skin tones, keycaps — stay whole; and the text-PNG cache key must hash the FULL text (it hashed the stripped text, so "SALE" and "🔥 SALE" collided). The browser fetches artwork from `GET /api/emoji/{codepoints}.png`, which is global and read-only — letting it paint emoji with the OS font instead would put Apple/Segoe art in the preview and Fluent in the delivered file.
  - **VERTICAL placement is measured per side, NOT a shared constant** (`_cap_band_mid` / `capBandMid`): the emoji square centres on the text's **cap band**. A single `EMOJI_TOP_RATIO = 0.06` em-box fraction could not be right for both, because where the cap band sits inside the em box is a per-font property *and* the two renderers start from different origins — Pillow's `draw.text()` draws from the ASCENDER TOP, canvas `textBaseline='middle'` from the EM-BOX MIDDLE. It put the bake 26.5px above the text and the preview below it: misaligned on both sides and disagreeing with each other, which is the one thing this whole subsystem exists to prevent. Horizontal advance (`EMOJI_BOX_RATIO`) stays a shared constant — it drives wrapping, so it must be identical, and it has no font-relative origin problem.
  - **Wrap units carry a `glued` flag (`_emoji_words` / `wrapUnits`) so the wrapper cannot invent spaces.** An emoji must be its own wrap-word (the text font measures it at ~0px, so a glued one overflows the line by exactly its box), but `_wrap` then rejoined words with a hard `" "` — laying "GG🔥🔥" out as "GG 🔥 🔥" and spacing emoji **0.32 em** apart against a 0.24 em word space ("the space between the emoji is too much"). Now 0.086 em, and a space the writer *did* type still survives. General rule: splitting a string for measurement must not change what gets drawn.
  - **Artwork arriving must itself trigger a repaint** (`emojiGeneration()` in `lib/emojiArt.ts`). `TextLayer`'s rAF loop skips a frame unless the playhead moved; artwork is requested DURING a draw and lands after it, so a PAUSED preview painted exactly one frame — the one with the fetch still in flight — reserving each emoji's box and leaving it blank forever ("it left an empty space in place of the emoji"). The counter (bumped on load AND on error) is compared alongside the playhead, the same role `fontsReady` plays for a late-loading font. Any future layer that both throttles redraws and paints async-loaded assets needs the same signal.
- **Emoji sticker artwork is FETCHED, never an OS font** (`ai/emoji.py`) — that is the invariant; *which* set it fetches is a look decision layered on top. Preview and export must show identical pixels, and a Mac and a Windows user opening the same project must too; drawing the glyph with a system font gives Apple Color Emoji vs Segoe UI Emoji vs the baked art — three different designs. **The set is Apple/iOS artwork at 160×160**, from `iamcal/emoji-data@16.0.0/img-apple-160`. It was Noto (Android, 512px) for one round; the switch back to Apple is a deliberate, user-directed choice and the reasoning is in the module docstring so nobody "corrects" it by accident.
  - **160 is Apple's ceiling, not the mirror's.** Apple Color Emoji is an `sbix` BITMAP font with strikes 20/32/40/48/64/96/160 (verified via `tmm1/emoji-extractor`, which reads the system font). `img-apple-320`/`-512` 404, `emoji-datasource-apple` stops at 64, and Emojipedia serves 160 even from its `/thumbs/320/` path. **There is no higher-resolution Apple artwork to find — don't go looking again.**
  - **What 160 costs is narrower than it sounds.** Emoji *inside text* render at `size × EMOJI_BOX_RATIO × EMOJI_INK_RATIO`; the largest role (`hook`, 170pt) needs 156px, so **every text role downscales and stays sharp**. Only standalone stickers upscale (422px ÷ 160 = 2.64×), and Apple's gradient-heavy art survives that better than hard-edged vector would.
  - **Apple wins on consistency**, which is why the fallbacks barely fire: it covers **3778 of the 3781** RGI emoji (99.9%), flags included. Exactly three fall through to Noto (♀️ ♂️ ⚕️). Under Noto-primary every flag came from Fluent — a visibly different house style inside one line.
  - **The licence is the real cost, accepted deliberately.** Apple's emoji are Apple's copyright on a third-party mirror: fine locally, a genuine redistribution question if an export with a baked sticker is published commercially. The openly-licensed sets stay wired up (Noto Apache-2.0/OFL, Fluent MIT, Twemoji CC-BY 4.0) so reverting is one constant. `test_the_proprietary_primary_is_a_documented_choice` **inverts the old gate**: using Apple is allowed, using it *silently* is not — it fails if the module docstring stops explaining the trade.
  - **Filename spelling is per-source on three independent axes and every one was verified live**, because a wrong guess doesn't error — it 404s, falls through, and that one emoji silently renders in the wrong style. Apple: dash-joined, **zero-padded to 4**, **VS16 kept** for legacy dingbats (`0023-fe0f-20e3`, `2764-fe0f`; plain `2764` 404s). Noto: `emoji_u` prefix, `_`-joined, padded, VS16 always stripped. Fluent/Twemoji: dash-joined, unpadded.
  - **The cache namespace must change on every chain change** — now `…/emoji/apple2/`. Note it is `apple2`, not `apple`: an earlier round already used `apple/` with a chain that had no Noto, so its entries for the emoji Apple lacks came from a different source. **A namespace identifies the whole chain, not just its first link.** Prior namespaces (`noto`, `apple`, `fluent3d`, bare root) stay readable **newest-first** as offline fallbacks.
  - **`EMOJI_INK_RATIO = 0.92` gives the emoji a side bearing of our own** (`text_overlay.py`, mirrored in `TextLayer.tsx` — they must move together). A text glyph has side bearing, a PNG doesn't, so an emoji butted against neighbouring text ("GG🔥" with the G's stroke touching). Do NOT "simplify" this away on the theory that the artwork already has margin: measured, **Apple's own tiles run 0.000 (😊 😂 🎉, edge-to-edge) to 0.119 (🔥)**, so spacing would otherwise be whatever each artist happened to leave. The advance is unchanged, so wrapping is unaffected.
  - Finally, the **text-PNG cache key carries a version prefix** (`v9`) that must be bumped on any artwork or placement change — nothing else in that key tracks either, so a stale hit silently exports the old art forever.

## Desktop app assembly

**The whole thing is a single FastAPI process.** At import time `main.py` mounts `frontend/dist` at `/` as `StaticFiles(html=True)`, so `/` is the editor and `/api/*` is the backend on the **same origin** — no separate frontend server in production. Because `/` is a catch-all mounted **last**, every real API route must be declared before that mount — **route ordering is load-bearing**.

`desktop.py` is an in-process wrapper: it starts uvicorn on a daemon thread in the same process, polls `/api/health`, then opens a pywebview native window (OS webview — no Electron). In dev it auto-runs `npm run build` if `frontend/dist/index.html` is missing; in a frozen `.app` it hard-exits instead. Almost every filesystem lookup (`frontend/dist`, `VERSION`, presets, fonts) is **`sys._MEIPASS`-then-repo** to work both bundled and from source.

**`desktop.py` (the PyInstaller entry) MUST use absolute imports, never `from .`.** PyInstaller freezes the entry script as the top-level `__main__` (the `.spec` and `build_app.sh` both point at the *file path* `src/video_ai_editor/desktop.py`, not `-m`), so `__package__` is unset and any package-relative import raises `ImportError: attempted relative import with no known parent package` in the built EXE/.app — even though the package is bundled. This is **invisible in every dev path** (`run.sh`/`run.ps1` use `python -m …`, which sets `__package__`; pytest uses `pythonpath=["src"]`) and reproduces **only** in the frozen artifact. Use `from video_ai_editor import …` in `desktop.py`; the absolute name resolves regardless of `__package__` because `collect_submodules('video_ai_editor')` bakes the package into the PYZ. (Contrast `main.py`, which *can* use `from .` — it's always loaded via the absolute string `"video_ai_editor.main:app"` passed to `uvicorn.run`, so it's imported *with* a parent package.)

## Import-time config chokepoint — `config.py`

Importing `config` runs side effects and every entry point hits it before shelling out:
- **Augments `PATH`** so shelled-out binaries resolve regardless of launch method: on macOS the Homebrew/MacPorts bins (a double-clicked `.app` inherits launchd's minimal PATH); on Windows the winget-ffmpeg package dir (`%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg*\...\bin`, since Gyan.FFmpeg famously isn't put on PATH).
- **Loads `.env` with non-standard precedence:** real shell env always wins; among files the **first loaded wins** (only sets keys not already set), order `<repo>/.env` then the per-OS user config dir's `.env` (`_pu.user_data_dir("Video AI Editor")` — `~/Library/Application Support/…` on Mac, `%APPDATA%\…` on Windows). The user-level dir is how a shipped app picks up `ANTHROPIC_API_KEY` (the repo `.env` is invisible inside the read-only bundle). Note: `.env` values are read literally — inline `# comments` after a value become part of the value.
- **Creates `WORKDIR`** (dev `<repo>/workdir`; frozen `<user data dir>/workdir`, per-OS).
- **`VAI_ALLOWED_ROOTS` splits on `os.pathsep`** (`;` on Windows, `:` on POSIX) — not a hardcoded `:`, which would shred `C:\` paths.
- Key vars: `CLAUDE_MODEL=claude-sonnet-4-6`, `WHISPER_MODEL=small` (fast, for uploads) vs `WHISPER_CAPTION_MODEL=large-v3` (captions), and `VAI_RESTRICT_PATHS` (default **OFF**) — flip on for hosted deployments to force tool path args under `WORKDIR`/`VAI_ALLOWED_ROOTS`.

## Storage — the filesystem is the database

No DB. Everything is session-scoped under `WORKDIR/s_<hex>/` with fixed subdirs `uploads/ previews/ exports/ cache/ snapshots/` (`storage.py`). `storage.py` is path/meta plumbing; real state lives in `EDLStore`. Portable projects (`storage_project.py`): a `.vae` file is a ZIP of the state JSON + `media/` + `manifest.json` (caches excluded — they regenerate). `load_project()` **always creates a new session**, extracts media to `uploads/imported/`, and rewrites absolute `src` paths via the manifest remap — so importing the same `.vae` twice yields two independent sessions. **`_media_srcs` must collect `Sticker.src` as well as `Clip.src`** — it was `isinstance(c, Clip)` only, so no sticker PNG was bundled and none was remapped on load; the restored EDL still pointed at the *original* session's `uploads/stickers/` (and, for emoji, at a per-machine `user_cache_dir/emoji/…`). That resolves fine on the authoring machine, which is why it went unnoticed — but move the `.vae` anywhere else and every sticker's file is gone, and `text_overlay` skips a missing sticker **silently**, so the symptom is "my stickers just aren't there" with no error. **`save_project` also refuses on a corrupt session** (`store.is_data_loss_state`) — see the `load_state` bullet under State + persistence.

## HTTP API, MCP, async jobs — `main.py`, `api/`, `agent/mcp_server.py`

- `api/` has **no routes** (`api/__init__.py` is empty) — only `hardening.py` and `jobs.py`. `hardening.install(app)` adds a request-context middleware, a uniform error envelope `{error:{code,message,request_id}}` + `X-Request-ID`, a 60 rps/IP rate limiter, and hidden `/livez` `/readyz` (503 if ffmpeg absent) `/metrics`. An `HTTPException.detail` that is a **dict** lands under `error.details` (not `error.message`); a bare `ValueError` auto-converts to 400.
- **Async jobs:** uploads run whisper in a `BackgroundTask` (upload returns `transcript_pending:true`, fetched later via `GET /transcript`). Preview/export **and `/dispatch`** support `wait=0` → `202 {job_id}` polled via `GET /api/jobs/{id}` (`JOB_MANAGER`, in-memory). `wait=0` works for **any** tool, but `main.py::ASYNC_DISPATCH_TOOLS` (mirrored in `store.ts`, and a test asserts the two lists agree) names the ~10 that load an ML model and walk every frame — held on the sync path each pins a request-threadpool worker for minutes, which is the concrete mechanism behind the "app becomes unresponsive" reports (VAI-09/VAI-11). The job worker re-resolves the store via `_store(sid)` under `_session_lock(sid)`, since the LRU cache may have evicted and rebuilt it while the job was queued.
- **Stability guards, added in round 5 — don't undo them.** `/livez` is `async def` on purpose: a `def` endpoint runs on the bounded anyio worker threadpool every sync route shares, so a saturated pool made a healthy process report dead. `compositor._RENDER_SLOTS` (a `BoundedSemaphore`, `VAI_MAX_CONCURRENT_RENDERS`, default 2) wraps `_render` — the single chokepoint both preview and export pass through, and it never recurses. `_INFLIGHT` only collapses renders of the *same* EDL hash; N different hashes still launched N core-saturating ffmpeg processes. ffmpeg/ingest failures map to **422** with a stderr tail — `_render_failure_message()` pattern-matches the stderr tail for `st_/text_/sa_`-hash or `mask_*` overlay-cache filenames and substitutes a friendlier message than raw ffmpeg output. Missing/invalid `ANTHROPIC_API_KEY` only warns and disables the chat pane — the editor works without Claude.
- `GET /api/sessions/{sid}` includes `redo_available: bool` (mirrors the on-disk `redo_stack.json`, see the snapshot/persistence bullet above) so the UI can grey out Redo instead of guessing from local state. `add_clip`/`move_clip` raise `ValueError` (→ **400**, via the bare-`ValueError`-to-400 rule above) when a media `Clip` targets a non-video/audio-family track — see `_v_track_for_media()` under Frontend below.
- `DELETE /api/sessions/{sid}` removes a session dir. **`sid` is untrusted URL path input and is validated against `storage.is_valid_session_id()` (`^s_[a-zA-Z0-9]{6,64}$`) at BOTH layers** — the route 400s a malformed id before any filesystem op, and `storage.delete_session()` re-checks the id shape AND that the resolved path is a direct child of `WORKDIR` before `shutil.rmtree` (`_pu.rmtree_with_retry`, for Windows open-handle locking). Without this, a `sid` like `../../Documents` was an arbitrary-directory-deletion primitive. (Starlette normalizes `..` out of URL path params before routing, so it never reaches the handler through a browser — but don't rely on that; the storage-layer check is the real guard for any caller.)
- **Export** (`POST /api/sessions/{sid}/export`) takes `height`/`fps`/`crf`/`container` (`ExportRequest`). Output is MP4 (default) or MOV — both H.264/AAC via the same `mov` muxer, only the extension differs; `render_export`'s `container` param must be allowlisted (`in ("mp4","mov") else "mp4"`). `crf` IS honored on hardware encoders now (VideoToolbox `-q:v` via `_crf_to_videotoolbox_qv`, mapping the 0-51 crf scale onto its 0-100 higher-is-better knob; nvenc/qsv/amf best-effort onto `-cq`/`-global_quality`/`-qp`) — it used to be wired only to the libx264 fallback, making the UI Quality selector a silent no-op on Mac. The TopBar Export popover exposes resolution + quality + format; it portals to `document.body` (escapes `.topbar`'s overflow clip).
- **MCP server** at `POST/GET /mcp`: a hand-written JSON-RPC 2.0 adapter (no SDK) into the **same** `dispatch()` machinery. It drives one lazily-created **"active" session** (`_MCP_ACTIVE_SESSION`); any `tools/call` can override targeting with a `session_id` arg (popped before dispatch). Results carry `_meta.session_id`. `tools/list` advertises only tools that exist in `DISPATCH`.

## Frontend — `frontend/` (React 19, Vite, Zustand, WebCodecs)

- A single flat **Zustand store** is the source of truth and **never optimistically edits the EDL.** Every gesture and every Claude tool call funnel through `store.dispatch()` → `POST /sessions/:id/dispatch` → `refreshSoon()` (~120ms debounce) re-fetches and overwrites the EDL wholesale — the frontend mirror of the single-mutation-path principle. `dispatch()` tracks an in-flight counter (`state.pendingOps`) surfaced as a small "⋯ Applying" toolbar pill, and wraps the call in try/catch → `toast.error()` on failure — edits used to fail silently with zero UI feedback.
- **`Preview.tsx`'s `videoFingerprint` hashes the WHOLE per-clip object** on video/audio-family tracks (`{id, clips: t.clips}`), not a hand-picked field list — this is deliberate: `types.ts`'s `Clip` interface doesn't declare `speed`/`effects`/`transform`/`audio` (see below), so a field-enumeration fingerprint silently drifts stale every time the backend schema grows a new video-affecting property. This is what makes speed/color-grade/transform/volume/fade edits actually re-render the preview instead of committing to the EDL invisibly — mirrors how `edl.hash()` (the server render-cache key) hashes the entire EDL rather than a subset. Live transform preview (`liveTransform`, a pure CSS transform during a drag) is cleared on the `<video>`'s `onLoadedData` — i.e. once the NEW render has actually loaded — not eagerly on pointer-up, or the preview visibly snaps back to the pre-drag frame for the gap between commit and re-render; a bounded safety-net timeout force-clears it if the expected reload never lands (render failure/aborted fetch).
- **EVERY transparent overlay canvas must CLEAR IN DEVICE PIXELS, never CSS pixels.** The canvases size their backing store to `Math.round(cssSize * dpr)` and then draw under a `setTransform(dpr, …)`, so a `clearRect(0, 0, cssW, cssH)` only reaches `cssW * dpr` device px. At a **fractional** dpr those two differ, and the last device column and row are never erased — they keep whatever was painted there **forever**. Reset the transform first: `setTransform(1,0,0,1,0,0)` → `clearRect(0, 0, cv.width, cv.height)` → restore. This is the "phantom colour strip … when I hover them at the right side of the video", reported **four times** and surviving three wrong diagnoses (a GPU sampling artifact, the splitter's hover tint, the sticker being dragged half off-frame) because it is invisible wherever anyone looked for it: headless Chromium at dpr 1 cannot reproduce it. Measured in the packaged WebView2 window at dpr 1.25 — canvas cssW 914 → backing 1143 while the clear reached 1142.5, leaving accent ink (`#5b8dff`) in columns 1139–1142 that was **byte-identical** before a drag, after dragging right, and after dragging back, i.e. never redrawn, just never erased. Two follow-ons: fractional dpr is **not** Windows-only (125% scaling makes it routine there; a Mac on a scaled Retina mode hits it just as well), and fixing one canvas is not fixing the bug — `StickerLayer`, `TextLayer`, Preview's source canvas and Timeline's label/playhead canvases all needed it. The **only** exempt canvas is Timeline's main one, which repaints an opaque background over its whole area immediately after clearing.
- **A ROTATED v1 clip previews from the RAW SOURCE, not from CSS over the last render** (`lib/sourcePreview.ts`, gated by `sourcePreviewApplies`). v1 rotation is baked **in place**, which genuinely destroys the corners — 27.5% of the picture at 61° — so once a clip is committed at an angle, no CSS transform of that render can recover what was cut, and dragging the slider back toward 0 showed a progressively more cropped picture that only healed on release ("the video got cropped from the rotation, this happened when my cursor was holding at 0 degree"). Drawing from the untouched source is the only thing that can be correct mid-gesture. The trade is explicit: during that drag the picture is the **ungraded** source (no effects/LUT), which is why it is scoped to v1, non-`cover`, non-keyframed, and only when the clip's committed rotation is already non-zero.
- **Chat streaming is SSE-over-fetch, hand-parsed in `ChatOverlay.tsx`** (not `EventSource`, because it's a POST): reads `res.body.getReader()`, splits on `\n\n`, JSON-parses each `data:` line. On an `op` event it `refresh().then(renderPreview)` — the bridge that makes Claude's edits appear.
- **`FrameScrubber.tsx`** is a WebCodecs pipeline (mp4box.js demux → `VideoDecoder`, bisect to keyframe) for frame-accurate scrub, with an automatic hidden-`<video>` fallback from five distinct failure points. The playback clock is a rAF wall clock (migrated off `requestVideoFrameCallback`) so the playhead keeps moving even on render failure. **The clock only follows `<video>.currentTime` when it moves in the play direction** — a mid-playback edit reloads the `<video src>` to the new render's URL, resetting `currentTime` to 0 even though the wall-clock-tracked playhead is still mid-timeline; naively following any change (regardless of sign) yanked the playhead backward-then-forward-from-zero. A `resyncing` flag ignores the video clock until it's caught back up within a tolerance of the wall clock (the existing playhead-sync effect actively seeks the reloaded video to the right spot, so this converges in ~1 frame). `onTimeUpdate` is gated to only drive `playhead` while paused, for the same reason (it fires independently of the rAF loop and would otherwise race it).
- **The scrubber canvas is TEMPORARY, so every frame it paints is a promise about what the `<video>` will show when it fades out.** The canvas covers a paused seek and then hands the picture back; if the two disagree, the picture visibly jumps a beat after the gesture — reported as "the video stutters just a little bit after I pause, and the same when I move the playhead". Measured with a fixture whose frame N is a flat grey of luma N (so the displayed frame index is readable from the pixels) plus a rAF recorder sampling the visible element: **canvas frame 165, `<video>` frame 163**, on every paused seek and every single-frame step. Three separate causes, all of which had to go:
  - **The walk assumed decode order == presentation order.** mp4 sample tables are in DECODE order while `cts` is COMPOSITION time, and the preview is libx264 with its **default B-frames** (verified on a real preview: `has_b_frames=1`, `pict_type=B`), so a GOP arrives as `I P B B P B B…`. The old walk stopped at the first sample whose `cts` passed the target — in that stream the P frame that *displays* two or three frames later — and stopped **before feeding the B frames that actually cover the target**. Even with no B-frames it deliberately included "the first sample whose cts > target … (closest match)", which is +1 frame. `<video>.currentTime = t` shows the frame whose interval CONTAINS t, so the correct rule is **the greatest `cts` ≤ target**, decoding every sample from the keyframe up to it (the ones above the target in that span are references the covering frame depends on — decode them, never paint them). The rule is pure and unit-tested in **`lib/frameWalk.ts`**; the decoder's output gate now paints on an exact `paintUs` match (±2µs) instead of "covers-or-follows", because a covers-or-follows gate paints every frame from the target onward and the decoder emits in presentation order, so the *last* one won. **That exact gate carries one deliberate safety net**, because it is the only claim in the scrubber that cannot be measured on the engine it matters most for: WebCodecs *requires* a decoded `VideoFrame.timestamp` to echo its `EncodedVideoChunk`'s, Chromium does, and WKWebView is unverified — while the cost of being wrong is asymmetric, since an unmatched gate paints **nothing** and leaves a blank canvas over an otherwise correct `<video>`. So a `painted` flag (reset per seek, alongside `paintUs`) lets the first frame arriving *past* the target paint when the exact match never landed: presentation order makes that frame proof the match is not coming, and painting it degrades to the pre-existing covers-or-follows behaviour (≤1 frame late) rather than to blank. On a conforming decoder the exact branch always fires first, so it is unreachable — re-measured on the frame-numbered ramp fixture after adding it: pause/seek/step/drag all still settle with canvas and `<video>` on the SAME frame (22/22, 163/163, 164/164, 144/144) and zero frame changes after settle.
  - **The `<video>` seek was skipped for small moves.** The defer threshold was 0.05s while a frame at 30fps is 0.033s, so a single-frame step queued no seek at all: the canvas showed the stepped frame, then hid 250ms later and revealed the `<video>` still on the original frame — the step undid itself (`currentTime` never moved for the whole gesture). The threshold is now a **quarter frame** of `edl.canvas.fps`.
  - **The pause transition scrubbed to the pre-pause playhead.** `justPaused` deliberately pulls `playhead` FROM the video (so the pause itself doesn't rewind), but the scrub block in the same effect run then seeked the scrubber to the stale `playhead` in its closure — the canvas faded up on the frame BEFORE the one on screen and faded back 230ms later. Measured: stopped on 55, canvas showed 54, back to 55. A pause now takes no canvas at all (the `<video>` is already displaying the right frame — there is no seek to hide), and neither does any move smaller than a quarter frame, including the `<video>`'s own settle echo, which `onTimeUpdate` also drops for the same reason (writing the echo back counted as a playhead change and stood up a whole uninvited reveal ~250ms after the user stopped).
- **On v1, a clip's `start` is NOT where it plays — `Timeline.tsx` draws OUTPUT positions** (`lib/timelineLayout.v1Layout`, a pure function mirroring `EDL.transition_overlap()` rule for rule). `xfade` overlaps two clips, so every clip after a transition plays *earlier* than its `start`, and the canvas drew them at raw `start * zoom`. Reported as "the video duration is 8 sec, yet it plays only up to 7 sec": on the real session (8s split at 2/4/6, transitions at 2.0 and 4.0 → renders 7.0s) the strip was drawn out to 8.0s, so the last second was unreachable — and worse than that stray tail, **every clip after the first transition sat up to a second right of its picture**, putting the playhead over clip 3 while the preview showed clip 4. Four things follow, and they must move together:
  - **The hit list and the draw loop use the same shifted `start`**, or clicks select a clip other than the one under the pointer — they already shared this bug's mirror image for speed-adjusted clips.
  - **The seam affordance is drawn at the MIDDLE of the overlap** (`seams[].outAt = boundary - cumulative - overlap/2`), which degrades to the exact cut position when there is no transition. Its `at` stays EDL time, because that is what `add_transition`/`remove_transition` are called with.
  - **The overlap WARNING is tested against EDL positions, never the drawn ones.** Under a transition the drawn rects overlap *on purpose* — that is what a cross-dissolve looks like — so testing the drawn values flagged every transition as corrupt data with the dashed outline meant for genuinely broken clips.
  - **Pointer→time for a tool argument needs the inverse** (`edlTimeFromOutput`). A drag commits a *delta* so it is immune, but dropping new media onto a v1 lane that already has transitions would otherwise land it earlier than the pointer by the accumulated overlap. Overlay lanes carry no transitions, so there the mapping is the identity — and the playhead/ruler are already output time and must NOT be converted.
  The EDL is deliberately left alone: rippling the stored starts would make clips overlap in the data, tripping `_first_free_gap`, `_repack_media` and the overlap warning, all of which correctly assume v1 is a non-overlapping sequence.
- **`Timeline.tsx`'s `<canvas>` is sized to the full timeline CONTENT (`contentW`/`contentH`), not the viewport** — `.timeline-canvas-wrap` is `overflow:auto` and genuinely scrolls it; a separate small canvas draws just the track-label column and is kept pinned via a manual `wrapRef` `scroll` listener setting `label.style.transform = translateX(scrollLeft)` (CSS `position:sticky` doesn't work here — the label needs to overlay the main canvas's rows, not stack after it in flow). `contentH` is **content-only** (`headerHeight + tracks*(rowH)+…`), NOT `Math.max(size.h, …)` — clamping to the viewport height made `wrap.scrollHeight <= clientHeight` even when rows genuinely overflowed, defeating vertical scroll. **The wheel handler is a native `addEventListener('wheel', …, {passive:false})` effect, NOT a JSX `onWheel` prop** — React attaches wheel/touch listeners passive by default, so `preventDefault()` inside a JSX handler is a silent no-op (Chrome logs "Unable to preventDefault inside passive event listener"), which broke the `⌘`-zoom guard too. Wheel mapping: `⌘/Ctrl+wheel` zooms; `shift+wheel` always pans horizontal; a plain vertical wheel **scrolls vertically when the rows overflow** (`canScrollV && |deltaY|≥|deltaX|` → let native scroll happen, no preventDefault) and only falls back to horizontal pan when there's no vertical overflow. (It used to hijack *all* deltaY-dominant wheels to horizontal `scrollLeft`, so lower rows like captions were unreachable by wheel — don't reintroduce that.) The playhead supports a real drag mode (`dragRef.kind === 'playhead'`), with `window`-level `mousemove`/`mouseup` listeners so a drag that leaves the canvas bounds still resolves. **Click-to-seek fires on the ruler (`y < headerHeight`), within 5px of the playhead, AND on empty track-row space below the ruler** (`x > labelWidth`, no clip hit) — clicking directly on a clip selects it without seeking.
- **The `.center` grid (`styles.css`) is `minmax(120px, 1fr) 6px minmax(0, var(--timeline-h))`, NOT a bare `1fr 6px var(--timeline-h)`.** With `.center` set to `overflow:hidden`, bare tracks couldn't shrink below their content/px minimums on a short window, so one pane (usually the timeline) overflowed the clip box and vanished entirely. `minmax(0, …)` lets the timeline shrink below its stored `--timeline-h`, the preview keeps a 120px floor, and `.preview-pane`/`.timeline-pane` carry `min-height:0` so they actually respect it. Verified across 400–900px window heights × 280/640px stored timeline heights.
- `types.ts` **hand-mirrors** the backend Pydantic schema (no codegen) **and is incomplete on purpose** — its `Clip` interface omits `speed`/`effects`/`transform`/`audio` ("M1 frontend ignores transform/effects/etc." per its own comment), so any code reading those fields does so via `as unknown as {...}` casts (see `Properties.tsx`). `AnyClip = Clip | TextClip` is discriminated at runtime by `isMediaClip`. Export is async job-polling (poll `getJob` every 500ms → hidden `<a download>`).
- **`StickerLayer.tsx` is the interaction layer for EVERY canvas overlay, not just stickers** (the name is historical). Text and stickers must select/drag/resize identically — text had no on-canvas handles at all until round 5 (M-01). The split is by *ownership*: `TextLayer.tsx` is the only place that measures and wraps a text string, so it publishes each active clip's measured box into `lib/overlay`'s `publishTextBoxes()` registry each frame, and `StickerLayer` hit-tests those boxes with the identical code path as a sticker's. Live drag flows the other way through `setOverlayDrag()` — module-level mutables, **not** React state, because both are rAF loops and routing a 60 Hz drag offset through `setState` would re-run TextLayer's whole draw effect every frame. **A published text box is already LIVE and must not be adjusted again by the consumer**: TextLayer reads that same override to draw its glyphs, so the move offset and resize multiplier are folded in before publishing. `StickerLayer` re-applied both, so the chrome travelled at *double* the pointer distance — visibly detaching upward from the text it framed ("when I drag the text, the text box gets outside of the text") — and inflated by mul² on a resize. The commit reads `d.live.*` rather than the box, which is why the text still landed correctly and only the box lied. TextLayer is the right owner because a live resize RE-WRAPS the string: line breaks can change, so the true box isn't a uniform scale of the old one and can't be reconstructed downstream. Cost is ≤1 frame of chrome lag; being 2× wrong was not a cost worth paying to avoid it. Handle sizes and the chrome drawing live once in `lib/dragVisuals.drawSelectionChrome`. Two things a text box deliberately does NOT get: **captions** (position is owned server-side by the captions block, so a drag would commit an x/y the renderer ignores — a control that does nothing is worse than none) and **keyframed x** (one drag can't express a curve). A text resize commits `set_property style.size`; a sticker resize commits `set_clip_transform scale`. `StickerLayer` also **paints the sticker pixels themselves every frame** (not just chrome) — see the preview-baking bullet under Render pipeline for why that ownership is load-bearing rather than cosmetic.
- **A dropped overlay must keep being drawn at the committed position until the EDL comes back carrying it — and that hold is needed SEPARATELY in each layer.** A commit is not instant: `dispatch` → ~120 ms `refreshSoon()` debounce → `GET /edl`. Clearing the live override on pointer-up redraws from the STORED coordinates for that whole window, so a drop visibly bounced back to the pick-up point and then jumped forward ("the emoji goes back to the place from where it was picked up and then comes to the place where I placed"). It is not a render cost and will not "just get faster". `lib/overlay.resolveLiveOverride()` is the one rule — live gesture, then the committed-but-unconfirmed drop, then stored — and `dropSettled()` decides when the wait is over, with tolerances because the commit ROUNDS (an exact compare never settles and would pin every drag to the timeout) and a deliberate `false` on a keyframed value so the **bounded** 2 s safety net resolves it instead. That timeout is load-bearing: a permanently wrong position is far worse than the flicker being fixed. Preview.tsx's `liveTransform` (cleared on the `<video>`'s `onLoadedData`) is the same lifecycle for a v1 clip. **The trap: `setOverlayDrag()` is TextLayer's channel, NOT a general live-position mechanism.** Fixing only that leaves stickers broken, because `StickerLayer` resolves sticker geometry itself and read its own `dragRef` in *two* places (the hit-test box and the paint loop) — so the first version of this fix verified fine on text and changed nothing for the sticker actually reported. Each layer owns its own draw math, so each must consult `resolveLiveOverride` itself. Measured on the packaged build with a per-frame centroid sampler over the overlay canvas: dragged to x=287, **back to x=190 for 18 frames (274 ms)**, then forward to x=285 — matching the 233 ms measured off the user's screen recording. Two follow-ons: the held sticker stays hoisted in `paintOrder` (its z is raised by the very commit being waited on, so dropping to stored order mid-hold would make it dive under a neighbour and pop back), and a move must not leak `scale` nor a resize leak `x`/`y`, or a field the gesture never touched gets pinned and `stickerGeom`'s `?? sampleKF()` fallthrough is defeated.
- **`unsentinel()` exists because TextLayer's anchor resolution is sentinel-based.** `resolveAnchor` treats a handful of exact canvas-px values (540, 1700, `canvas.w/2`, `canvas.h*0.85`, the role's own server anchor y) as "no explicit anchor — use the role layout", since nothing in the schema tracks per-field set-ness. The role anchor is a very reachable drag target (you dragged *from* there), and committing it would make the drag visibly snap back. TextLayer publishes its own sentinel lists on the box so the two can't diverge.
- **Lane/clip-type validation lives in `agent/dispatch.py`, not just the frontend.** `_v_track_for_media()` rejects `add_clip`/`move_clip` targeting a non-video/audio-family track (a media `Clip` parked on e.g. the captions track used to succeed silently at the data-model level, then vanish from every render since `collect_text_clips`/`collect_stickers`/etc. each only look at their own track type) — `move_clip` only applies this when the clip being moved `isinstance(c, Clip)`, since a `Sticker`/`TextClip` legitimately moves between two tracks of its own kind (e.g. `tx_super` → `tx_hook`). The Timeline drag/drop handlers duplicate this check client-side for immediate feedback (`toast.error`), but the backend check is the real enforcement — Claude/MCP callers bypass the frontend entirely.
- **`move_clip` also snaps to the nearest free gap to prevent silent time-overlap** (`_first_free_gap()` in dispatch.py, mirrored client-side in `Timeline.tsx`'s drop handler). Dropping a clip onto a track where it would overlap an existing clip's time range used to be allowed with no check — the two clips then drew with identical fill and no z-order cue, reading as "merged/broken" (no data was lost; both clips survived). Now the dropped clip snaps its `start` to the first free gap on the destination track; a dashed-outline draw in the canvas loop is defense-in-depth for any still-overlapping (legacy) clips. **`move_clip` takes an opt-in `close_gap`** which, after the move, repacks the sequence so the vacated slot closes (`_repack_media`). The Timeline drag passes it (a drag means "reorder": dragging clip 1 to the end otherwise left a hole at 0s and simply made the timeline longer); Claude/MCP callers don't, because they place clips at absolute times and must not have neighbours shuffle underneath them.
- **`close_gap` is V1-ONLY, and it closes the lane the clip LEFT — three distinctions that each had a bug on the wrong side of them.** The gate was `track.type == "video"` and ran after `track` had already been reassigned to the destination, so:
  - **It repacked the wrong lane.** A v1→v2 drag closed gaps on **v2** — shuffling clips the user never touched and pulling the dropped one straight back out of the slot it was dropped in — while the real hole sat open on v1, holding `edl.duration` at the old length. Origin and destination coincide for a same-lane move, which is why it read as correct. Now: cross-lane closes the **origin** and leaves the destination exactly where it was dropped (a drop onto another lane is a *placement*; `_first_free_gap` already keeps it off other clips), same-lane reorders.
  - **It repacked v2.** `type == "video"` matches v2, whose clips are *not* a sequence — `render/pip.py` floats them over the composite at absolute times, so packing them from t=0 is the same damage `test_set_speed_rejected_on_v2_pip` already pins down (deliberate 8.0/20.0 placements collapsing to 0.0/2.0). The gate is now `id == "v1"`, the one lane where clips follow one another. Every other lane holds elements positioned *against* v1's picture — a caption's start is a coordinate, not a slot, and so is a PIP's.
  - **A reorder could not move a clip LEFT.** `_first_free_gap` ran first and walked *forward* past the very clips the drag was jumping, so dragging the last clip to the front returned it bit-for-bit to where it started, the repack re-derived the original order, and the drag did nothing — while the UI announced "Snapped to the nearest free gap" for it. **Landing on an occupied slot IS the reorder gesture**, so the snap is skipped when `close_gap` is set on a same-lane v1 move; `_repack_media` assigns the real positions, breaking a start-time tie in favour of the dragged clip (`prefer_first`) so a drop onto clip 1 inserts *before* it instead of re-deriving the order. **The ordering rule is "the dropped clip's LEFT EDGE against the other clips' starts"**, and it is implemented three times — `_repack_media`, `dragResolve.reorderLanding` (the drag preview), and the drop handler's decision to skip the snap — so they must move together or the landing line goes back to promising an outcome the backend won't produce.
- **Text overlays on a track REPLACE on temporal overlap, they don't stack** (the "double subtitle" fix). `add_super_text`/`add_text` remove any existing same-role clip on the same track whose `[start,end)` overlaps the incoming one, then append (opt out with `allow_stack:true`). An earlier fix only deduped EXACT matches (same text AND same start/end), so two clips with different text ("RIPPLE TEST" vs "RIPPLE TEST 2") at the identical time both survived and `TextLayer.tsx` (which has no collision handling) rendered them stacked. The fix is forward-only — it does NOT retroactively clean EDLs already carrying stacked duplicates; resolve those with an explicit `ripple_delete`, never a silent load-time mutation.

## Framing (crop/reposition) — the crop window is the OUTPUT FRAME

`CropReposition.tsx` mounts over the preview when the selected v1 clip is `fit: 'cover'`. Its geometry lives in **`lib/cropLayout.ts`**, a pure function, because every bug in it was a sign or derivation error that a unit test catches instantly and a screenshot does not.

- **The window never moves and never resizes; the PICTURE moves and scales.** Both faults came from the opposite arrangement. Pinning the picture meant showing the same crop required sliding the window the *other* way, so dragging right sent the yellow rectangle left ("the framing panel moves opposite to the mouse"). And deriving the layout zoom from the *current* scale (`fitScale = min(paneW/scaledW, …)`, which divides by scale) shrank the window as you zoomed instead of enlarging the footage — read as "there is video behind the framing which gets bigger". `winScale` is therefore derived from the **scale-1** cover size and is independent of `scale`.
- **`+x` moves the picture RIGHT, matching `compositor.py` exactly** — its cover pan is `crop=…:'(in_w-out_w)/2 - x':'(in_h-out_h)/2 - y'`, and moving a crop window left by x *is* moving the picture right by x. Keeping the same sign on both sides is what makes the live drag and the bake agree; an inversion here has to be hand-maintained against a filtergraph and will drift.
- **`SCALE_MIN` is 1, not 0.1, and that is a render contract.** The cover-with-pan branch applies `extra_zoom = max(1.0, scale)` because a sub-1 zoom shrinks the frame below the canvas and `crop` then renders **solid black with no ffmpeg error**. Offering 0.1 in the UI let the view show a picture the renderer would never produce.
- **`.preview-pane video`'s `max-width/max-height: 100%` must not apply to it** (`video.crop-source` opts out). That rule is right for the composited preview and wrong here, where being bigger than the pane *is the point*: it clamps per axis, so a 2× zoom rendered a 715px-wide element at 349px with height left at 402px — the picture squashed sideways instead of growing.
- **x/y are CLAMPED to the margin ffmpeg will honour** (`clamped`/`limit` from `cropLayout`, and the drag commits `clamped`, not the raw pointer total). `crop` pins its x/y into `[0, in_w-out_w]`, so past the margin the bake silently ignores the rest while the view kept sliding the picture and painting black. Worst case is a source whose aspect **equals** the canvas — a 9:16 phone clip on a 9:16 canvas, the most common upload — where both margins are 0 at scale 1 and *every* drag was a no-op in the render. Measured: on a 1920×1080 source over a 1080×1920 canvas, `y=400` and `y=-978` both rendered byte-identically to `y=0`. The badge says "Zoom in to reposition" rather than printing a number that does nothing.
- **The view mirrors `extra_zoom = max(1, scale)`, but only when panning** — because the renderer itself splits: the cover-with-pan branch clamps a sub-1 zoom (it would leave `crop` with less input than output and render solid black), while the no-pan path applies the scale exactly and pads. A clip stored with `scale < 1` is still reachable (the Properties slider allows 0.1, as do Claude/MCP), so drawing the raw value showed a half-size picture with black inside the yellow frame.
- **The view is withheld when x/y/scale is KEYFRAMED** (`showReposition` in `Preview.tsx`) and renders `null` when the source's dimensions can't be probed. It reads only scalar transforms, so an animated pan drew as if centred, and one drag would `set_clip_transform` the whole keyframe list away — the same "one drag cannot express a curve" rule StickerLayer applies to text. The dims-`error` branch previously neither set dims nor retried, leaving an opaque black div over a working preview with no way out but deselecting; that also split by platform, since a codec WKWebView decodes can fail in WebView2.
- **The raw-source `<video>` seeks on `onLoadedMetadata`, not only from the effect.** On first mount `readyState` is 0 (the element is created in the same commit), and since the view only opens while paused none of the deps changed afterwards — so the source sat at time 0, a different moment than the composited preview the user was looking at, and they framed against the wrong footage.

**Rotation is IN PLACE on v1** (`rotate=<rad>:c=black`, no `ow`/`oh` override). It used to expand to the rotated bounding box and scale that back down to fit, so nudging a clip 3° to straighten it visibly zoomed the whole shot out — and `Preview.tsx`'s live preview is a CSS `rotate()`, which rotates in place, so the picture jumped size the moment the value committed ("while rotating the preview is correct, but when the changes are made the preview gets changed"). `pip.py` deliberately still expands (`c=black@0`, `ow=rotw`): a PIP element floats over the composite and has no frame to be cut off by.

**Unticking "Fill frame" resets `x`/`y`/`scale`** (`set_clip_fit`, cover → contain only). Those are a crop-window pan that means nothing under `contain`, where they instead translate an already-letterboxed picture and crop the far edge — so the control was not an undo of itself ("the video gets cropped, but doesn't come to its original aspect ratio"). **Two gates gate the reset, both found by review after the first version shipped without them:**
- **v1 ONLY.** `fit` is read exclusively by `_build_clip_video_chain` (the v1 base layer); `render/pip.py` never looks at it. On a v2/PIP clip `x`/`y`/`scale` are the on-canvas **placement**, so the reset turned a toggle that renders *nothing* differently into a silent teardown of the PIP layout — a bottom-right PIP jumped three-quarters off the top-left corner.
- **Nothing keyframed on ANY of the three**, not each guarded independently: they are coupled. Zeroing a scalar `scale` while a keyframed `x` survives leaves the pan no headroom (the animated branch emits `scale=<canvas>*max(1,1.0)`, so `iw` equals the canvas and ffmpeg clamps the pan expression to 0) and the authored animation renders motionless. Preserving a keyframed value while destroying what makes it visible is not preserving it.

Known trade-off: the reset is to **identity**, not to whatever the transform was before cover was entered — so ticking and unticking to compare also discards a zoom the user had set while in `contain`. Restoring the pre-cover values would need that state stored on the clip.

## Why the chat agent "gets confused" — the mechanical causes

Reports of the assistant losing the thread were mostly two structural faults in `agent/loop.py`, not model behaviour:

- **A tool result must stay VALID JSON when it is bounded.** It used to be `json.dumps(result)[:8000]`, which slices mid-structure — an unclosed string, half a key. `get_timeline` on a 40-clip timeline was ~11.4k chars, so what reached the model simply stopped mid-document; asked to reason over that it reports confusion or invents the missing half. `_tool_result_json()` now wraps an oversized payload in a labelled envelope (`_truncated`, `original_chars`, `preview`) that parses. Re-encoding escapes quotes and backslashes, so the envelope is longer than the preview it holds — it shrinks in a loop until it genuinely fits rather than assuming a fixed allowance.
- **`get_timeline(summary=True)` is capped at `MAX_SUMMARY_CLIPS` per track**, keeping the common case inside that budget instead of relying on the truncation. It keeps the head and the last 5 clips with an `_omitted` marker between them, because positional reasoning needs the boundaries, not the middle of a long strip. `clip_count` always reports the true number.
- **Running out of `max_turns` must not end in silence.** The loop used to fall out of `for turn in range(max_turns)` with no closing text — the user saw a run of tool calls and then nothing, which reads as the assistant giving up — and left `history` ending on a `user` tool_result, so the next message appended a second consecutive user turn and the API rejected the conversation ("roles must alternate"). That is the same wedge the credit-failure path guards against, reached from the other direction. The `for/else` now emits an explanatory message AND closes the history on an assistant turn.

The live-context block (`_live_context_block`) was already bounded at 12 clips per track — that one was fine.

## Transitions — `render/transitions.py`

Three kinds of entry, and picking the wrong one is how a name ends up promising a motion the engine cannot perform:
- **NATIVE** — one of ffmpeg's 58 xfade transitions. All 58 are exposed; there are no more to find.
- **CUSTOM_EXPRS** — `xfade=custom` with a per-pixel expr. It can express any **mask** (shape, band, hash, luma key) but **cannot sample another coordinate**, so no zoom, rotation or smear. Both `if(cond,B,A)` and `A*(1-k)+B*k` are plane-safe; anything that mixes A and B unevenly per plane shifts colour.
- **POST_FILTERS** — a real filter on the xfade **output**, gated with `enable='between(t,…)'` to the transition window. The only way to get motion blur, which is what makes a whip pan read as one. Sigma scales with the **axis being smeared** (`WHIP_SIGMA_RATIO`), never a fixed pixel count — preview and export render at different resolutions, so a constant would smear the preview harder than the delivered file.

**A transition SHORTENS the timeline, and `EDL.duration` has to say so.** `xfade` plays both clips at once for its duration, so each applied transition removes exactly that much from the output — `compositor.py` has always tracked it (`cur_dur = cur_dur + seg_dur[i] - tdur`) and the EDL never did. An 8s timeline split at 2/4/6 with three 0.5s transitions **renders 6.5s** while the header badge, the timeline and the transport denominator all still said 8.0, so playback stopped early with a dead tail and no explanation ("the 8 sec video got stopped at 7 sec"). `EDL.transition_overlap()` now models it and `recompute_duration()` subtracts it; verified against the real renderer, preview and export both land on 6.500s exactly. It **mirrors the renderer's applicability rule**, because charging for a transition that never renders is the same bug pointing the other way: only a boundary between two **adjacent** clips (a gap becomes black filler and the renderer leaves that seam a hard cut), the same 0.05s boundary tolerance, one charge per seam (`seg_trans` is keyed by segment index, so a legacy stack at one cut still renders once), never more than the shorter clip can give, and **v1 only** (`render/pip.py` never looks at transitions). `EDL.video_duration()` deliberately does NOT subtract — it answers "where does v1's content end", which is where the next upload gets appended; subtracting there would append the next clip *on top of* the last one. No transitions → overlap 0 → every existing timeline's duration is unchanged. `add_transition` reports the change in its summary (`timeline 8.00s → 7.50s`), because a tool that silently shortens the video is the most surprising one in the app.

**ALIASES are synonyms, not effects.** `catalog()` publishes `looks` and `count` separately: a single combined number read as "88 transitions" when a third were synonyms (`mosaic` = `pixelate` = `pixel` = `pixelize`), so a tester working through the list found repeats and reported the catalogue as padded. Two rules a test now enforces: no alias may share a name with a real look (the resolver checks customs first, so it would silently shadow it — this happened to `blinds`), and every look must appear in some `CATEGORIES` entry, since `list_transitions` is the only discovery surface. **`list_transitions` repeats `looks`/`alias_count`/`note` at the TOP level, not only inside `catalog`** — `count` (105 accepted names, 72 looks) sits at the top of the result and is the number a reader actually quotes, so the honest split has to live where the padded one does.

`spin` used to resolve to `radial`, a clock wipe with no rotational motion, and `whip` to `smoothleft`, a soft slide with no blur — both named a movement that never happened. `zoomout` still maps to `circleclose` because a true zoom needs coordinate sampling; its description says so rather than pretending.

**`add_transition` REPLACES any transition within 0.05s of the same cut** instead of appending. The compositor keys transitions by seam, so a second one at the same boundary never rendered — it just accumulated in the EDL, which then disagreed with the picture. Same rule the text overlays follow. `remove_transition` still sweeps *all* entries near a cut, because legacy projects and MCP callers can still hold stacks. **`TransitionPopover` exposes Remove**, but only when the cut already has one — removal was otherwise reachable only through chat/MCP, so a transition added by a mis-click had no way back but Undo. It sits at the far left of the action row (`margin-right:auto`), deliberately not adjacent to Update, since it is the one destructive control there.

## Feature availability — `ai/features.py`, `check_features`

Every optional capability has its own `available()` probe, but until round 8 nothing aggregated them and **nothing exposed them to the chat agent**. With no way to look, Claude invented diagnoses: it told a user to run `uv add noisereduce soundfile` for a noisereduce that was installed and working, and reported vocal isolation as "not installed" when demucs, torch and the model were all present. `check_features` returns, per feature, whether it works here and the exact fix if not; `SYSTEM_PROMPT` requires calling it before claiming anything is missing and forbids composing install commands by hand. Probes must be cheap (import-spec + file existence, never a model load) and must never raise — a probe that throws on a machine missing a dependency takes the diagnosis down with it.

**A tool raising is not evidence its dependency is absent.** `vocal_isolate` failing on Windows was `python -m demucs.separate` loading audio through torchaudio → torchcodec, whose `libtorchcodec_core*.dll` links against ffmpeg's **shared** libraries — Windows installs a static `ffmpeg.exe`, so the DLL never loads and demucs exits 1. `ai/separate.py` now runs demucs through its **Python API** on audio decoded with soundfile, which it already had; that path never touches torchcodec, drops an interpreter start-up, and keeps the model resident.

**In the PACKAGED app the honest answer is usually "run from source", NOT an install command.** Measured on the real Windows build: **8 of 13** optional features report unavailable, because the `.spec` `excludes` demucs/pyannote/librosa/rembg/noisereduce/transformers/mediapipe to keep the download ~1GB rather than several. So "most of the tools are not installed" in a tester report can be **literally true** of a packaged install and not an agent hallucination — check which build they were on before treating it as a model failure. A pip fix is *actively wrong* there: nothing can be installed into a frozen bundle, so the user runs it, nothing changes, and the tool loses the trust this module exists to protect. `Feature.in_packaged_app=False` marks the features whose dependency is in `excludes`, and `feature_report()` swaps their fix for `PACKAGED_FIX` when `sys.frozen`. The flag is **not** a blanket `frozen` check: features backed by an external **binary** (realesrgan, rife, an ffmpeg with libvidstab) are drop-in installable in *both* builds, so substituting there would replace correct advice with a dead end. A test parses `excludes` straight out of the `.spec`, since the flag is a claim about that list and would otherwise drift.

**The two builds do NOT exclude the same libraries, so the flag is a claim about BOTH.** `build_app.sh` (macOS) additionally drops **torch, torchvision, torchaudio, faster_whisper, open_clip, timm, scipy** — the `.spec` (Windows) keeps them. Deriving the flag from the `.spec` alone is how `visual_search` came to tell every packaged-**Mac** user to run `uv sync` inside a frozen `.app`: bundled on Windows (so it probes available there and no fix is ever shown), excluded on macOS (so it probes unavailable and hands out advice that cannot work) — the exact defect this field exists to prevent, reintroduced on the platform nobody was testing. Marking a feature `in_packaged_app=False` is free on the build where it IS bundled, because `fix` is only ever emitted for a feature that probed unavailable. `captions` is the third case, a **hybrid**: faster-whisper is excluded on macOS but whisper.cpp is a drop-in binary, so it carries a `packaged_fix` naming the route that actually works there instead of the blanket "run from source". The drift test now parses `--exclude-module` out of `build_app.sh` as well as `excludes` out of the `.spec`.

## Local-AI conventions

All heavy models are lazy-loaded singletons built on first use; every AI feature **degrades rather than crashes** when a dep/model/token is missing.
- **Transcription** (`ingest/transcribe.py`): two backends chosen at call time — `faster-whisper` (pip, CPU int8) and whisper.cpp's `whisper-cli` (Metal, ~4-5×). `backend='auto'` prefers whisper.cpp only when both the binary and the ggml model exist. The whisper.cpp path carries hard-won Hindi fixes: `-l auto` (its default `-l en` decodes Hindi as garbage), `-et 2.8` + `-mc 0` (kill repetition-loop hallucination), and segment mode not `-ml 1` (which splits Devanagari into invalid UTF-8). **ggml models are NOT auto-downloaded** — the code hunts a fixed dir list and errors with a `download-ggml-model.sh` hint. `auto_caption` re-transcribes with `large-v3` (the only model that does Hindi cleanly; `turbo` explicitly rejected).
- **Diarization** (`ai/diarize.py`): pyannote-first (needs HF token + EULA), falling back to a token-free librosa MFCC+KMeans heuristic. Forced to CPU on Mac (MPS is flaky for pyannote). Cached under `<session>/cache/diarize/`.
- **Keyframes: one button, one op, one key** (`Properties.tsx` + `add_keyframe`/`remove_keyframe`'s `props` list). The panel used to show five diamonds, one per animatable property — correct for a pro NLE, but read as "I don't understand why there are 5 buttons to add the keyframes", and pressing one changed nothing visible anywhere. Three rules now, all load-bearing:
  - **One click keys the whole transform in ONE commit.** The button sends `props: [scale, rotation, opacity, x, y]`; five separate dispatches would be five undo steps and an Undo could leave a clip keyed on some properties and not others. A property omitted from `values` is pinned to whatever it already reads at that time, so keying an untouched property never moves the clip.
  - **The `props` form does NOT seed the implicit t=0 anchor; the single-`prop` form still does.** Keying a not-yet-animated property converts the scalar to a key at 0 first, so `add_keyframe scale @2s = 1.5` RAMPS from the current value — the contract every Claude/MCP/template caller was written against, so it must not change. But it also meant one click produced *two* keyframes, which is why a tester counted more keyframes than clicks. `seed_anchor=len(props) == 1` keeps both true.
  - **Removing the last key restores the value it HELD, never 0.0.** A lone keyframe is a constant, so dropping it must leave the clip looking identical. Zeroing gave scale 0.0 (clamped by `Transform` to 0.01) and opacity 0.0 — the clip vanished. Tolerable while five buttons each removed one property; with one button it is two clicks from a blank clip. A removal that matches no key commits **nothing** (a no-op op still clears the redo stack).
  - Visibility is the other half: `lib/overlay.keyframeTimes()` feeds both the amber diamonds `Timeline.tsx` paints on the clip and the panel's clickable "N keys · 0.00s, 3.00s" readout. Times collapse within half a frame and are sorted BEFORE dedup, so the panel and the canvas can't report different counts.
- **CLIP visual search** (`ai/clip_search.py`, `search_media`): fully local open_clip ViT-B-32 (~150MB, torch cache), keyframes via ffmpeg, cosine ranking, per-clip embeddings cached as `.npz`. Missing torch returns `{status:'unavailable'}` rather than raising. `scope='spoken'` is a substring match over transcript segments; `broll.py` is filename/tag-based (no model) with a separate global cache at `~/.cache/video-ai-editor/`.

## `show/` — house-style presentation layer (no ML)

Distinct from `ai/` (models) and `ingest/` (media prep). `audit.py` is a **pre-export quality gate** (3-axis hook-stack scorer that blocks export when no hook is present in the first 3s, plus captions/brand/shot-length checks → 0-100 score). `brand_kit.py` attaches a persistent watermark + end-card. `templates.py` holds built-in EDL templates and user-saved `ShowSnapshot`s (canvas + brand + captions + music_seed) so a recurring segment's look re-applies to new footage in one call.

## Testing conventions

- `pyproject.toml` sets `pythonpath = ["src"]` (import `video_ai_editor.*` without install) and `asyncio_mode = "auto"`. There is **no `conftest.py`** — fixtures are per-file, typically building an `EDLStore` in `tmp_path` with ffmpeg-lavfi-synthesized media.
- `test_all_tools_smoke.py` parametrizes over `sorted(DISPATCH.keys())` — a new tool is auto-covered by a smoke test.
- CI (`.github/workflows/ci.yml`) runs four jobs in parallel: backend pytest on **ubuntu** (Python 3.11, ffmpeg via apt), on **windows-latest** (Python 3.13, ffmpeg-full via Chocolatey — the real cross-platform gate), on **macos-latest** (Python 3.13, `brew install ffmpeg`), and frontend `tsc + vite build`. **The macOS job was missing for a long time**, which meant the app's *primary* shipping platform — the `.app` bundle, WKWebView, the VideoToolbox ladder — had no automated gate at all and every macOS claim rested on reading the code. ubuntu covers POSIX path/encoding semantics but not Darwin-specific ones (`~/Library/Application Support`, `exe_name` as a no-op, avfoundation, VideoToolbox probing), which is exactly where `platformutil` branches. Note the macOS runner installs plain `ffmpeg`, not `ffmpeg-full`, so it has no libvidstab and `stabilize` skips — that exercises the documented degrade-don't-crash path rather than a 10-minute source build. Its ffmpeg step asserts that **`ffmpeg` runs**, not that `brew install` exited 0: the runner image may already carry one, and `brew install` on an already-installed formula can exit non-zero on a link conflict — failing the job over a working toolchain. (Deliberately no `set -o pipefail` there: `ffmpeg -version | head -1` SIGPIPEs ffmpeg, which pipefail reads as a failure.)
- **The macOS job also BOOTS the app** (`uv run python -m uvicorn …` → poll `/api/health`, then `/readyz`), because pytest proves the logic imports and behaves but never proves the process runs: every module importing *together* under a real ASGI server, uvicorn binding, and the app's own readiness probe finding ffmpeg (`/readyz` is 503 when it does not) are all outside its reach. It is the closest a headless runner gets to "did it launch" — the native window (WKWebView) and the `.app` bundle still need a human on a Mac. It sets **`PYTHONPATH=src`**, mirroring `run.sh`, so the step tests the app rather than the runner's Spotlight state: the hidden-`.pth` gotcha above is a macOS-wide daemon behaviour and a CI runner is not exempt. All **force `ANTHROPIC_API_KEY`/`HUGGINGFACE_TOKEN` empty** so tests never hit real endpoints and heavy-AI tests skip cleanly. The Windows runner has no local AI binaries/models, so a few more tests skip there (e.g. torchcodec-dependent) — that's expected. **Windows-only regressions surface here, not locally on a Mac** — the CI job is the source of truth for Windows behavior.
- CI runs `npx tsc -b --force` then a separate `npx vite build`. It used to run `npx tsc --noEmit`, which type-checks **zero** files against this repo's solution-style `tsconfig.json` (see the Frontend-checks note above) — so the type gate was inert and `tsc -b`-only failures were invisible. Keep the two as separate steps so a typecheck failure is distinguishable from a bundling failure in the log.
- **Running the PACKAGED app is a THIRD gate, above pytest and above live HTTP against `uvicorn`.** Some defects exist only in the frozen artifact and are invisible in every dev path. `dist\Video AI Editor\Video AI Editor.exe` after `build_win.ps1`, then hit `127.0.0.1:8765`. **Confirm which process owns the port** (`Get-NetTCPConnection -LocalPort 8765`) before trusting a 200 — a stale backend answering while your "restart" silently failed to bind has already invalidated one round of testing here. What this gate caught that the other two could not: the `BUILD_ID` **BOM** (no dev path writes that file); `check_features` advising `uv sync` for libraries the `.spec` *excludes*, which cannot be installed into a bundle; and — from the browser network log on the app's own origin — a **422 on the thumbnail for a clip's tail**, because a seek at/past the last frame decodes nothing (`thumbs.py` now retries with `-sseof`). Load the origin in Playwright and assert on `response.status >= 400`, not just on console errors: the broken thumbnail printed one generic "Failed to load resource" line that says nothing about which request failed.
- **Verifying a fix over live HTTP is a different gate from pytest, and it finds different things.** Round 5 ran a 46-check sweep against a real uvicorn + real uploaded media after the unit tests were green. Unit tests prove a handler *raises*; only HTTP proves the client sees **400 vs 422 vs 500**, which is what a tester actually reports. It surfaced two bugs pytest could not (`apply_lut` accepting a nonexistent path; the render error blaming the wrong file). Three harness rules, each learned by getting it wrong first:
  - **Pace the calls.** `hardening.py` rate-limits **60 rps per (ip, path)** and every tool shares one dispatch path, so a tight loop 429s and silently masks every later result as a failure. Pace to ~45 rps; do **not** disable the limiter to make a test pass — it is correct shipped behaviour.
  - **Never hardcode the canvas.** `upload` infers it from the media, so a landscape source legitimately yields 1920×1080. Asserting 1080×1920 tests the fixture, not the fix.
  - **Measure differentially for pixel claims.** Counting "bright pixels" in a `testsrc` frame measures the background. Export the same timestamp with and without the overlay (move its time window) and diff — that isolated the dragged text's centroid to y 0.659 vs the EDL's predicted 0.644.
- **In a browser check, probe the app's own feedback instead of assuming coordinates.** The text overlay's box was located by sweeping for `canvas.style.cursor === 'nwse-resize'`, which both finds the handles and proves the hit test is live. It also caught a *harness* artifact: a multi-step synthetic `pointermove` drag applied only its first step (size ratio 1.06 when the geometry said 1.6); one decisive move gave an exact 1.500. Don't "fix" the product for a synthetic-input artifact — re-measure first.
- **Env-var-reload tests must restore state in a `finally`, in the right order, or they poison the rest of the pytest process.** A monkeypatched `importlib.reload(cfg)` to pick up a changed env var needs its "undo" reload to happen **after** `monkeypatch.delenv`/`setenv` teardown, not before — otherwise the module keeps the test's env-driven state (e.g. `VAI_RESTRICT_PATHS=True`) for every test that runs later in the same process, since pytest doesn't re-import modules between tests. This class of bug hides until an alphabetically-later test file happens to depend on the polluted global state; it won't reproduce running the buggy test file alone.

## Release identity — why "which build?" must always be answerable

`VERSION` alone is **not** a build identity. It read `0.3.7` for 99 commits across
three fix rounds, and `git tag` was empty, so three consecutive tester reports said
"v0.3.7" and could not be dated. The measurable cost: **13 of 45 issues in the
2026-07-28 QA round were re-reports of code that had already been fixed** (mute
checkbox, text coordinates, video fade, font size, music-clip showing video
controls, PNG stickers, sticker ✕, cropped context menu, full-path labels…), and a
fourth investigation round was spent re-proving correct code.

Three mechanisms now keep what ships equal to what runs — do not weaken any of them:
- **`/api/version` returns `{version, build}`**, where `build` is `config.build_id()`:
  the baked `BUILD_ID` file in a frozen app, else `git rev-parse --short HEAD`
  (+`-dirty`). It is lazy and cached, deliberately NOT computed at `config` import
  (that module is the import-time chokepoint for every entry point). `BUILD_ID` is
  written by `build_app.sh`/`build_win.ps1` before packaging and is **gitignored** —
  if it were tracked, the next build would see it as untracked and stamp `-dirty`.
  It is read **BOM-tolerantly** (`_pu.read_text_config`) and written BOM-less:
  PowerShell 5.1's `Set-Content -Encoding utf8` prepends `EF BB BF`, `.strip()`
  does not remove it, and the packaged app reported `﻿c93af1e-dirty` — a sha
  matching no git object, in the one mechanism whose entire job is making
  "which build?" answerable. It reproduced **only** in a real Windows build (no
  dev path writes that file), which is why running the exe is its own gate.
  The TopBar badge shows `v<VERSION> · <sha>` (e.g. `v0.4.1 · 8cfe0fb`), and a
  `-dirty` suffix when the working tree has uncommitted changes — which is a
  useful signal, not a bug, when you are verifying a local build.
- **`desktop.py::_ensure_frontend_built()` compares mtimes**, not mere existence. The
  old `if dist/index.html exists: return` let a bundle from a previous checkout
  satisfy the guard forever. Failure policy differs on purpose: a *missing* bundle is
  fatal, a *stale* one only warns — bricking a working launch because npm is absent
  would be worse than serving old bits. `build_win.ps1` now also `rm -rf`s `dist`
  unconditionally (mirroring `build_app.sh`) and asserts `$LASTEXITCODE`, because
  `$ErrorActionPreference='Stop'` does **not** trip on a native exe's non-zero exit.
- **`index.html` is served `no-store`** (`main._NoCacheHtmlStatic`) while `assets/*`
  stay `immutable`. Vite emits content-hashed assets behind a stable HTML url, so a
  cached `index.html` pins a deleted asset hash. This was observed live during the
  fix round: after a rebuild the page kept loading a bundle that no longer existed on
  disk, and a verified frontend fix appeared not to work at all.

## Packaging

The macOS `.app` is built via PyInstaller (`build_app.sh`, entry `desktop.py`, `--windowed`), **excluding heavy ML libs** (torch/pyannote/faster-whisper/librosa/demucs) to stay ~150MB — those users run `uv run video-ai-editor` instead. `ffmpeg`/`piper`/`realesrgan` must be on PATH at runtime. Version is single-sourced from the repo-root `VERSION` file (baked into Info.plist and served at `/api/version`).

**`build_app.sh` does NOT use `Video AI Editor.spec`** — it invokes `pyinstaller` with CLI flags, and PyInstaller's CLI mode *regenerates/overwrites* the `.spec` as a side effect. So editing the `.spec` has no effect on the macOS build, and running `build_app.sh` silently clobbers any hand-maintained `.spec` content. The `.spec` IS used by the Windows build (`build_win.ps1` → `pyinstaller "Video AI Editor.spec"`), where it is darwin-guarded around `BUNDLE` and adds the `clr` (pythonnet/WebView2) hidden import. If you need to change the macOS bundle config, edit `build_app.sh`'s flags, not the `.spec`.

**Voiceover recording in the packaged app is a THREE-layer problem — the Info.plist key alone is necessary but NOT sufficient** (this failed repeatedly until all three landed):
1. **`getUserMedia` is fundamentally unusable in the packaged WKWebView.** pywebview's Cocoa backend implements no `webView:requestMediaCapturePermissionForOrigin:…` WKUIDelegate method, so WKWebView denies capture regardless of Info.plist; and the app is served over `http://127.0.0.1:<VAE_PORT>`, a non-secure-context origin where `navigator.mediaDevices` is typically `undefined` anyway. So VO in the packaged app does NOT use `getUserMedia` — `VoRecorder.tsx` detects the pywebview `js_api` bridge FIRST and routes Record/Stop through **`desktop.py`'s `_Api.vo_start`/`vo_stop`**, which capture natively via `ffmpeg -f avfoundation` and POST the WAV to the same `/vo_record` endpoint the browser path uses. (Browser-dev mode at `:5173` still uses `getUserMedia` + MediaRecorder — that path is unchanged and works.)
2. **macOS TCC grants mic access per *responsible process*, and a subprocess (ffmpeg) under an ad-hoc-signed bundle gets denied silently.** So `vo_start` first calls `_ensure_mic_authorized_mac()` — requests authorization via **`AVFoundation.AVCaptureDevice.requestAccessForMediaType_` from the APP process** (pyobjc; `pyobjc-framework-avfoundation` is an explicit `darwin`-only dep) so TCC attributes the prompt to "Video AI Editor" and the child ffmpeg inherits the grant. The import is wrapped in try/except so a missing dep degrades to the subprocess-only path rather than crashing — **but then the fix silently no-ops**, so the dep must actually be installed/committed.
3. **`build_app.sh` re-signs the bundle with hardened runtime + `entitlements.plist`** (`com.apple.security.device.audio-input` + the three PyInstaller cs.allow-* keys) so TCC attribution is deterministic. PyInstaller's own BUNDLE-stage ad-hoc `codesign` has no entitlements/runtime and emits a "resource fork … not allowed" warning — `build_app.sh` supersedes it by signing in a **`/tmp` staging copy** (a Desktop-rooted checkout gets `com.apple.FinderInfo` re-stamped by Finder/LaunchServices within ~1s, which `codesign --strict` rejects — route around the daemon, same posture as the `.pth` guidance) then `mv`-ing the verified bundle back into `dist/`. The final `--verify --deep` (non-strict) is the functional check TCC/Gatekeeper rely on; `--strict` failing on a Desktop-rooted artifact is a submission-hygiene lint, not a functional failure.

Also: **`NSMicrophoneUsageDescription` is still required** (added as a post-build `PlistBuddy` step since CLI-flag builds regenerate the `.spec`; the `.spec`'s `info_plist` dict carries it too for the Windows-adjacent path). And **VoRecorder.tsx has a guaranteed-working fallback**: an "Import audio file as voiceover" file-picker posting to the same `/vo_record` endpoint, so VO works even if TCC still refuses native capture. On **Windows** the native bridge returns `{ok:false, unsupported:true}` (avfoundation is mac-only) and VoRecorder.tsx falls through to `getUserMedia`, which WebView2 supports — detection is by the `unsupported` flag, NOT method presence, or Windows dead-ends on an error.
