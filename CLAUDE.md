# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**There is exactly ONE CLAUDE.md in this repo — this file, at the repo root. Never create a second one.** Two copies diverge silently and the agent then follows whichever it happened to read. Two things make a duplicate appear even when nobody wrote one:
- **macOS/APFS is case-insensitive**, so `claude.md` and `CLAUDE.md` are the *same* file. A reference to either resolves here; that is not a duplicate and needs no action.
- **A nested git worktree is a real duplicate.** `.claude/worktrees/<branch>/CLAUDE.md` is a second checkout living *inside* the primary working tree, so every repo-wide `find`/`grep` sees two. `.claude/worktrees/` is in `.git/info/exclude`, so git stays quiet about it. Check with `git worktree list`; if the branch is fully pushed (`git branch -r --contains <sha>`), `git worktree remove` it — the commits survive on the remote and can be checked out again *outside* the repo tree, which is where a worktree belongs.

## What this is

A local, chat-driven, CapCut-class video editor. Python/FastAPI backend + React/TS frontend, packaged as a native macOS app via pywebview. Everything runs on-device; only Claude API calls leave the machine. The backend also exposes an MCP server so external agents (Claude Code / Cursor / Codex) can drive the timeline.

- **Lint (`npm run lint`) has 65 pre-existing problems (61 errors, 4 warnings) that are NOT part of the CI gate.** Measured on 2026-08-19 (64 on 2026-08-17, 32 on 2026-07-30); only 1 is `--fix`-able. The number drifts by ±1 between rounds in files nobody edited, which is precisely why the instruction below is to re-measure rather than diff against this figure. When checking whether your change added lint issues, compare against this baseline (e.g. `git stash` / a worktree at the pre-change commit) rather than treating a nonzero exit as your regression — most are pre-existing `no-empty`/`react-hooks/*` debt in files you didn't touch. **Re-measure the baseline rather than trusting this number**: the jump from 32 to 64 is almost entirely **`react-hooks/refs` in `Preview.tsx` (4 → 36)**, from the render-time ref-latch pattern the live-transform/live-filter/source-preview work leans on (`if (ref.current?.hash !== previewHash) ref.current = …`). Reading and writing a ref during render is what the rule objects to, and the objection is real in general — a discarded concurrent render leaves the mutation behind. It is tolerated **here** because every one of those latches is keyed on `previewHash` + `clipId` and is therefore **idempotent**: re-running the render with the same inputs recomputes the same value, so a double-render (StrictMode, or a discarded concurrent one) cannot produce a state the next render disagrees with. Do not "clean these up" by moving them into effects — the latch has to be settled *before* paint or the preview shows the pre-gesture pose for a frame, which is the exact class of flicker `liveTransform`/`resolveLiveOverride` exist to remove.

## Launching on macOS — the hidden-`.pth` gotcha (use `run.sh`)

`uv run video-ai-editor` (and any bare import of the package) can fail with `ModuleNotFoundError: No module named 'video_ai_editor'` **even when the venv is correctly synced.** Root cause: macOS Spotlight's metadata daemon `com.apple.metadata.mdflagwriter` marks Python `.pth` files with the hidden flag (`UF_HIDDEN`) within ~1s of creation, and Python 3.13+ `site.py` **skips hidden `.pth` files** — so the editable install's `.pth` (which puts `src/` on `sys.path`) is never processed. It recurs system-wide (even in `/tmp`), so `chflags nohidden` does not hold, and rebuilding the venv only fixes it transiently.

**Always launch with `bash run.sh`**, which runs `PYTHONPATH="$PWD/src" .venv/bin/python -m video_ai_editor.desktop` and bypasses the `.pth` mechanism entirely. (The README used to document `uv run video-ai-editor` as *the* launch command with no mention of `run.sh` — i.e. it handed every Mac user the one command this section exists to warn about. Fixed; keep the two in agreement.)

**`bash verify_mac.sh` is the post-pull check on a Mac** — toolchain, `tsc -b` + `vite build`, every backend module imported together, an actual server boot (`/api/health`, then `/readyz`, which is 503 when the app can't find ffmpeg), and the optional-feature report; `--no-tests` skips pytest. It deliberately does **not** `set -e`: every check runs so one pass lists all failures instead of one relaunch per failure. Kept to **bash 3.2** constructs because macOS still ships that as `/bin/bash` — no associative arrays, no `mapfile`, and never expand a possibly-empty array (`"${arr[@]}"` under `set -u` is an "unbound variable" error there, while `${#arr[@]}` is fine). It also runs under Git Bash on Windows, which is how it was smoke-tested before ever reaching a Mac. Diagnose the flag with `ls -lO <file>.pth` (shows `hidden`); confirm the culprit with `launchctl list | grep mdflagwriter`. Do **not** fight the Spotlight daemon directly. (`pytest` is unaffected — it uses `pythonpath = ["src"]` in `pyproject.toml`.)

## Cross-platform layer — `platformutil.py` (the ONE place OS differences live)

The app runs on both macOS and Windows from one codebase. **All OS-conditional logic routes through `src/video_ai_editor/platformutil.py`** — no raw inline `sys.platform` checks elsewhere (design rule; a test enforces the encoding side). On macOS every Windows branch is dead code (`IS_WINDOWS` is False, `exe_name()` is a no-op), so macOS behavior is preserved byte-for-byte. Helpers: `IS_WINDOWS`/`IS_MAC`, `exe_name(name)` (adds `.exe` on Windows), `find_binary(name, extra_dirs)`, `user_data_dir`/`user_cache_dir` (per-OS `%APPDATA%`/`%LOCALAPPDATA%` vs `~/Library`), `read_text_utf8`/`write_text_utf8`, `replace_with_retry`/`unlink_with_retry`, `FFMPEG`/`FFPROBE` constants, `ffmpeg_filter_path(path)`.

Four Windows footguns are non-obvious and were only caught by the `windows-latest` CI job — respect them when touching render/AI/subprocess code:

1. **ffmpeg *filtergraph* paths ≠ *argv* paths.** A path passed as an `-i` argv element needs NO escaping. But a path embedded INSIDE a `-vf`/`-filter_complex` option value (`vidstabdetect=result=…`, `sendcmd=f=…`, `lut3d=…`, `movie=filename=…`) hits ffmpeg's filtergraph parser, where `:` separates options and `\` escapes — so a raw Windows `C:\Users\x.trf` is mangled. **Always wrap such paths in `_pu.ffmpeg_filter_path()`** (converts `\`→`/` and escapes the drive colon as `\\:` — the only form that survives ffmpeg's two-pass parser; single-backslash and single-quoting both fail, verified empirically).
2. **`subprocess(..., text=True)` MUST pass `encoding="utf-8", errors="replace"`.** Windows defaults to cp1252-strict, so decoding ffmpeg stderr that echoes a Devanagari media path raises `UnicodeDecodeError` and crashes — even on a *successful* ffmpeg run (the decode happens in `communicate()` before the returncode check). `-hide_banner`/`-v error` do NOT suppress the input-filename line. Byte-mode captures (no `text=`) are exempt.
3. **Bare exe name + `cwd=` fails on Windows.** `CreateProcess` resolves argv[0] against PATH + the *parent* cwd, not the passed `cwd=`. rife/realesrgan (`ncnn-vulkan` binaries that need `cwd` for their `models/` dir) use the **absolute** binary path (`RIFE_BIN`/`ESRGAN_BIN`) on Windows; the `./exe` form only works on POSIX (child chdir's before exec).
4. **Windows-illegal filename chars** (`< > : " | ? *`) can't exist on NTFS — tests that create on-disk fixtures must use Windows-legal names (`_safe_filename` handles user uploads; `repair_media_paths` sanitizes only the leaf stem, which is already Windows-safe).
5. **A hand-editable config file on Windows can start with a UTF-8 BOM — read it with `_pu.read_text_config()`, never `read_text(encoding="utf-8")`.** Notepad and PowerShell **5.1**'s `Set-Content -Encoding utf8` both prepend `EF BB BF` (PS **7** does not, so this depends on which shell ran the script — and `powershell -File …`, the documented launch form, *is* 5.1). A BOM is **not whitespace**, so `.strip()` does not remove it and the `﻿` lands inside the first value. Two live instances, both Windows-only and both silent: `.env`'s first key parsed as `﻿ANTHROPIC_API_KEY`, so the key never loaded and the app reported it missing **while the file plainly contained it**; and `BUILD_ID` made `/api/version` report a sha matching no git object, defeating the one mechanism that exists to answer "which build?" (found by actually running the packaged exe — see Release identity). `read_text_config` is `utf-8-sig`, which decodes BOM-less UTF-8 byte-for-byte identically, so it is a strict widening. It is deliberately **separate from `read_text_utf8`**, which stays strict for media/EDL/sidecar reads where eating a leading `﻿` would be a content change rather than a fix. `build_win.ps1` also writes `BUILD_ID` through a BOM-less `UTF8Encoding $false` (a test guards the writer, since the reader fix alone would hide a regression); macOS `echo >` never had the problem.

Windows launch/build: `run.ps1` (parallel of `run.sh`, uses `PYTHONPATH=src`) and `build_win.ps1` (drives the `.spec` directly via `pyinstaller "Video AI Editor.spec"`). See "Running on Windows" above.

## The one idea that unlocks the codebase

**The EDL is the program; `dispatch()` is the only way to change it.** Every feature is a variation on one loop: something produces a tool call → `dispatch(store, tool, args)` mutates the EDL Pydantic tree in place → `store.commit()` persists it → the render pipeline re-derives video/audio from the EDL. There is no diff/patch layer and no inverse-op undo — the EDL tree *is* the timeline, on-disk snapshots *are* the history, and render output is a pure function of `edl.hash()`.

### EDL data model — `edl/schema.py`
- A Pydantic v2 model tree (`EDL_VERSION = 3`; a v2 file is migrated on load by `EDL._migrate_v2` — QA-076 text sentinels); **the model classes are the schema** (no separate JSON-Schema file). An `EDL` has a `Canvas` (default 1080×1920@30 vertical), `Track`s, optional `BrandKit`/`show_template`, `Markers`. `empty_edl()` (schema.py:220) pre-creates the standard tracks; compositing order is the track `z` index.
- **Timeline time ≠ source time.** On a `Clip`, `in_`/`out` index into the source file (trim); `start` places it on the timeline. `duration` is computed (`out - in_`). `in_` serializes as `"in"` (Pydantic alias).
- **A `TextClip`/`Sticker` stores an ABSOLUTE `end`, so anything that moves one in TIME must move `start` and `end` together.** A media `Clip` derives its span from `in_`/`out` and is immune; an overlay is not. `move_clip` assigned `start` alone, so dragging a text clip from 2–5s to 20s produced `start=20, end=5` — a negative span that validated and persisted. It compounds: `_ripple_overlays` remaps `start` and `end` *independently* (correct for a clip straddling a cut), so the next ripple collapsed the inverted pair to that function's 0.1s minimum-span floor and stranded it far out on the timeline. Since `edl.duration` is a **max over EVERY track**, a 0.1s sliver at 56s held the whole timeline open: delete a long video, add a short one, and the timeline still ran to the OLD length, playing black past the new clip — and every re-render encoded ~56s of black, which is why the stale preview also took so long to clear (`Preview.tsx` only shows its empty-state placeholder when `duration` is 0). Reconstructed from a real session's `ops.json`; the two symptoms had one cause. `set_clip_timing` already floors an inverted span, and `_ripple_close_gap`/`close_gap` only touch media clips — `move_clip` was the sole writer that could invert one. The fix is **forward-only**: an EDL already carrying stranded slivers keeps them (same stance as the stacked-text-overlay fix), because a silent load-time mutation of someone's timeline is worse than a visible leftover.
- Transform props (`x/y/scale/rotation/opacity`) are each `KFNum = float | Keyframe` — any can be keyframed. `keyframes.to_ffmpeg_expr()` emits **linear interpolation only** server-side; ease/curve modes animate in the browser preview but export as linear.
- **Every model inherits `_EDLModel`, whose only job is `validate_assignment=True`. Do not add a model to this tree without it** (a test enforces it). Constructing a Pydantic model always validated, which is why `add_mask`/`add_super_text`/`add_keyframe`/`set_aspect_ratio` were always safe — they build a new model. But **Pydantic v2 does not validate on assignment by default**, and the handlers mutate the tree by assignment: `cap.config.style = style` in `add_caption_track`, `setattr(obj, key, value)` in `set_property`. So `style='karaoke'` landed in the tree, was written to `edl.json`, and only surfaced as a ValidationError on the **next load** — by which point `MAX_UNDO` further edits had rotated every retained snapshot past the poisoning and the session opened with **zero clips** (QA round 5, VAI-01: total loss after 32 ordinary edits). Cost is ~0.5 µs vs ~0.14 µs per assignment.
- **Domain bounds live on the model, not in the handler**, for the same reason: `set_clip_transform` is not the only writer (`add_keyframe`, `motion_track`, `set_property` all reach `Transform`). `Transform` clamps opacity to [0,1], scale to [0.01,100], rotation to ±3600 and rejects non-finite; `Canvas` clamps w/h to [16,7680] **snapped even** (H.264 chroma subsampling + the round-4 letterbox parity math) and fps to [1,240]. Bounds are expressed as `field_validator`s, **not** `Field(ge=…, le=…)` — pydantic cannot attach a numeric constraint to a `float | Keyframe` union, and the validator handles both shapes. Out-of-range **clamps**, non-finite **raises**: rejecting on load would make an EDL that already holds a bad value unloadable, which is the exact failure class this all exists to prevent. Handlers that want a crisp 400 (`set_canvas`) reject *before* the clamp. The same holds for `Clip.start/in_/out` (clamped to [0, 6 h]), `Clip.speed` ([0.1, 100]; ≤ 0 stores None = 1×), `AudioProps.gain_db` and `TextStyle`/`CaptionLook` `size` ([1, 2000]) / `stroke_w` ([0, 200]) — the generic `set_property` reaches them without a typed tool's bounds, so it rejects out-of-range values itself (`dispatch._check_property_bounds`, editor-worded 400) and refuses `out <= in`. A `set_canvas` fps change re-quantises every committed time to the new grid in the same commit (`_requantise_times`).
- **`TextClip`/`Sticker` transform x/y are ABSOLUTE CANVAS PIXELS, not relative to duration/track.** Two consequences enforced in `dispatch.py`, both easy to regress: (1) `cut_range`/`ripple_delete`/`trim_clip` — which only re-time the video track they operate on — additionally call `_ripple_overlays(edl, removed_start, removed_end)` to shift every text/sticker/caption clip's `start`/`end` by the same left-shift, only when the affected track is `v1` (a v2/PIP cut must not ripple the primary overlay timeline) and only for the actual clip kind removed (deleting a sticker itself must not ripple *other* overlays). The removed-interval math genuinely differs between trimming from the front (`in_` grows: removes `[old_start, old_start+delta_in)`, the head of the old slot) vs. the back (`out` shrinks: removes `[old_start+new_duration, old_start+old_duration)`, the tail) — don't try to unify these into one formula, verify with a written-out numeric trace first. **A track may only keep ONE clip collapsed onto the cut point, not one per orphaned clip.** `_ripple_overlays` snaps an overlay wholly inside the removed interval to `removed_start` rather than deleting it — correct and tested for a single sticker (issues 31/32/50), where one stub is exactly one visible artifact. But `auto_caption` produces many short, sequential cues covering the entire spoken timeline, so deleting even one ordinary v1 clip routinely orphans several consecutive captions AT ONCE — and every one of them used to collapse onto the identical `[removed_start, removed_start+0.1)` stub independently, stacking N different captions on top of each other at that single instant. Reported as garbled, overlapping caption text right after deleting a clip — the exact "don't silently vanish" convenience that protects a lone sticker becomes a bug the moment the overlay track is dense rather than sparse. Fixed by keeping only the FIRST clip that collapses onto a given track's cut point per `_ripple_overlays` call and dropping the rest — a no-op for the single-sticker case these tests already covered (there is only ever one to keep), and the fix for the caption case (four tests pin it: exactly one of several orphaned cues survives, the untouched-before/shifted-after cues on the same track are unaffected, the choice is deterministic — first in track order — and two DIFFERENT overlay tracks orphaned by the same deletion each keep their own survivor independently). **No stub survives past the END of the main lane (QA-021-TAIL):** when the removal took v1's tail (`_ripple_overlays(tail=…)`, derived from the repacked lane for single-interval callers, passed explicitly by `bulk_delete`), a fully orphaned overlay is DROPPED like the emptied-v1 case — a 0.1 s stub at the new end held the timeline 0.1 s past the picture over black. (2) `set_canvas`/`set_aspect_ratio` call `_rescale_overlays_for_canvas_change()` to proportionally rescale every clip/sticker/text transform's x/y (handles both scalar and `Keyframe`-list values) — otherwise a sticker positioned near the bottom of a 1080×1920 canvas ends up off-screen after switching to 1920×1080.

### State + persistence — `edl/snapshot.py`, `edl/ops_log.py`
- `EDLStore(session_dir)` is the per-session state manager; `store.commit(tool, args, summary)` is the **single durability point**: recomputes duration, hashes the EDL, writes a numbered snapshot (bounded by `MAX_UNDO = 500` AND `UNDO_DISK_BUDGET_BYTES` = 64 MB, newest two always kept — QA-046: the old cap of 30 gave ~29 undos while History listed every op; `store.undo_depth` is the honest count, it never reaches past the project's own `init` op, and `GET /api/sessions/{sid}`, every `/dispatch` answer and `undo`/`redo` return it so the Undo button and History's greyed horizon bind to it, never to `ops.length`), atomically writes `edl.json`, appends an `Op` (before/after hashes, tool, args, `by=user|claude`) to the append-only ops log, and **clears the redo stack**. Undo/redo restores snapshot files — **not** inverse-op replay. Read-only tools (`get_timeline`, `diarize`, `generate_hook`) deliberately skip `commit()`.
- **A choice that changes nothing still counts (QA-130 × QA-111).** `commit()` records no op for an unchanged tree, so choosing 9:16 on the default 9:16 canvas left no trace and the first landscape import re-shaped the project anyway. `dispatch()` persists such a no-op canvas choice as `meta.json` `canvas_chosen: true` (`dispatch.is_canvas_choice` / `canvas_choice_remembered`; meta.json travels in a `.vae`), and `main._user_chose_canvas` reads it beside the ops. A choice that DID change the canvas stays an op, so undoing it still brings the auto-match back. Never "fix" this with `record_unchanged=True` — that is the dead undo step QA-130 removed.
- **The redo stack (`EDLStore._redo_stack`) is persisted to `redo_stack.json`** (`_save_redo_stack()`/`_load_redo_stack()`), not just held in-process — it used to be a plain Python list, so it silently emptied whenever the store object was recreated (a real restart, or eviction from `main.py`'s `_STORES` LRU cache below), which read as "Redo does nothing" with no explanation even though the session's own `edl.json`/`ops.json` persisted fine. `store.redo_available` is surfaced through `undo_op`/`redo_op`'s return dict and `GET /api/sessions/{sid}`'s `redo_available` field so the frontend can disable the Redo button correctly instead of dispatching a guaranteed no-op.
- **`commit()` re-validates before it writes** (`_assert_reloadable`, using the exact `EDL.model_validate_json` call `_load_edl` uses, so the check means precisely "would a reload survive?"). An invalid tree raises `ValueError` → 400 to the caller that caused it, and **nothing is written** — instead of succeeding, staying fine in-memory for the rest of the process, and surfacing to whoever opens the project next. ~0.65 ms on a 130-clip timeline, and it reuses the one `to_json()` the snapshot + `edl.json` writes already needed.
- **`store.load_state`** records how this store got its EDL: `new` / `clean` / `recovered` (fell back to a snapshot) / `corrupt` (nothing parsed → empty timeline). `corrupt` and `new` both *present* as an empty timeline, which is why `save_project` used to write a valid `.vae` with `manifest.media == []` over a user's only other copy (VAI-02). `store.is_data_loss_state` is `corrupt AND still has no media clips` — deliberately AND-ed, so once the user adds footage the session is a real project again and a permanent latch doesn't trap them. `save_project` refuses in that state, warns on `recovered`, and bundles `store.edl.to_json()` rather than the on-disk `edl.json` (after a recovery the file on disk is still the unreadable one).
- `main.py` holds a process-global LRU cache of `EDLStore`s (`_STORES`, cap `VAI_STORES_CACHE_MAX=64`, guarded by `_STORES_LOCK`) — the lock matters because FastAPI runs sync endpoints in a threadpool. Eviction needs no flush; the cache is a rebuildable read cache. A separate per-session `threading.Lock` (`_session_lock(sid)`) serialises `/dispatch`, because `dispatch()` read-modify-writes that shared store and background jobs can hold a session for minutes.

### Dispatch engine — `agent/dispatch.py` (~2700 lines, the whole editing engine)
- A tool is a plain module-level function `fn(store: EDLStore, args: dict) -> dict`, callable **only** by being a literal entry in the `DISPATCH` dict at the bottom of the file. No decorators, no class framework — `dispatch()` just does `DISPATCH.get(tool)()`.
- **Adding a tool is a two-file edit with no shared source of truth:** (1) write the handler and add its `"name": fn` line to `DISPATCH`; (2) add a matching schema in `agent/tools.py` via the `_t(...)` helper and append it to `ALL_TOOLS`. The name string must match by hand — nothing enforces it. Not every dispatch tool is advertised to Claude: `DISPATCH` holds **102** unique tools, `tools.py`/`ALL_TOOLS` schematizes **96** for the chat LLM, and every advertised name resolves to a live handler (verified); the remaining 6 are reachable via `/dispatch` and MCP but invisible to Claude. **`tests/test_wave3_correctness.py` now enforces the registry by AST**: no duplicated module-level handler name and no duplicated `DISPATCH` key. Both had regressed — `set_track_muted`, `vocal_isolate` and `instrumental_isolate` were each defined twice with *different bodies* (Python keeps the last, so the earlier body was unreachable and any edit to it would be silently ignored) and were also listed twice as dict keys.
- Three callers share this **single mutation path**, all getting identical undo/ops-log/persistence: (1) Claude chat via `agent/loop.py`, (2) UI gestures via `POST /api/sessions/{sid}/dispatch`, (3) external agents via the MCP server.
- Many handlers are **composites** that call other handlers (`remove_silences` loops `cut_range` back-to-front so timeline coords stay valid; `apply_template` → `apply_hook_stack` → `generate_hook` + `add_super_text`), so one tool call can produce multiple commits/ops.
- Handlers defensively accept **arg aliases** (`index|idx`, `src|lut_path`, `target_lang|to`, `ratio|aspect`, `fit|mode`) because the same fn is reached from Claude, UI, MCP, and docs. User path args funnel through `_safe_src()` → `assert_path_allowed()`.
- **Any tool that DUPLICATES a clip must go through `_clone_clip()`** (`dispatch.py`) — `model_copy(update=…)` is **shallow** in Pydantic v2, so a bare copy hands both clips the SAME `Transform`, the SAME `effects` list and the SAME `ClipAudio`. Editing one then edits both, silently, with no error anywhere. Measured on a clip split at 4s: `a.transform is b.transform` was True, so `set_clip_transform scale=1.75` on the right half also scaled the left and `add_effect vignette` on one put a vignette on both. Reported as a **keyframe** bug with three symptoms that are all this one cause: a key added to the second half "also appeared on first half at the same place"; a key on the first half showed "at the starting of the video AND at the end of the first half" (one key at t=0, drawn on both halves at `c.start + 0` = 0.0s and 4.0s); and one "didn't show up in the video layer" on the half it was added to. Keyframe times are **clip-local** and `Timeline.tsx` draws them at `c.start + t`, so an aliased transform puts the same key at a *different absolute position* on each half — which is why it read as the keyframe moving rather than being duplicated. **The frontend was innocent** — `Properties.tsx` sends `time: playhead - clip.start` correctly and the diamond math is right; don't go looking there. It also **persisted to disk**: the aliased object is serialised once per clip, so both clips genuinely carry the duplicated state, and a reload only stops them tracking each other going forward — which made it look intermittent. Four sites were affected (`split_at` ×2, `cut_range` ×2, `duplicate_clip`, the batch duplicate) and `test_no_bare_shallow_model_copy_survives_in_dispatch` fails on any `model_copy` in that file without `deep=True`.
- **`dispatch()` validates args against the tool's advertised JSON schema** (`_validate_tool_args`) before calling the handler, so `apply_lut {src: true}` is a 400 instead of `Path(True)` → TypeError → 500 (VAI-03) and `add_sticker {position:'center'}` no longer reaches `float('c')` (VAI-04). **Four non-goals, all load-bearing — do not "tighten" them:**
  - **`additionalProperties` is NOT enforced** — it would break the arg aliases above and older UI builds.
  - **`required` is NOT enforced.** The round-5 plan assumed it was safe; the suite disproved it in one run. `split_at` declares `track` required but its handler defaults to `v1`, so the schema's `required` is advice to Claude, not a contract callers have honoured. Instead, `dispatch()` converts a handler's `KeyError` into a `ValueError` **only when the key is schema-declared and genuinely absent from `args`** — an internal KeyError still surfaces as the 500 it is.
  - **Coercible values are accepted** (`"3.5"` for a number), matching `_num()`'s long-standing tolerance. A `bool` never satisfies a numeric or string field (`isinstance(True, int)` is True in Python — that's the trap).
  - **Enum matching is case-insensitive and rewrites `args[key]` to the canonical spelling**, because `add_text` and `set_clip_fit` deliberately normalise case at storage; rejecting `'Pop'` broke them on day one.
  - A property may set **`"x-validated-by-handler": True`** to opt out of the generic enum check where the handler answers better (`add_transition` gives a did-you-mean over ~88 names). `loop.py::_strip_internal_keys` projects every `x-*` key out before the tool list goes to Claude, the same way `category` is dropped.
  - **Numeric bounds ARE enforced (QA-041), from the schema.** `tools._apply_numeric_bounds` writes `minimum`/`maximum` into `ALL_TOOLS` from `_ARG_BOUNDS` plus a generic `TIMELINE_MAX_SECONDS` (6 h) cap on every time arg; `_check_bounds` rejects (400) whatever the schema declares. Time args are upper-bounded only (handlers CLAMP negatives to 0), and an arg whose handler already clamps by contract (`apply_lut.intensity`) is deliberately absent. `_check_ordered_pairs` rejects `end <= start` / `out <= in` when both are present, except for `add_sticker`/`set_clip_timing`, which repair a collapsed span by design. A typo'd `new_start=100000` used to build a 27-hour timeline and an ffmpeg that outlived Undo.
- **Track lock is enforced in `dispatch()` (QA-023), not drawn.** `_call_guarded`: a pre-check refuses a tool whose args NAME a locked lane (clip ids, `track`/`new_track`, and the v1 default of `_V1_DEFAULT_TOOLS`), then the handler runs inside `store.batch()` and any change to a locked lane's JSON rolls the batch back — so composites and unlisted side effects are covered, nothing is committed or logged. Locked overlay lanes do NOT follow a main-lane ripple (`_ripple_overlays`, set_speed's slow-down shift and `_open_main_lane_slot` skip them). `_LOCK_EXEMPT` is reads, history, the lock/mute toggles and project-level canvas/preset changes.
- Enum-constrained values come from **one source**: `add_effect` validates against `render.effects.EFFECT_BUILDERS` (the same registry `list_filters` reports, and `tools.py` now generates its enum from it via `_effect_names()` — the hardcoded list had already drifted, missing `color_grade`); caption `style`/`position` come from the `CaptionsConfig` Literal via `_literal_values()`.
- **A path argument is checked for EXISTENCE at dispatch time, not deferred to render.** `apply_lut` resolved a bundled *name* strictly (`list_luts` → `presets/luts/<name>.cube`, error if absent) but accepted any *path* unchecked, so a typo was stored on the clip as an `Effect(type="lut")` and only failed inside the ffmpeg filtergraph — where `_render_failure_message` saw "No such file or directory" and blamed the clip's SOURCE, sending the user hunting through footage that was fine. Same defect family as VAI-07, found by the round-5 end-to-end sweep rather than by the tester. That message now distinguishes a `.cube`/`lut3d` failure from a missing media file.
- **Normalised bboxes are enforced, not assumed** (`_norm_bbox`, used by `motion_track` and `object_erase`). Every bbox arg is documented 0..1 and nothing checked it, so a pixel bbox (`[10,10,100,100]`) made `ai/tracker.py` hand OpenCV MIL an init box ~100× the frame per axis; MIL sizes its feature buffers from the box area, so the **whole process was OOM-killed** — exit 137, no traceback, every session in it gone (VAI-06, and the likeliest contributor to the VAI-11 instability report). `tracker.track_object` clamps and floors independently: a library that can kill the process must defend itself, not trust its caller.
- Heavy-AI handlers **lazy-import** their deps (librosa, demucs, rembg, open_clip, pyannote, Real-ESRGAN) inside the function body and raise `RuntimeError` when missing, which `main.py` maps to **HTTP 422** — keeping core dispatch importable without the AI extras.

### Chat loop — `agent/loop.py`
Sends tool schemas (projected from `tools.py`, dropping the internal `category` field) + `SYSTEM_PROMPT`, runs the Anthropic tool-use loop (bounded `max_turns=8`, tool_result JSON truncated to 8000 chars), calls `dispatch()` per `tool_use` block, and streams SSE events: `text_delta`, `tool_use`, `tool_result`, `op`, `done`, `error`. The `op` event is how the UI learns the EDL changed.

**Every API call carries `_live_context_block(store)`, recomputed each iteration of the tool-use loop** — a fresh `get_timeline(summary=True)` snapshot (duration + per-track clip counts/ids), never persisted into `history`. It is sent as the LAST text block of the trailing user message (after the prompt-cache marker), not in `system`: `system` is `SYSTEM_PROMPT` alone, cached, and a second system block ahead of every message would invalidate the cached conversation on every mutating round (see the prompt-caching note in `agent/loop.py`). Without this, Claude answers purely from prior conversation text, including about footage from an earlier upload that's no longer on the timeline (confirmed live: a user uploaded a yoga video and asked to remove hand-raising moments; Claude replied "this is a screen recording, there is no woman" — describing a *previous* upload's stale transcript). `main.py`'s `upload()` also resets `chat.json` to `[]` when a video lands on a genuinely empty timeline (not on every upload — a mid-project upload, e.g. b-roll into existing footage, intentionally keeps history since it's still relevant). Relatedly, `get_transcript`/`add_caption_track`/`auto_caption` resolve `ingest.json` from `_current_v1_ingest_json()` — the CURRENT v1 clip's own `uploads/<stem>/` directory (siblings by construction, see `ingest_upload()`) — never `glob("uploads/**/ingest.json")[0]`, which has no ordering guarantee and can silently return a different upload's transcript in a session with more than one. `get_transcript` and `add_caption_track` go through `_load_transcript()` (like `export_srt/vtt/ass`), so an explicitly imported `<session>/transcript.json` (`import_srt`) wins over that ingest transcript — the "Import subtitles → Captions from transcript" flow depends on it.

**Without `ANTHROPIC_API_KEY` the chat turn does not error — it delegates to `agent/prompt/service.prompt_turn`** (0.7.0), the same path the Prompt bar uses, and the first `text_delta` of every turn starts with `via <Brain> — ` so the phone (whose `mobile/lib/sse.ts` drops the five new event types) still shows which brain answered — the phone itself cannot pair in 0.7.1 (see "Phone pairing" below), and the prefix stays precisely so that path works unchanged when `VAE_PHONE_PAIRING` comes back. The cloud path above is untouched; `main._validate_ai_config` logs the no-key state at `info`.

### Prompt Editor — `agent/prompt/` (0.7.0; `docs/PROMPT_EDITOR.md`, spec `docs/design/PROMPT_EDITOR_SPEC.md`)
One sentence → a validated, staged, verified Plan, with no key. Modules, in the order a prompt meets them: `facts.py` (`build_facts`: pure reads of the store + UI state into `TimelineFacts`, every speech fact in **timeline** seconds via `agent/timemap`, `first_use` = the artefacts NOT on disk); `slots.py`/`grammar.py` (pure, table-tested: `1080x1920` is a ratio not a speed, `youtube shorts` is a platform not a count, Hinglish verbs); `recipes.py` (the recipe table: each recipe = steps at a composition **stage** + postconditions; `from_intents(IntentDraft, facts)` is how every on-device brain's output becomes a Plan, so an LLM plan gets stages/prerequisites/idempotence for free); `planner.py` (`compose`: stages 0 inspection · 1 `transcribe` · 2 cuts · 3 shorts (terminal) · 4 look · 5 **transitions** · 6 reframe (+`set_clip_fit(cover)`) · 7 captions · 8 text · 9 music · 10 audio · 11 export preset · 12 audit — transitions BEFORE captions because a cross-fade shortens the timeline and does not ripple overlays; never two transcription passes); `validate.py` (**THE security boundary**, called inside the executor immediately before dispatch: `PLAN_DENY`, unknown arg → reject, `path_args.PATH_ARGS` + `facts.allowed_paths`, enum whitelists for every free string that reaches disk or network, `ARG_BOUNDS`); `presets.py` (text styles, transition looks, edit templates, generated music beds, `SAFE_ZONES` — one table for the §4.9 handler defaults AND the verifier); `executor.py` (one `EDLStore.batch()`, sentinels `$v1_all`/`$selected`/… resolved against the LIVE edl per step, a side-effect snapshot of `ingest.json`/`transcript.json` restored on rollback, ONE `commit("prompt", …)` = one undo step; execution outlives the SSE stream via `runlog.RunBus`, cancel only via `POST …/prompt/cancel`); `live.py` (wave B: run-time sentinels the executor resolves against the live store right before dispatch — `$hook_from_transcript` writes the hook from the transcript that landed after planning, `$fit_to:<s>` ends a target-length trim on the last sentence that fits, and the `$v1_seams` fan-out skips seams next to clips under 0.3 s and reports any cap; what a step did differently rides back as `StepOutcome.notices` into the reply); `verify.py` (every `CHECK_SPECS` name measured from the EDL / timemap-mapped transcript / ffprobe / one 360p `render/verify_render.py` render — never assumed); `pending.py` (clarification + resume; a chat reply resumes only on a **whole-message** match); `service.py` (`EVENT_TYPES`: the phone's six + `brain`, `plan`, `step`, `verify`, `clarify`; `ROUTES`); `summary.py` (the honest reply: failed checks first, `effect:"none"` steps named). Routes: `api/prompt_routes.py` (`/api/sessions/{sid}/prompt*`, `/api/prompt/brains|models`; model downloads are loopback-only); `api/locks.py` holds the session/history locks and the prompt-run registry (`/dispatch` answers `409 prompt_running` rather than queueing a UI gesture behind a caption pass).

**The K3 safety net — no phrasing may leave a wrong edit committed.** Three sweep rounds each found 5-8 new wrong edits from new phrasings, so fixing readers phrase by phrase did not converge. Two layers now sit between any brain's plan and the commit, inside the executor's one `EDLStore.batch()` (`executor.safety_net`, run before the single `commit`): (1) every **blocking** postcondition (`schema.BLOCKING_CHECKS`: EDL-measured checks only — speed, mutes, levels, looks, flips, transitions, text, canvas; the verify event marks each check `blocking`) must hold; advisory checks (captions coverage, speech kept, silences, render loudness, `duration_between` — which measures against the run-START duration and so is stale in multi-cut plans) keep the honest "done with issues" report; (2) the **prompt contract** (`contract.py` + `contract_rules.py`) judges `contract_diff.diff(before, after)` against what the user's WORDS say, read through `semantics.py` with no reference to the plan: `direction` (slower/quieter/smaller went the other way, or a direction contradicts its own amount), `scope` (an attribute changed on a clip or lane the prompt did not name), `partial` (a clause it reads confidently is not true of the result), `unasked` (a kind of change no clause licenses — a voice-over for "add a title", a NEW title for "make the title red"), `range` (a cut past the video, a new title past its end). Any violation raises inside the batch, so the tree is restored (one atomic undo, nothing in history, side-effect files restored) and the run thread pauses on a clarify card ("I undid that: … Which did you mean?", options from `planner.safe_options`; a pick re-plans the same words as that intent and the net judges again, the pick licensing its own family). The contract only judges runs the SERVICE started from a prompt (`contract_hint` is `{}`/`{"picked": …}` there; `None` for hand-built plans, tools and the shorts finishing pass); an optional step that failed and is reported `skipped` exempts `partial`. Precision over recall: a clause the contract cannot read adds no expectation, and composite asks (auto edit, reels, templates, platforms) license every kind of change. `VAI_CONTRACT_SHADOW=<path>` logs what it would roll back without rolling back — how it was calibrated against every existing prompt suite. **`semantics.py` is the ONE reading** of direction, relative vs absolute amounts, scope (several clips, "except", "only", the selection, "it/them" carried across clauses), time phrases, "keep only", typos (`TYPOS`) and ambiguity (`ambiguities()` → the planner answers with a question) — used by the contract, the planner (`semantic_fixups.py`: recipe relabels where the grammar's pick contradicts the words, readings for clauses the grammar read nothing in, lane/clip fixes, typo retry; `scope_planner.py`: one intent per named clip — the composer keeps ONE intent per recipe — merged in stage order with range cuts latest-first) and the on-device adapters (`brains/content.ground_semantics`). A title's look is a plan edit now (`set_text_style`: colour, size / `size_scale`, font / bold, outline, box, case, top/middle/bottom; check `text_style_is`); it never touches the words. Proof: `tests/test_k3_prompt_corpus.py` (286 phrasings + two held-out sets, every one run through the real service; wrong-commit rate must be 0) and `tests/test_k3_safety_net.py`. **Run 4 (Q3) readings, all in `semantics.py` and its consumers:** a percentage of a level is a ratio OF THE CURRENT level (`level_ask`: "music volume 50%" → −6.02 dB from now, "200%" → +6.02; "to 50%" the same; `pct_to_db` keeps 2 decimals) — never a level on the dB scale; "twice as fast" / "double the speed" / "N times faster" / "half speed" / "by half" carry `SpeedAsk.scale` and MULTIPLY each clip's own speed ("slow motion" stays the named 0.5x; "50% faster" stays relative to 1x); `direction(t, "look")` reads a look's strength ("stronger" / "weaker" step `LOOK_STRENGTH_STEP` on the clips that carry it, `ClipFact.look_intensity`), `ClipFact.color` lets "brighter still" step from the clip's grade; `whole_video_by` ("shorten the video by 3 s", "make it 2 s shorter") is a tail `TimeRef("last")`; `ui_range` reads playhead- / marker-anchored ranges ("from here to the end", "after the playhead", "before the marker" — `TimelineFacts.markers`), which `planner._ui_ranges` binds to a `TimeRange` (a missing anchor is one question) and `range_targets` turns into a split at the playhead plus `$playhead` (the right half, resolved live) — the contract binds the same span (`ClauseRead.ui_span`, `Contract.read(markers=, video_end=)`) and the verifier resolves `$playhead` / `$selected` to the one clip; "fade the title in" is a `set_text_style(anim_in=…)` restyle (`text_look_of`, the fade→title relabel), "appear at 3s and disappear at 7s" reads both clauses, two restyles naming different texts stay two edits (`_another_title`), and a scope-only lead clause ("take clip 3, …") is not reported "Not done". Proof: `tests/test_run4_prompt_leftovers.py` and the corpus's "run 4 (Q3)" block.

**Preview, then apply (0.8.0; `preview.py`, `changes.py` + `change_rules.py` + `change_words.py`, `prompt_setting.py`) — owner decision: a key-free plan changes nothing until the person presses Apply.** When the plan's brain is not `claude` and "Ask before applying Prompt bar edits" is on (`prompt_setting.confirm_before_apply()`: `VAI_PROMPT_CONFIRM` env › `settings.json` `prompt.confirm_before_apply` › default **ON**; `GET/PUT /api/settings/prompt`, loopback + same-origin + JSON), `service._run_and_stream` starts the run thread in mode `preview`: `executor._preview_run` runs the SAME `run_plan` as a **dry run** on `preview.scratch_store` — a throwaway `EDLStore` at `<workdir>/.prompt_preview/<run>/<sid>/` (beside the sessions, named by the sid, holding a deep copy of the live tree + meta/transcript/speakers.json), so every file a handler writes under `store.dir` lands there and is deleted; `ingest.json` beside the media is covered by the side-effect snapshot, restored after every dry run; render-only tools are skipped, `make_shorts` runs with `save_as_sessions=False`, no verify render, no commit, no op, no undo step. The K3 net judges the dry run exactly as a real one (a violation becomes the same question, saved in the LIVE session). The card's lines come from the EDL diff, never the plan text: **`changes.summarize` NEVER omits a change** — `flat_state` flattens the whole model dump under stable keys (`clip:<id>.audio.gain_db`, `trans:v1@4.0`, `canvas.w`; None ≡ absent; only `EDL.duration`/`version` are derived and excluded), every rule CLAIMS the keys it describes, and `generic` writes a line for every unclaimed key, so `covered ⊇ diff_keys` holds by construction (`tests/test_prompt_preview_changes.py`: every `TOOL_STAGE` tool op by op + 400 random mutations). A rule may claim only what it explains: a split claims a piece's fade ONLY when the fade demonstrably moved to another piece (claiming every edge field once hid "fade in" behind "Split"). The run pauses as a `confirm` pending state (`pending.save_pending(preview=…)`: the plan, `base_hash` = live `edl.hash()`, `fingerprint` = `changes.canonical` — new ids renamed in document order, scratch paths mapped to the session's — and the full line list) and streams `clarify{…, preview:{summary, lines, more, total, note, nothing_changed}}` with ONE confirm question `apply` (so the chat pane and the phone still get yes/no + the list as text; a whole-message "yes" applies). **Apply** (`POST …/prompt/answer {token, apply:true}` or `answers.apply`) → `service._resume_preview`: expired or `live.edl.hash() != base_hash` → re-plan the prompt and show a fresh card (never a stale apply); else mode `apply` re-runs the SAME plan on the live store in one batch (one op, one undo step), re-checking the base hash INSIDE the session lock (`handle.stale` → the stream re-plans instead of ending) and, before the commit, `preview.apply_check`: the result must fingerprint the same OR produce the very same lines, else roll back and redraw the card (`_repreview`). Change/Cancel = `POST …/prompt/cancel {token}` (or `apply:false`): nothing committed. A new prompt while a card is open drops it. Setting OFF → the old immediate behaviour (the net still runs). **The dry run's heavy work is done ONCE (final QA r4, `artefacts.py`)**: previewing "add captions" used to transcribe on the scratch copy and Apply transcribed again (reframe/denoise/remove_background likewise), because the byte-identical rule forbids the dry run writing into the live session and the scratch copy is deleted. The dry run now writes what it derives to a content-addressed cache under the preview area, `<workdir>/.prompt_preview/artefacts/<kind>/<key>/`, keyed by (tool, input file identity = size+mtime+head/tail hash, parameters, model version — faster-whisper release+batch or the ggml file+whisper-cli stat); Apply reads an entry whose key still matches and derives again otherwise. Two adapters: `cached_transcribe` wraps the whisper call in `transcribe_tool`/`_auto_caption_one` (a hit returns the same `Transcript`; the handler still writes ingest.json as after a real pass), and `StepCarry` (in `_dispatch_step`) captures the files a `DERIVED_TOOLS` step created under `<scratch>/cache/` and lays them into `<live>/cache/` before Apply's handler runs, so the helper's `dst.exists()` check finds them. On ONLY inside a prompt run via a contextvar (`for_mode`: preview writes, apply reads, a plain run never touches it), so every other transcription, `force` included, is unchanged. Entries are self-contained copies (hard-linked where possible); an incomplete one is a miss and is removed, never a dangling reference. `render/cache_budget.enforce_artefacts` trims the area LRU by whole entry to `VAI_PROMPT_ARTEFACT_CACHE_MB` (default 2048) after every write, so a cancelled or dropped card just leaves entries to age out; `preview._sweep` skips `ARTEFACT_DIR`. `tests/test_prompt_preview_artefacts.py` pins: preview+Apply of a captions plan calls whisper once and commits the card's fingerprint while the live session stays byte-identical, a replaced source under the same path is transcribed again, a dropped card's entry survives to the LRU and a miss re-derives, a denoise render is derived once. The prompt suites test plan semantics with the explicit auto-apply switch (`tests/conftest.py` sets `VAI_PROMPT_CONFIRM=0`); the preview suites turn it on (`test_prompt_preview.py`, `test_prompt_preview_corpus.py` — preview+Apply commits exactly what auto-apply commits — and `test_prompt_preview_ui.py` in Chromium + WebKit). ### Render pipeline — `render/` (one ffmpeg `filter_complex`, keyed by EDL hash)

- **A PIP is placed in TIME inside the graph (`pip.pip_video_timing`: frame-exact, then `setpts=…+<first frame>` in whole ticks — never `-itsoffset`, see below), and on the CANVAS by an x/y its lane must supply.** Reported as "PIP/overlay not working properly, instead of adding a layer on the video, it just applies a black box on the top left" — one sentence covering two independent defects, either of which produces that description:
  - **No time offset.** `enable='between(t,start,…)'` gates *when the overlay is drawn*, but the PIP's own frames entered the filtergraph at t=0, so by the time the window opened the stream had already ENDED and `overlay`'s default `eof_action=repeat` held the **last decoded frame** for the whole appearance. A PIP anywhere but t=0 was a still image of its own final frame — literally a black box whenever the clip ends dark, which is most clips. Measured with a 4s source of 1s colour blocks at `start=5`: the window showed YELLOW (source second 3) throughout where RED (second 0) was due; after the fix the walk is red→green→blue→yellow across 5.5–8.5s and empty either side. The **PIP audio path had the offset all along** (`adelay` in compositor.py), so the sound played in the right place while the picture was frozen — that asymmetry is the tell. Same defect the text-overlay path already fixed for animated overlays. Use **`-t <duration>`, never `-to <abs end>`**, alongside it: `-to` is an absolute input timestamp and `-itsoffset` shifts what it is compared against, so together they can truncate the input to nothing.
  - **…and `-itsoffset` is gone from PIP inputs (QA-002, 0.7.3).** With an input offset ffmpeg 8.1 stops seeking accurately: it keeps every frame from the keyframe BEFORE `-ss` whose shifted timestamp is still ≥ 0, and counts `-t` from that keyframe — so a PIP trimmed deep into a long GOP (any camera file) lost that much of its tail, frozen on one frame (`-ss 0.983 -t 3 -itsoffset 2.5` decodes frames 0-89, not 30-119). A PIP input is now `pip_input_args` (half-frame pre-roll seek, `-t` for n frames + slack) and the chain rebases, `fps=`, clone-pads, `trim=end_frame=n`, then shifts by an INTEGER tick count: `setpts` truncates, and `1.001/(1001/30000)` is 29.999…, which put every PIP on a 29.97 project a frame early. Its sound (`pip.pip_audio_chain`, shared by the full render and the remux fast path) is cut to the same frames' samples and delayed in samples. `tests/test_b5_pip_frame_exact.py`.
  - **No placement.** `add_clip` sets `x=w/2, y=h/2, scale=0.6` when it *places* a clip on a PIP lane, but a clip that arrives by being **dragged** kept `Transform`'s plain `x=0, y=0` — which `pip.py` reads as "centre this element on the canvas ORIGIN", emitting `overlay=x='(0.00)-overlay_w/2'`. Three-quarters off-screen, only the bottom-right corner visible, in the top-left of the frame: on a 720×1280 preview it occupied x0-223/y0-167 instead of x136-583/y472-807. `move_clip` now re-bases through `_rebase_transform_for_lane()` whenever a clip crosses **between v1 and a PIP lane** — in both directions, because those three fields mean different things on the two lanes (a v1 crop-pan/zoom vs. an on-canvas centre/size), so carrying the numbers across is not preservation. Detached is fine to *seek* and `drawImage` from, which is all this file originally did; it is not fine to **play**, which the flicker fix changed them to do. Blink runs a detached element, WebKit makes no such promise, and WKWebView is what the packaged macOS app renders in — so this is a defect that cannot appear on a Windows dev machine and lands on a Mac as "the PIP freezes on one frame during playback". The host is deliberately **not** `display:none` (an unlaid-out element may stop being fed frames) but 1×1/transparent/`pointer-events:none`. FrameScrubber's fallback `<video>` *is* `display:none`, correctly — it is only ever seeked.
  - **While PLAYING, play the element; do not seek it.** The playhead advances ~1/fps per frame against a max(1/fps, 0.03) tolerance, so every single frame re-assigned `currentTime`; each assignment starts an async seek, `readyState` dips below HAVE_CURRENT_DATA while it runs, and the loop painted its no-frame placeholder — 30 seeks/sec that never settle, which is exactly "the pip video keeps flickering when the video is played and sometimes it gets vanished". Seeks stay for scrubbing; playback corrects only real drift (`PIP_RESYNC_TOL`).
- **A PIP's box, shape and inner framing are ONE decision, and the crop order is load-bearing.** `circle` forces a **square** box (a circular mask over a 16:9 element is an ellipse — "when i chose circle it gave me ellipse"); `fit='cover'` takes the canvas aspect, which is what finally makes the Fill-frame checkbox do anything on a PIP lane (`pip.py` ignored `fit` entirely before, so the control was inert). Shapes are cut procedurally with **`geq`** in the stream's own `W`/`H` rather than by alphamerging `effects.render_mask_png`'s canvas-sized PNG — the element's pixel size depends on a source aspect this module never probes, so a canvas-sized mask would be the wrong size and off-centre. `Framing.rotation` turns the picture *inside* the shape while the shape stays put (distinct from `Transform.rotation`, which turns the whole element); it must be applied **before** the crop and the cover **grown first** to `w·|cos| + h·|sin|` by `w·|sin| + h·|cos|`, or the rotation drags transparent corners into the shape. Rotating therefore costs magnification — inherent to rotate-and-fill, not a choice. Contrast v1, which rotates **in place** and accepts cut corners because the canvas *is* the frame. The mask is applied before the rotate, so the shape turns with the element.
- **`Transform.opacity` on v1 is a fade toward BLACK, not an alpha channel — and until 2026-08-17 it was not implemented at all.** `compositor.py`'s per-clip chain had no opacity handling, so the value committed to the EDL, survived a reload, and changed nothing in the preview or the export. It was honoured for PIPs (`pip.py`), text and stickers, which is precisely why it looked implemented. It did worse than nothing: `Preview.tsx` applies its live CSS opacity **relative to what the visible render has baked in** (`liveCssTransform` divides by the baked value) and reads that baked value from the **EDL** — so the EDL said 0.3 while the frame was still at full brightness, dragging further down dimmed by the wrong amount, and dragging back **up** did nothing at all, since CSS opacity cannot exceed 1 and the "restore" it counts on never existed. Three things to keep straight:
  - **Not `pip.py`'s line.** A PIP is OVERLAID, so `format=yuva420p,colorchannelmixer=aa=` lets the layer beneath show through. v1 is the **base**: nothing is beneath it, so alpha there is discarded at yuv420p conversion. Multiplying RGB toward black is what the canvas already does (the letterbox is black) and what the browser does fading the element over the black preview pane — which is what makes the live preview and the bake agree.
  - **The multiply must happen in `gbrp`.** `colorchannelmixer` on YUV input scales the chroma **offsets** as well as luma, dragging 128/128 toward 0/0 — the picture tints hard green as it dims. The filter string looks identical either way; only pixels catch it, which is why `test_dimming_does_not_TINT_the_picture` measures RGB spread.
  - **A keyframed opacity uses `geq` with `T`, never the chain's lowercase `tvar`.** geq's expression namespace is its own (X/Y/W/H/N/T); lowercase `t` is not in it, so a `tvar`-built expression fails the WHOLE graph with `Unknown function in 't-0.0000)…'` — the render dies rather than animating wrong. `rotate` on the line above legitimately uses `t`, which is exactly why reusing `tvar` here looks right and isn't. `text_overlay.py`'s animated-opacity geq already had this right.
  - The source-preview canvas (`Preview.tsx`) applies the same fade via `globalAlpha` over its black fill. It REPLACES the `<video>` while up, so anything it does not reproduce simply vanishes from the preview — it ignored opacity entirely, so a dimmed clip jumped to full brightness the moment a rotation drag took over.
- **The source preview gets its OWN `<video>` pool (`sourcePreviewVideo`), never `pipVideo`'s.** `pipVideo` keys on `src` alone, so the instant the same file sits on v1 *and* on a PIP lane, `StickerLayer`'s paint loop and `Preview`'s source-preview loop hold the SAME element — and each calls `syncPipVideo` on it every frame with a **different clip trim**. The seeks never settle, `readyState` never reaches HAVE_CURRENT_DATA, and the source canvas paints only its black fill: **the main video goes black for the whole rotation drag while the PIP keeps drawing** (the PIP survives on `drawPipVideoFrame`'s `LAST_FRAME` fallback, which this path had no equivalent of), and releasing the pointer fixes it because the source preview unmounts and the PIP regains sole ownership. Reported as "when i rotate the video up to certain angle, after rendering, when i change or rotate the video, the video gets blacked out… when i leave the cursor, it works fine". Three things worth keeping:
  - **It only bites when the two clips point at DIFFERENT SOURCE TIMES.** At the same in-point both loops want the same instant and `syncPipVideo`'s tolerance suppresses the seek entirely, so nothing thrashes. The first repro used `in=0` on both and proved nothing; the live session had v1 at `in=0` and a circle PIP of the same file at `in=4.0125` (past the end of a 4.01s source). If you cannot reproduce a "two loops, one element" bug, check whether both loops actually *want different values* before concluding the mechanism is wrong.
  - **The pools must also be separate for `pausePipVideosExcept`**, which pauses every element it owns that is not a currently-active PIP — a v1 source is not a PIP at all.
  - **An armed-but-blank source canvas must not take the picture away.** The `<video>` is now hidden only once the canvas has actually PAINTED a frame (`srcDrawnRef`), and a decoder dip after that leaves the last painted frame rather than clearing to black — the same "stale frame beats a hole" rule the PIP follows. This is what turned the failure from "black rectangle" into "worst case, the old CSS stand-in".
- **`edl.render_hash()` keys every render; `edl.hash()` is the EDL's identity (wave C, QA-131).** Both are sha256[:16] of canonical JSON; `render_hash` leaves out what no render reads — `markers` and a track's `locked`/`label` (`schema.NON_RENDER_TRACK_FIELDS`). Previews (`previews/<render_hash>.mp4`), the supersede registry (`cancel.PREVIEWS`), `GET preview.mp4?h=` and verify renders use it, so adding a marker is served from the same file (it re-rendered 49.8 s on a 12-min timeline). `hash()` stays everywhere an EDIT must count — the ops log, `/dispatch`'s `edl_hash`, stale-edit checks, "export outdated". `GET preview.mp4?h=<the EDL hash>` is aliased to the current render. A field that DOES change pixels or samples must never be added to the exclusion list. Preview returns instantly on a hit; an `_INFLIGHT` dict collapses concurrent identical renders.
- **Chunk cache** (`render/chunks.py`): with no V1 transitions, each clip renders once to a content-fingerprinted mp4 and the timeline becomes a fast `concat` — editing one clip re-renders only that chunk. Disabled under transitions (xfade needs both streams in one graph). **Previews only (QA-097): an EXPORT is one ffmpeg pass** (`_render(chunked=False)` from `render_export`) — chunking it encoded every frame twice (~2x slower, a generation of PSNR, and 0 % progress for the whole chunk stage: 200 s clip 28.0 s → 13.6 s, first progress 14.6 s → 0.7 s). - **Render caches are bounded by BYTES, LRU** (`render/cache_budget.py`, QA-106). A render's own working set (`since=` its start) and files touched in the last 30 s are never evicted. `GET/DELETE /api/sessions/{sid}/render-cache` report and clear (keeping the on-screen preview).
- **`Clip.reverse` renders** (`render/reverse.py`, QA-037): the clip's source range is built ONCE into a cached intermediate that already plays backwards (bounded segments, each `reverse`/`areverse`d on the project grid, joined last-first by packet copy; PCM sound), and `with_reversed_sources` swaps it in for the clip at the top of `_render_locked` / `_remux_with_new_audio` — everything downstream is the ordinary forward path. - **Exports are named after the project and their settings** (`compositor.export_filename`, QA-098): `<Project> 1920x1080 29.97fps q18.mp4` / `… 8000kbps.mov`, one per-destination lock. - **Audio rules live in `render/audio_mix.py` (wave B, QA-079/082/086).** (1) **The duck is a gain envelope, not a compressor:** speech activity is detected on a level-normalised key (`dynaudnorm` → 20 ms envelope → threshold → ~1 s hold → 25 ms attack / 160 ms release, 60 ms lookahead) and the bed is `amultiply`'d by exactly `10^(to_db/20)` while anyone speaks — `sidechaincompress` made the dip follow the talker's level, ignored `to_db` and never keyed a −33 dBFS talker. Every `aeval` in that chain names `c=same`/`c=mono`: with an unset layout the biquad after it silently passes through. The prompt's `music_ducked` check measures the dip the renderer applied (`STEM_DUCK_PROBE`, a 1 kHz carrier × the duck gain) over the transcript's speech. (2) **The preview is loudness-matched to the export** (`render/preview_loudness.py`): an in-graph `ebur128` tap measures the pre-gain mix, a static gain + −1 dBFS `alimiter` (`level=0`) follows, the session remembers the measurement, and only a >1 LU miss pays an in-place AAC re-gain — unless the tap's pre-gain sample peak × the applied gain reached the −1 dBFS ceiling, in which case the audio is re-rendered in ONE pass at the wanted gain (`_rerender_audio`, the audio-only remux): re-gaining a file the limiter already squashed at the wrong gain kept the squash (Final QA: 4.8 dB low in a loud overlap on a session's first render). `loudnorm` itself stays export-only. Tests that measure RAW preview levels must set `canvas.loudness_lufs = None`. (3) **Pro tools:** `Track.solo` (applied as clip mutes by `apply_solo` at the top of `_render_locked`/`_remux_with_new_audio`), `detach_audio`, volume keyframes in `AudioProps.gain_env` (dB offsets from `gain_db`, clip-local timeline time, applied PER SAMPLE by `aeval` with the picture's 1 µs key rule — wave E, not `volume=…:eval=frame`, a per-packet staircase — and rebased on split, `cut_range` and head trims via `dispatch._piece_gain_env`; `add_keyframe prop="audio.gain_db"` speaks the absolute level), and `AudioProps.keep_pitch=False` varispeed (`asetrate`, sample-exact — atempo's WSOLA moves transients ±12 ms). Single-pass `loudnorm` (dynamic, rode the gain and missed −14 by 1.2 LU) with a SAMPLE-peak `alimiter=0.97` (−0.3/−0.6 dBTP delivered) is only the fallback when pass 1 fails. Without a target a MIXED timeline still gets the limiter; a lone v1 track is untouched. - **A preview render is superseded, not queued** (`render/cancel.py`, QA-004). `main._render_preview_latest` registers each interactive render in `cancel.PREVIEWS` (one live render per session): a request for a DIFFERENT EDL hash sets the older render's event, every preview-path ffmpeg (`cancel.run`, a drop-in for `subprocess.run` that IS `subprocess.run` when no scope is active) is terminated, and the old request answers 409 `preview_superseded`. - **Long clips preview from picture SEGMENTS** (`render/segments.py`, QA-005 partial). Every overlay gate is HALF-OPEN on frame-exact bounds (`timebase.enable_window` → `text_overlay.enable_expr`; client `lib/overlayGate.ts`) — `between()` drew both captions on an SRT cue change.
- **Mixed-script text is shaped PER SCRIPT RUN with a per-run face (wave-B review).** `shaping.ShapedFont.runs` splits each line by bidi level AND Unicode script (`script_of`; Common/Inherited — spaces, digits, marks, ZWJ — join the neighbouring run), sets `buf.script` explicitly (never `guess_segment_properties`, which took the script from the first strong character: "Hello नमस्ते" shaped as Latin), and draws a run the clip's font does not cover in the bundled Noto face for its script (`text_overlay._SCRIPT_FALLBACK_FONTS`, pinned in `text_layout_cases.json` `script_fallback`; the preview's canvas font list puts the same Noto families after the role family — `textLayout.fontFamilyList`). `_pick_script_font` still picks the PRIMARY face by dominant script, so single-script text renders exactly as before.
- **A `font` value is a bundled font NAME, never a path (`render/fonts.py`).** `resolve_font` only resolves a plain leaf inside `FONTS_DIR` (`is_relative_to` after resolve); `check_font_arg` is the tool-boundary 400 used by add_text, set_caption_style, apply_brand_kit and `set_property style.font`. `FONTS_DIR / name` let '/etc/hosts' escape and 500 every later export.
- **Emoji INSIDE a text clip are composited as images, not glyphs.** The role fonts (Anton, Bebas, Inter, Montserrat) carry no emoji, so `render_text_png` used to push text through `_strip_emoji` first — typing "🔥 SALE" exported "SALE" and a pure-emoji clip exported a blank PNG ("I was unable to apply the emojis through the text section"). Both `render_text_png` and `TextLayer.tsx` now tokenize the string and paste the same Fluent 3D artwork a sticker uses, each emoji occupying a square of `EMOJI_BOX_RATIO × font size` that participates in wrapping — **that constant, and `_emoji_clusters`/`emojiClusters`, are duplicated on both sides and must move together or the preview wraps differently from the bake.** Two traps: `_EMOJI_RE` ends in `+`, so a match is a RUN and must be split into renderable clusters ("😍🤩" was looked up as `1f60d-1f929`, found nothing and drew nothing) while genuine multi-codepoint emoji — ZWJ sequences, flag pairs, skin tones, keycaps — stay whole; and the text-PNG cache key must hash the FULL text (it hashed the stripped text, so "SALE" and "🔥 SALE" collided). The browser fetches artwork from `GET /api/emoji/{codepoints}.png`, which is global and read-only — letting it paint emoji with the OS font instead would put Apple/Segoe art in the preview and Fluent in the delivered file.
  - **VERTICAL placement is measured per side, NOT a shared constant** (`_cap_band_mid` / `capBandMid`): the emoji square centres on the text's **cap band**. A single `EMOJI_TOP_RATIO = 0.06` em-box fraction could not be right for both, because where the cap band sits inside the em box is a per-font property *and* the two renderers start from different origins — Pillow's `draw.text()` draws from the ASCENDER TOP, canvas `textBaseline='middle'` from the EM-BOX MIDDLE. It put the bake 26.5px above the text and the preview below it: misaligned on both sides and disagreeing with each other, which is the one thing this whole subsystem exists to prevent. Horizontal advance (`EMOJI_BOX_RATIO`) stays a shared constant — it drives wrapping, so it must be identical, and it has no font-relative origin problem.
  - **Wrap units carry a `glued` flag (`_emoji_words` / `wrapUnits`) so the wrapper cannot invent spaces.** An emoji must be its own wrap-word (the text font measures it at ~0px, so a glued one overflows the line by exactly its box), but `_wrap` then rejoined words with a hard `" "` — laying "GG🔥🔥" out as "GG 🔥 🔥" and spacing emoji **0.32 em** apart against a 0.24 em word space ("the space between the emoji is too much"). Now 0.086 em, and a space the writer *did* type still survives. General rule: splitting a string for measurement must not change what gets drawn.
  - **Artwork arriving must itself trigger a repaint** (`emojiGeneration()` in `lib/emojiArt.ts`). `TextLayer`'s rAF loop skips a frame unless the playhead moved; artwork is requested DURING a draw and lands after it, so a PAUSED preview painted exactly one frame — the one with the fetch still in flight — reserving each emoji's box and leaving it blank forever ("it left an empty space in place of the emoji"). The counter (bumped on load AND on error) is compared alongside the playhead, the same role `fontsReady` plays for a late-loading font. Any future layer that both throttles redraws and paints async-loaded assets needs the same signal.
- **Emoji sticker artwork is FETCHED, never an OS font** (`ai/emoji.py`) — that is the invariant; *which* set it fetches is a look decision layered on top. Preview and export must show identical pixels, and a Mac and a Windows user opening the same project must too; drawing the glyph with a system font gives Apple Color Emoji vs Segoe UI Emoji vs the baked art — three different designs. **The set is Apple/iOS artwork at 160×160**, from `iamcal/emoji-data@16.0.0/img-apple-160`. It was Noto (Android, 512px) for one round; the switch back to Apple is a deliberate, user-directed choice and the reasoning is in the module docstring so nobody "corrects" it by accident.
  - **160 is Apple's ceiling, not the mirror's.** Apple Color Emoji is an `sbix` BITMAP font with strikes 20/32/40/48/64/96/160 (verified via `tmm1/emoji-extractor`, which reads the system font). `img-apple-320`/`-512` 404, `emoji-datasource-apple` stops at 64, and Emojipedia serves 160 even from its `/thumbs/320/` path. **There is no higher-resolution Apple artwork to find — don't go looking again.**
  - **What 160 costs is narrower than it sounds.** Emoji *inside text* render at `size × EMOJI_BOX_RATIO × EMOJI_INK_RATIO`; the largest role (`hook`, 170pt) needs 156px, so **every text role downscales and stays sharp**. Only standalone stickers upscale (422px ÷ 160 = 2.64×), and Apple's gradient-heavy art survives that better than hard-edged vector would.
  - **Apple wins on consistency**, which is why the fallbacks barely fire: it covers **3778 of the 3781** RGI emoji (99.9%), flags included. Exactly three fall through to Noto (♀️ ♂️ ⚕️). Under Noto-primary every flag came from Fluent — a visibly different house style inside one line.
  - **The licence is the real cost, accepted deliberately.** Apple's emoji are Apple's copyright on a third-party mirror: fine locally, a genuine redistribution question if an export with a baked sticker is published commercially. The openly-licensed sets stay wired up (Noto Apache-2.0/OFL, Fluent MIT, Twemoji CC-BY 4.0) so reverting is one constant. `test_the_proprietary_primary_is_a_documented_choice` **inverts the old gate**: using Apple is allowed, using it *silently* is not — it fails if the module docstring stops explaining the trade.
  - **Filename spelling is per-source on three independent axes and every one was verified live**, because a wrong guess doesn't error — it 404s, falls through, and that one emoji silently renders in the wrong style. Apple: dash-joined, **zero-padded to 4**, **VS16 kept** for legacy dingbats (`0023-fe0f-20e3`, `2764-fe0f`; plain `2764` 404s). Noto: `emoji_u` prefix, `_`-joined, padded, VS16 always stripped. Fluent/Twemoji: dash-joined, unpadded.
  - **The cache namespace must change on every chain change** — now `…/emoji/apple2/`. Note it is `apple2`, not `apple`: an earlier round already used `apple/` with a chain that had no Noto, so its entries for the emoji Apple lacks came from a different source. **A namespace identifies the whole chain, not just its first link.** Prior namespaces (`noto`, `apple`, `fluent3d`, bare root) stay readable **newest-first** as offline fallbacks.
  - **`EMOJI_INK_RATIO = 0.92` gives the emoji a side bearing of our own** (`text_overlay.py`, mirrored in `TextLayer.tsx` — they must move together). A text glyph has side bearing, a PNG doesn't, so an emoji butted against neighbouring text ("GG🔥" with the G's stroke touching). Do NOT "simplify" this away on the theory that the artwork already has margin: measured, **Apple's own tiles run 0.000 (😊 😂 🎉, edge-to-edge) to 0.119 (🔥)**, so spacing would otherwise be whatever each artist happened to leave. The advance is unchanged, so wrapping is unaffected.
  - Finally, the **text-PNG cache key carries a version prefix** (`v9`) that must be bumped on any artwork or placement change — nothing else in that key tracks either, so a stale hit silently exports the old art forever.
  - **`add_sticker` never fetches — dispatch resolves artwork LOCALLY** (`emoji.local_emoji_png`, gate X3). An edit op that opened a connection to jsDelivr stalled on it, failed offline and was an unguarded fetch inside the single mutation path. Order: the pinned `apple2` cache (normally filled by the picker's swatch request) → `emoji/local/` → a tile drawn ONCE from the installed Apple emoji font (`ai/emoji_local.py`) → prior-style caches. That tile is not the forbidden OS-font path: the pinned set *is* that font's 160 px sbix strike (😂's embedded bitmap is byte-identical to the download; over 3433 cached tiles alpha matched on all, colour within ±1 on 3415, 10 are newer revisions), and it is baked to a PNG the session copies, so preview, export and a collaborator all read the same bytes. It refuses anything the text colour reaches (the font has OUTLINE-only ♂/♀/⚕ — exactly the three the pinned set lacks) and anything wider than one tile. macOS only; elsewhere offline stickers need a cached tile. `fetch_emoji_png` (text emoji, export) deliberately never draws locally, and the serving-path restyle only swaps a copy for art from the CURRENT namespace, never backwards to a prior-style cache.

## Desktop app assembly

**The whole thing is a single FastAPI process.** At import time `main.py` mounts `frontend/dist` at `/` as `StaticFiles(html=True)`, so `/` is the editor and `/api/*` is the backend on the **same origin** — no separate frontend server in production. Because `/` is a catch-all mounted **last**, every real API route must be declared before that mount — **route ordering is load-bearing**.

`desktop.py` is an in-process wrapper: it starts uvicorn on a daemon thread in the same process, polls `/api/health`, then opens a pywebview native window (OS webview — no Electron). In dev it auto-runs `npm run build` if `frontend/dist/index.html` is missing; in a frozen `.app` it hard-exits instead. Almost every filesystem lookup (`frontend/dist`, `VERSION`, presets, fonts) is **`sys._MEIPASS`-then-repo** to work both bundled and from source.

**`desktop.py` (the PyInstaller entry) MUST use absolute imports, never `from .`.** PyInstaller freezes the entry script as the top-level `__main__` (the `.spec` and `build_app.sh` both point at the *file path* `src/video_ai_editor/desktop.py`, not `-m`), so `__package__` is unset and any package-relative import raises `ImportError: attempted relative import with no known parent package` in the built EXE/.app — even though the package is bundled. This is **invisible in every dev path** (`run.sh`/`run.ps1` use `python -m …`, which sets `__package__`; pytest uses `pythonpath=["src"]`) and reproduces **only** in the frozen artifact. Use `from video_ai_editor import …` in `desktop.py`; the absolute name resolves regardless of `__package__` because `collect_submodules('video_ai_editor')` bakes the package into the PYZ. (Contrast `main.py`, which *can* use `from .` — it's always loaded via the absolute string `"video_ai_editor.main:app"` passed to `uvicorn.run`, so it's imported *with* a parent package.)

## Import-time config chokepoint — `config.py`

Importing `config` runs side effects and every entry point hits it before shelling out:
- **Augments `PATH`** so shelled-out binaries resolve regardless of launch method: on macOS the Homebrew/MacPorts bins (a double-clicked `.app` inherits launchd's minimal PATH); on Windows the winget-ffmpeg package dir (`%LOCALAPPDATA%\Microsoft\WinGet\Packages\Gyan.FFmpeg*\...\bin`, since Gyan.FFmpeg famously isn't put on PATH).
- **Loads `.env` with non-standard precedence:** real shell env always wins; among files the **first loaded wins** (only sets keys not already set), order `<repo>/.env` then the per-OS user config dir's `.env` (`_pu.user_data_dir("Video AI Editor")` — `~/Library/Application Support/…` on Mac, `%APPDATA%\…` on Windows). The user-level dir is how a shipped app picks up `ANTHROPIC_API_KEY` (the repo `.env` is invisible inside the read-only bundle). Note: `.env` values are read literally — inline `# comments` after a value become part of the value.
- **Creates `WORKDIR`** (dev `<repo>/workdir`; frozen `<user data dir>/workdir`, per-OS).
- **`VAI_ALLOWED_ROOTS` splits on `os.pathsep`** (`;` on Windows, `:` on POSIX) — not a hardcoded `:`, which would shred `C:\` paths.
- Key vars: `CLAUDE_MODEL=claude-sonnet-4-6`, `WHISPER_MODEL=small` (fast, for uploads) vs `WHISPER_CAPTION_MODEL=large-v3` (captions), `WHISPER_DEVICE=auto` (**probes for a CUDA GPU — it used to mean cpu**, see Local-AI conventions) with `WHISPER_COMPUTE_TYPE` and `VAI_WHISPER_BATCH_SIZE` alongside it, and `VAI_RESTRICT_PATHS` (default **OFF**) — flip on for hosted deployments to force tool path args under `WORKDIR`/`VAI_ALLOWED_ROOTS`.
- **The Claude key has ONE resolver: `config.anthropic_api_key()`** (wave C, QA-063-SETTINGS) — every Claude call site (chat loop, cloud brain, hooks, vision, translate, `/api/features`' `anthropic_key_set`) calls it per use, never an import-time constant, so a key saved in **Settings** works without a restart. Order: a non-empty `ANTHROPIC_API_KEY` (shell/.env) wins; **present-but-EMPTY means "no Claude" and the Keychain is NOT consulted** (the test gate and benchmark harness run with `ANTHROPIC_API_KEY=""`, so an owner's saved key never leaks into them); otherwise the macOS Keychain item (`keychain.py`: service `"Video AI Editor"`, account `anthropic_api_key`, memoised 60 s, dropped on save/remove). The key is written through `security -i` on **stdin** (argv is world-readable via `ps`), must match `sk-ant-[A-Za-z0-9_-]{20,400}` before it is written (which also makes the stdin line unbreakable), and `security` runs with the ACCOUNT's home (`pwd`), not `$HOME` — with a sandboxed `$HOME` it finds no keychain and blocks on a create-keychain prompt. `tests/conftest.py` points `keychain.SERVICE` at a service that never holds a key; `VAI_KEYCHAIN_SERVICE` does the same for a QA server. **Any process started with its own `WORKDIR` and no `VAI_KEYCHAIN_SERVICE` gets a namespaced item** (`"Video AI Editor (scratch <sha12 of the folder>)"`, `keychain._service_for`): only the packaged app and `./run.sh` (neither sets `WORKDIR`) touch the owner's real item. WHY: a lane's QA backend with a scratch WORKDIR fell back to the real item and `test_c3_settings_ui`'s Save wrote a fake key into the owner's login Keychain (wave D2); that test now also refuses to run its Save against an external server without a throwaway service and always deletes its item. **Windows has no Keychain:** Settings says so and `ANTHROPIC_API_KEY` stays the way to add a key there.

## Storage — the filesystem is the database

No DB. Everything is session-scoped under `WORKDIR/s_<hex>/` with fixed subdirs `uploads/ previews/ exports/ cache/ snapshots/` (`storage.py`). `storage.py` is path/meta plumbing; real state lives in `EDLStore`. Portable projects (`storage_project.py`): a `.vae` file is a ZIP of the state JSON + `media/` + `manifest.json` (caches excluded — they regenerate). `load_project()` **always creates a new session**, extracts media to `uploads/imported/`, and rewrites absolute `src` paths via the manifest remap — so importing the same `.vae` twice yields two independent sessions. **`_media_srcs` must collect `Sticker.src` as well as `Clip.src`** — it was `isinstance(c, Clip)` only, so no sticker PNG was bundled and none was remapped on load; the restored EDL still pointed at the *original* session's `uploads/stickers/` (and, for emoji, at a per-machine `user_cache_dir/emoji/…`). That resolves fine on the authoring machine, which is why it went unnoticed — but move the `.vae` anywhere else and every sticker's file is gone, and `text_overlay` skips a missing sticker **silently**, so the symptom is "my stickers just aren't there" with no error. **`save_project` also refuses on a corrupt session** (`store.is_data_loss_state`) — see the `load_state` bullet under State + persistence.

## HTTP API, MCP, async jobs — `main.py`, `api/`, `agent/mcp_server.py`

- `api/` has **no routes** (`api/__init__.py` is empty) — only `hardening.py` and `jobs.py`. `hardening.install(app)` adds a request-context middleware, a uniform error envelope `{error:{code,message,request_id}}` + `X-Request-ID`, a 60 rps/IP rate limiter, and hidden `/livez` `/readyz` (503 if ffmpeg absent) `/metrics`. An `HTTPException.detail` that is a **dict** lands under `error.details` (not `error.message`); a bare `ValueError` auto-converts to 400.
- **Async jobs:** uploads run whisper in a `BackgroundTask` (upload returns `transcript_pending:true`, fetched later via `GET /transcript`). Preview/export **and `/dispatch`** support `wait=0` → `202 {job_id}` polled via `GET /api/jobs/{id}` (`JOB_MANAGER`, in-memory). `wait=0` works for **any** tool, but `main.py::ASYNC_DISPATCH_TOOLS` (mirrored in `store.ts`, and a test asserts the two lists agree) names the ~10 that load an ML model and walk every frame — held on the sync path each pins a request-threadpool worker for minutes, which is the concrete mechanism behind the "app becomes unresponsive" reports (VAI-09/VAI-11). The job worker re-resolves the store via `_store(sid)` under `_session_lock(sid)`, since the LRU cache may have evicted and rebuilt it while the job was queued.
- **Stability guards, added in round 5 — don't undo them.** `/livez` is `async def` on purpose: a `def` endpoint runs on the bounded anyio worker threadpool every sync route shares, so a saturated pool made a healthy process report dead. `compositor._RENDER_SLOTS` (a `BoundedSemaphore`, `VAI_MAX_CONCURRENT_RENDERS`, default 2) wraps `_render` — the single chokepoint both preview and export pass through, and it never recurses. `_INFLIGHT` only collapses renders of the *same* EDL hash; N different hashes still launched N core-saturating ffmpeg processes. ffmpeg/ingest failures map to **422** with a stderr tail — `_render_failure_message()` pattern-matches the stderr tail for `st_/text_/sa_`-hash or `mask_*` overlay-cache filenames and substitutes a friendlier message than raw ffmpeg output. Missing/invalid `ANTHROPIC_API_KEY` only warns and disables the chat pane — the editor works without Claude.
- `GET /api/sessions/{sid}` includes `redo_available: bool` (mirrors the on-disk `redo_stack.json`, see the snapshot/persistence bullet above) so the UI can grey out Redo instead of guessing from local state. `add_clip`/`move_clip` raise `ValueError` (→ **400**, via the bare-`ValueError`-to-400 rule above) when a media `Clip` targets a non-video/audio-family track — see `_v_track_for_media()` under Frontend below.
- `DELETE /api/sessions/{sid}` removes a session dir. **`sid` is untrusted URL path input and is validated against `storage.is_valid_session_id()` (`^s_[a-zA-Z0-9]{6,64}$`) at BOTH layers** — the route 400s a malformed id before any filesystem op, and `storage.delete_session()` re-checks the id shape AND that the resolved path is a direct child of `WORKDIR` before `shutil.rmtree` (`_pu.rmtree_with_retry`, for Windows open-handle locking). Without this, a `sid` like `../../Documents` was an arbitrary-directory-deletion primitive. (Starlette normalizes `..` out of URL path params before routing, so it never reaches the handler through a browser — but don't rely on that; the storage-layer check is the real guard for any caller.)
- **Export** (`POST /api/sessions/{sid}/export`) takes `height`/`fps`/`crf`/`container`/`bitrate_kbps` (`ExportRequest`). **`height` is a NAMED resolution = the canvas's SHORT side** (`compositor.export_dimensions`, mirrored by `frontend/src/lib/exportOptions.ts`): "1080p" on 9:16 is 1080×1920 — it used to be the literal output height, exporting 608×1080 (QA-025). **`canvas.bitrate_kbps` (set by `apply_export_preset`) is honoured by the export encoder** as an average-bitrate target (`_target_bitrate_args`: `-b:v` with a 1.5× peak; VideoToolbox undershoots to ~70 % if the cap is pinned at the target), scaled down by pixel ratio for a smaller-than-canvas export; `bitrate_kbps: 0` in the request means "encode by crf" (the Quality selector's explicit pick). Before QA-027 nothing in render/ read it. The top-bar platform presets dispatch `apply_export_preset` (whole spec, overlays re-placed), not `set_canvas`. Output is MP4 (default) or MOV — both H.264/AAC via the same `mov` muxer, only the extension differs; `render_export`'s `container` param must be allowlisted (`in ("mp4","mov") else "mp4"`). `crf` IS honored on hardware encoders now (VideoToolbox `-q:v` via `_crf_to_videotoolbox_qv`, mapping the 0-51 crf scale onto its 0-100 higher-is-better knob; nvenc/qsv/amf best-effort onto `-cq`/`-global_quality`/`-qp`) — it used to be wired only to the libx264 fallback, making the UI Quality selector a silent no-op on Mac. The TopBar Export popover exposes resolution + quality + format; it portals to `document.body` (escapes `.topbar`'s overflow clip). **`CaptionsButton`'s language/speed menu needed the identical fix, and initially didn't have it** — built as a plain `position:absolute` child of `.cc-wrap`, which lives inside `.topbar`, so it was clipped to nothing the instant it opened. Reported as "there is only an Auto option" — all three real targets (English/Hindi/Hinglish) were present in the DOM and being sent correctly; the menu that offered them was simply invisible, the fourth time this exact class of bug has shipped in this toolbar (session picker, export options, TextTool's font popover, now this). Fixed the same way: portal to `document.body`, position computed in an effect from `getBoundingClientRect()`, and a `data-cc-menu` marker on both the trigger and the portaled content so the outside-click handler doesn't mistake a click inside the (now DOM-detached) menu for a click outside it. Verified with a real headless-Chromium check, not just code review: the menu's `parentElement` is `BODY`, its bounding box is genuinely non-zero (492×298 measured), and all three languages plus the two speed options are present and clickable.
- **Projects, stale windows, paste (wave B, lane B2).** `PATCH /api/sessions/{sid}` `{name}` renames (400 empty/>120 chars); a new project with no name is **"Untitled project N"** (`storage.default_project_name`), never its `s_…` id, and a `.vae` opened while a project of that name exists becomes **"<name> (opened <date>)"** (`storage.name_reopened_copy`). `GET /api/sessions` rows carry `modified_at`. **`/dispatch` takes an optional `base_hash`** — the EDL hash the caller's view was built from — and answers **409 `stale_edl`** (`error.details.edl_hash` = the current one) instead of applying an edit, or an Undo of someone else's edit, to a timeline that window is not showing (QA-105); checked under the session lock, and again inside an async job. - **Settings routes (wave C, QA-063-SETTINGS): `GET/POST/DELETE /api/settings/anthropic-key` and `POST …/test`** (`api/settings_routes.py`). Loopback-only (403 for a paired phone), **same-origin only** (`_same_origin`: `Sec-Fetch-Site` must be `same-origin`/`none` when present — a page on another localhost port, e.g. any other Vite project at :5173, sends `same-site` and gets 403; without fetch metadata a named `Origin` must equal the Host; the loopback peer check alone could not tell those pages apart — REVIEW-C3-KEY-CORS-5173; the Vite dev proxy rewrites Host (`changeOrigin`) but forwards the browser's `same-origin`, so dev still works; `main.py` installs the :5173 CORS allowlist only when not frozen), writes must be `application/json` (415 otherwise), `Cache-Control: no-store`, and **no response, log line or file ever carries the key** — status is `{configured, source: env|keychain|none|disabled, masked: "sk-ant-…WxYz", keychain_available, can_edit}`. The body is parsed by hand, never by a pydantic model, because FastAPI's 422 echoes the offending `input`. ## Phone pairing — gated OFF behind ONE flag (0.7.1), deliberately reversible

**`PHONE_PAIRING_ENABLED` in `api/pairing.py` is the single source of truth, and `pairing.phone_pairing_enabled()` is the only legal way to read it.** A module-level bool, `False` by default, `True` when `VAE_PHONE_PAIRING` is `1`/`true`/`yes` (case-insensitive). Read it through the **function**, never by importing the constant: the value is resolved from the environment at CALL time, because the suite flips the variable per test and an import-time snapshot would make those tests depend on import order — the same stale-at-import trap `config._BUILD_ID` documents.

0.7.1 ships the desktop editor as a standalone CapCut-style editor, so the iPhone companion and local-network pairing are **turned off, not removed** — a temporary shipping decision, reversible in one line. `api/pairing.py`, `api/pair_routes.py`, `api/auth.py`, `PhonePanel.tsx`, `tests/test_pair_auth.py` and the whole `mobile/` app stay in the tree with 0.7.0 behaviour; `mobile/` keeps its own 0.7.0 version on purpose (the iOS app is shelved, not shipped). With `VAE_PHONE_PAIRING=1` the behaviour is EXACTLY 0.7.0's. Why off: pairing is the one feature that needs a second device plus a cooperative Wi-Fi network before the editor can cut a single clip, and that is a poor first run for a desktop app. A future release flips it back rather than rebuilding it.

- **`GET /api/version` carries `phone_pairing: bool`** (from `phone_pairing_enabled()`), and that key is the **only** channel the frontend uses to decide whether the phone affordance exists — one flag moves the backend posture and the UI together, with no second switch to forget. `version` and `build` keep their exact meaning and types.
- **OFF means, concretely:** every `/api/pair/*` route answers **404** in the standard `api/hardening.py` envelope (`error.code == "NOT_FOUND"`, message saying the phone feature is not available in this build); `lan_enabled()` is `False` whatever `settings.json` holds; `set_lan_enabled(True)` refuses **without writing**; `auth_required()` is `False` unless the socket is genuinely bound public; `desktop.py` binds loopback regardless of the persisted setting.
- **A user's `settings.json` is never rewritten, cleared or migrated by the gate** — its `lan_enabled` value and every remembered device survive untouched and are honoured again the moment the flag is back. Turning the flag off is **not** an unpair, and a docs/flag change must never be a destructive migration of someone's state.
- **The third rung of the posture ladder above is untouched:** a request arriving on a non-loopback interface still arms auth and the path allowlist. A flag that could disarm authentication in front of an already-public socket would be a security regression wearing a shipping decision's clothes.

- **`init()` reconnects to a REMEMBERED session (`localStorage['vai.sessionId']`), not to whatever is newest on the server.** It used to be `list.sessions[0]` unconditionally — and `storage.list_sessions()` sorts by each session directory's own mtime, which ANY client sharing this backend can bump: an MCP tool call, a QA/automation script hitting the API directly, another browser tab. Found during a fix round that itself repeatedly rebuilt-and-relaunched the packaged exe while separately running verification scripts that each created their own session — every relaunch's `init()` picked up whichever of those had been touched most recently, silently swapping the actual open project out for an unrelated one with zero error or prompt. The visible symptom was someone else's leftover content (in this case, stale captions from an already-fixed bug) suddenly appearing after an ordinary edit, which read as a NEW bug in that edit when the real fault was `init()` handing back the wrong project entirely. Fixed by writing `sessionId` to `localStorage` on every change (`useStore.subscribe`, covers `init()` itself plus TopBar's switchSession/newSession in one place) and having `init()` prefer it when the remembered session still exists — falls through to the original "most recent on the server" behavior exactly as before when there's nothing remembered (first-ever launch) or it's gone (deleted). Verified with a real browser: after another client creates and touches a session that becomes the server's own `sessions[0]`, reloading the original page still reconnects to what it had open, not the intruder.
- **Engine connection + multi-window sync (QA-109/105).** `lib/connection.ts` is the ONE engine state (`online`/`offline`): `api.ts`'s `send()` turns a network failure — or a proxy's 502/503/504, or the Vite dev proxy's bare empty-body 500 — into `EngineOfflineError` and flips the state; a probe polls `/api/health` (under `/api` so the dev proxy forwards it) until the engine answers. While offline `store.dispatch()` refuses gestures locally with ONE notice per offline spell and `ConnectionBanner` stays up; on reconnect the store toasts once and refreshes. `startSessionWatch()` (mounted by App) asks `GET …/head` on focus/visibility and every 4 s and refreshes when another window changed the project; every dispatch sends `base_hash` (only when no edit of this window is in flight and no import is placing clips) and adopts the answer's `edl_hash` at once; a 409 `stale_edl` refreshes and says why. `refresh()` also prunes selection ids that are gone (QA-047) unless an edit landed while it was in flight (`mutationSeq`). **Exports** end on a job 404 ("interrupted — the engine restarted"), wait at most `EXPORT_LOST_MS` for an unreachable engine, and **Cancel closes locally at once** (run token `exportRun`) whatever the cancel request does (QA-034). **Imports** go through one queue (`enqueueImport`): every dropped/picked file gets a placeholder row at once (stage, %, ETA, Cancel — XHR byte progress then the normalise job's), files run one at a time in drop order, `uploading` stays true until the last one, and "Add imports to the timeline" (`importAddToTimeline`) off means library-only (QA-044/094/010).
- A single flat **Zustand store** is the source of truth and **never optimistically edits the EDL.** Every gesture and every Claude tool call funnel through `store.dispatch()` → `POST /sessions/:id/dispatch` → `refreshSoon()` (~120ms debounce) re-fetches and overwrites the EDL wholesale — the frontend mirror of the single-mutation-path principle. `dispatch()` tracks an in-flight counter (`state.pendingOps`) surfaced as a small "⋯ Applying" toolbar pill, and wraps the call in try/catch → `toast.error()` on failure — edits used to fail silently with zero UI feedback.
- **`Preview.tsx`'s `videoFingerprint` hashes the WHOLE per-clip object** on video/audio-family tracks (`{id, clips: t.clips}`), not a hand-picked field list — this is deliberate: `types.ts`'s `Clip` interface doesn't declare `speed`/`effects`/`transform`/`audio` (see below), so a field-enumeration fingerprint silently drifts stale every time the backend schema grows a new video-affecting property. This is what makes speed/color-grade/transform/volume/fade edits actually re-render the preview instead of committing to the EDL invisibly — mirrors how `edl.hash()` (the server render-cache key) hashes the entire EDL rather than a subset. Live transform preview (`liveTransform`, a pure CSS transform during a drag) is cleared on the `<video>`'s `onLoadedData` — i.e. once the NEW render has actually loaded — not eagerly on pointer-up, or the preview visibly snaps back to the pre-drag frame for the gap between commit and re-render; a bounded safety-net timeout force-clears it if the expected reload never lands (render failure/aborted fetch).
- **EVERY transparent overlay canvas must CLEAR IN DEVICE PIXELS, never CSS pixels.** The canvases size their backing store to `Math.round(cssSize * dpr)` and then draw under a `setTransform(dpr, …)`, so a `clearRect(0, 0, cssW, cssH)` only reaches `cssW * dpr` device px. At a **fractional** dpr those two differ, and the last device column and row are never erased — they keep whatever was painted there **forever**. Reset the transform first: `setTransform(1,0,0,1,0,0)` → `clearRect(0, 0, cv.width, cv.height)` → restore. This is the "phantom colour strip … when I hover them at the right side of the video", reported **four times** and surviving three wrong diagnoses (a GPU sampling artifact, the splitter's hover tint, the sticker being dragged half off-frame) because it is invisible wherever anyone looked for it: headless Chromium at dpr 1 cannot reproduce it. Measured in the packaged WebView2 window at dpr 1.25 — canvas cssW 914 → backing 1143 while the clear reached 1142.5, leaving accent ink (`#5b8dff`) in columns 1139–1142 that was **byte-identical** before a drag, after dragging right, and after dragging back, i.e. never redrawn, just never erased. Two follow-ons: fractional dpr is **not** Windows-only (125% scaling makes it routine there; a Mac on a scaled Retina mode hits it just as well), and fixing one canvas is not fixing the bug — `StickerLayer`, `TextLayer`, Preview's source canvas and Timeline's label/playhead canvases all needed it. The **only** exempt canvas is Timeline's main one, which repaints an opaque background over its whole area immediately after clearing.
- **The timeline canvases are VIEWPORT-sized, never content-sized** (`lib/timelineViewport.ts`, QA-024). A content-sized backing store (`contentW*dpr`) passed Chromium's 32,767 px canvas limit on a 12-min project at dpr 2, or an 85 s one at 600 px/s: the 2D context died, the track area went white and stayed white after zooming back. Now a `contentW` spacer (`contentRef`) gives the scroll extent, a `position: sticky` layer holds the main + playhead canvases at the visible pane's size, every draw runs in CONTENT coordinates under `contentTransform(dpr, scrollX)` and culls off-screen clips/tiles/waveform columns, and every pointer handler measures against `contentRect()` (the spacer), not the canvas. A redraw is flushSync'd from the scroll event so the slice never lags the scroll.
- **A render swap must not blank the preview** (`Preview.tsx` `freezeRef`, QA-005). Changing `<video src>` shows nothing until the new file decodes (measured: a fully black frame after most edits in Chromium). A store subscription copies the on-screen frame into a cover canvas the instant `previewHash` changes — before React re-renders the src — and the cover drops on the new render's restore `seeked` (else `loadeddata`), 4 s net.
- **`TextLayer`'s draw loop needs a time source that survives v1 being EMPTY, and only `StickerLayer` had one.** Both layers sample "what time is it" every rAF tick to decide which overlay clips are active (`c.start <= t <= c.end`); with a v1 clip present that is simply `videoEl.currentTime`, read live off the `<video>` element. But delete the v1 clip and `videoEl` is `null` — there is nothing to poll — and `TextLayer` fell back to a **hardcoded `0`**. `c.start <= 0 && 0 <= c.end` is true for every clip whose `start` is at or near 0, generally one per overlay track (a caption cue, a hook, a super…), and since `t` never moves off 0 no matter where the scrubber sits, every one of those stays drawn and stacked forever — reported as garbled, overlapping caption text over a black frame the moment the main video was removed. **`StickerLayer.tsx` already had the fix** (`videoEl ? videoEl.currentTime : useStore.getState().playhead`), just never applied to its sibling. `getState()` rather than a subscribed prop is deliberate: `draw()` self-perpetuates via `requestAnimationFrame` and is NOT re-created on every store change (unlike most of this file's components), so a captured prop value would go stale immediately — an imperative read is what stays live inside a closure that never re-runs.
- **A ROTATED v1 clip previews from the RAW SOURCE, not from CSS over the last render** (`lib/sourcePreview.ts`, gated by `sourcePreviewApplies`). v1 rotation is baked **in place**, which genuinely destroys the corners — 27.5% of the picture at 61° — so once a clip is committed at an angle, no CSS transform of that render can recover what was cut, and dragging the slider back toward 0 showed a progressively more cropped picture that only healed on release ("the video got cropped from the rotation, this happened when my cursor was holding at 0 degree"). Drawing from the untouched source is the only thing that can be correct mid-gesture. The trade is explicit: during that drag the picture is the **ungraded** source (no effects/LUT), which is why it is scoped to v1, non-`cover`, non-keyframed, and only when the clip's committed rotation is already non-zero.
- **Chat streaming is SSE-over-fetch, hand-parsed in `ChatOverlay.tsx`** (not `EventSource`, because it's a POST): reads `res.body.getReader()`, splits on `\n\n`, JSON-parses each `data:` line. On an `op` event it `refresh().then(renderPreview)` — the bridge that makes Claude's edits appear.
- **`FrameScrubber.tsx`** is a WebCodecs pipeline (mp4box.js demux → `VideoDecoder`, bisect to keyframe) for frame-accurate scrub, with an automatic hidden-`<video>` fallback from five distinct failure points. The playback clock is a rAF wall clock (migrated off `requestVideoFrameCallback`) so the playhead keeps moving even on render failure. **The clock only follows `<video>.currentTime` when it moves in the play direction** — a mid-playback edit reloads the `<video src>` to the new render's URL, resetting `currentTime` to 0 even though the wall-clock-tracked playhead is still mid-timeline; naively following any change (regardless of sign) yanked the playhead backward-then-forward-from-zero. A `resyncing` flag ignores the video clock until it's caught back up within a tolerance of the wall clock (the existing playhead-sync effect actively seeks the reloaded video to the right spot, so this converges in ~1 frame). `onTimeUpdate` is gated to only drive `playhead` while paused, for the same reason (it fires independently of the rAF loop and would otherwise race it).
- **The scrubber canvas is TEMPORARY, so every frame it paints is a promise about what the `<video>` will show when it fades out.** The canvas covers a paused seek and then hands the picture back; if the two disagree, the picture visibly jumps a beat after the gesture — reported as "the video stutters just a little bit after I pause, and the same when I move the playhead". Measured with a fixture whose frame N is a flat grey of luma N (so the displayed frame index is readable from the pixels) plus a rAF recorder sampling the visible element: **canvas frame 165, `<video>` frame 163**, on every paused seek and every single-frame step. Three separate causes, all of which had to go:
  - **The walk assumed decode order == presentation order.** mp4 sample tables are in DECODE order while `cts` is COMPOSITION time, and the preview is libx264 with its **default B-frames** (verified on a real preview: `has_b_frames=1`, `pict_type=B`), so a GOP arrives as `I P B B P B B…`. The old walk stopped at the first sample whose `cts` passed the target — in that stream the P frame that *displays* two or three frames later — and stopped **before feeding the B frames that actually cover the target**. Even with no B-frames it deliberately included "the first sample whose cts > target … (closest match)", which is +1 frame. `<video>.currentTime = t` shows the frame whose interval CONTAINS t, so the correct rule is **the greatest `cts` ≤ target**, decoding every sample from the keyframe up to it (the ones above the target in that span are references the covering frame depends on — decode them, never paint them). The rule is pure and unit-tested in **`lib/frameWalk.ts`**; the decoder's output gate now paints on an exact `paintUs` match (±2µs) instead of "covers-or-follows", because a covers-or-follows gate paints every frame from the target onward and the decoder emits in presentation order, so the *last* one won. **That exact gate carries one deliberate safety net**, because it is the only claim in the scrubber that cannot be measured on the engine it matters most for: WebCodecs *requires* a decoded `VideoFrame.timestamp` to echo its `EncodedVideoChunk`'s, Chromium does, and WKWebView is unverified — while the cost of being wrong is asymmetric, since an unmatched gate paints **nothing** and leaves a blank canvas over an otherwise correct `<video>`. So a `painted` flag (reset per seek, alongside `paintUs`) lets the first frame arriving *past* the target paint when the exact match never landed: presentation order makes that frame proof the match is not coming, and painting it degrades to the pre-existing covers-or-follows behaviour (≤1 frame late) rather than to blank. On a conforming decoder the exact branch always fires first, so it is unreachable — re-measured on the frame-numbered ramp fixture after adding it: pause/seek/step/drag all still settle with canvas and `<video>` on the SAME frame (22/22, 163/163, 164/164, 144/144) and zero frame changes after settle.
  - **The `<video>` seek was skipped for small moves.** The defer threshold was 0.05s while a frame at 30fps is 0.033s, so a single-frame step queued no seek at all: the canvas showed the stepped frame, then hid 250ms later and revealed the `<video>` still on the original frame — the step undid itself (`currentTime` never moved for the whole gesture). The threshold is now a **quarter frame** of `edl.canvas.fps`.
  - **The pause transition scrubbed to the pre-pause playhead.** `justPaused` deliberately pulls `playhead` FROM the video (so the pause itself doesn't rewind), but the scrub block in the same effect run then seeked the scrubber to the stale `playhead` in its closure — the canvas faded up on the frame BEFORE the one on screen and faded back 230ms later. Measured: stopped on 55, canvas showed 54, back to 55. A pause now takes no canvas at all (the `<video>` is already displaying the right frame — there is no seek to hide), and neither does any move smaller than a quarter frame, including the `<video>`'s own settle echo, which `onTimeUpdate` also drops for the same reason (writing the echo back counted as a playhead change and stood up a whole uninvited reveal ~250ms after the user stopped).
- **On v1, a clip's `start` is NOT where it plays — `Timeline.tsx` draws OUTPUT positions** (`lib/timelineLayout.v1Layout`, a pure function mirroring `EDL.transition_overlap()` rule for rule). `xfade` overlaps two clips, so every clip after a transition plays *earlier* than its `start`, and the canvas drew them at raw `start * zoom`. Reported as "the video duration is 8 sec, yet it plays only up to 7 sec": on the real session (8s split at 2/4/6, transitions at 2.0 and 4.0 → renders 7.0s) the strip was drawn out to 8.0s, so the last second was unreachable — and worse than that stray tail, **every clip after the first transition sat up to a second right of its picture**, putting the playhead over clip 3 while the preview showed clip 4. Four things follow, and they must move together:
  - **The hit list and the draw loop use the same shifted `start`**, or clicks select a clip other than the one under the pointer — they already shared this bug's mirror image for speed-adjusted clips.
  - **The seam affordance is drawn at the MIDDLE of the overlap** (`seams[].outAt = boundary - cumulative - overlap/2`), which degrades to the exact cut position when there is no transition. Its `at` stays EDL time, because that is what `add_transition`/`remove_transition` are called with.
  - **The overlap WARNING is tested against EDL positions, never the drawn ones.** Under a transition the drawn rects overlap *on purpose* — that is what a cross-dissolve looks like — so testing the drawn values flagged every transition as corrupt data with the dashed outline meant for genuinely broken clips.
  - **Pointer→time for a tool argument needs the inverse** (`edlTimeFromOutput` for v1). A drag commits a *delta* so it is immune, but dropping new media onto a v1 lane that already has transitions would otherwise land it earlier than the pointer by the accumulated overlap. **Overlay lanes are NOT the identity** — that was the second half of this bug (2026-09): the renderer positioned captions, text, stickers, PiP, music and voiceover in raw layout time (`enable='between(t,start,end)'`, `adelay=start*1000`) while v1 was pulled left, so after 12 Zoom In transitions on a 71.86 s timeline (renders 69.46 s) every overlay and the ducked music bed drifted up to 2.4 s late against the picture and speech. The one truth now is `render_time(t) = t − Σ{d_i : seam s_i ≤ t}` over the v1 transitions the renderer actually applies (`lib/timelineLayout`: `seamTable`/`v1SeamsOf` → `renderTime`/`renderWindow`, mirroring `EDL.v1_seam_table()`): **every lane is drawn and played in render time** — `Timeline.tsx` draws overlay clips at `renderWindow(start, end)` via `drawnSpan`, and the live preview's `TextLayer`/`StickerLayer` test activity with `renderWindow` and run keyframes and a PiP's media offset from `renderTime(start)` (the seam table is computed once per EDL, never per frame). A window is `[render_time(start), render_time(end))`; a zero-or-negative mapped window (an overlay wholly inside a consumed span, e.g. exactly clip A's crossfaded tail) is **dropped**, never inverted — not drawn in the preview, drawn as a flagged sliver on the Timeline so it can still be dragged out. **Overlay drags decode back through `layoutTime`** (the inverse): a drop inside a crossfade window snaps to the seam's layout time, because `render_time` is not injective there and the seam is the only answer that does not silently pick one clip's side. The playhead/ruler are already render time and must NOT be converted. Layout time stays the EDL's coordinate space — nothing in `edl/`, `dispatch.py`, `timemap.py` or the mobile app moves; only the renderer and the desktop's drawing/write-back convert. **Every "at the playhead" write-back decodes first**: TextTool/StickerPanel/`add_marker` store `layoutPlayhead(edl, playhead)` (markers are layout time like every other EDL field and are drawn at `renderTime`), ⌘B / "Split at playhead" go through `lib/splitTargets` (v1 through `v1TimeFromOutput`, overlay lanes through `layoutTime`), and Properties' keyframe/transform `time` is `clipLocalTime` — clip-local time measured from where the clip PLAYS (`renderSpanOf`: v1 `start − shift`, overlays `renderWindow`), the same origin TextLayer's `animEnvelope` (render window) and StickerLayer's `renderLocal` use. **The compositor consumes the seam table, it does not re-derive it**: `_build_filter_complex` takes the cost of each xfade from `seam_table_for(clips, transitions)` (the body of `EDL.v1_seam_table()`) and only the look from the first matching record; it used to keep its own matcher (last record won, raw duration, no clamp to the shorter clip) and every disagreement was the picture running ahead of the overlay lanes with the video stream ending before the audio. `Transition.duration` is normalised in the schema (below 0.1 s → the look's default, on construction, load and assignment) and `add_transition` caps at 2.0 s and the shorter neighbour, so no EDL carries a number the renderer will not use. The v1 assembly pads its trailing filler to the LAYOUT end (`edl.duration + transition_overlap()`), not `edl.duration`.
  The EDL is deliberately left alone: rippling the stored starts would make clips overlap in the data, tripping `_first_free_gap`, `_repack_media` and the overlap warning, all of which correctly assume v1 is a non-overlapping sequence.
- **`Timeline.tsx`'s `<canvas>` is sized to the full timeline CONTENT (`contentW`/`contentH`), not the viewport** — `.timeline-canvas-wrap` is `overflow:auto` and genuinely scrolls it; a separate small canvas draws just the track-label column and is kept pinned via a manual `wrapRef` `scroll` listener setting `label.style.transform = translateX(scrollLeft)` (CSS `position:sticky` doesn't work here — the label needs to overlay the main canvas's rows, not stack after it in flow). `contentH` is **content-only** (`headerHeight + tracks*(rowH)+…`), NOT `Math.max(size.h, …)` — clamping to the viewport height made `wrap.scrollHeight <= clientHeight` even when rows genuinely overflowed, defeating vertical scroll. **The wheel handler is a native `addEventListener('wheel', …, {passive:false})` effect, NOT a JSX `onWheel` prop** — React attaches wheel/touch listeners passive by default, so `preventDefault()` inside a JSX handler is a silent no-op (Chrome logs "Unable to preventDefault inside passive event listener"), which broke the `⌘`-zoom guard too. - **`StickerLayer.tsx` is the interaction layer for EVERY canvas overlay, not just stickers** (the name is historical). Text and stickers must select/drag/resize identically — text had no on-canvas handles at all until round 5 (M-01). The split is by *ownership*: `TextLayer.tsx` is the only place that measures and wraps a text string, so it publishes each active clip's measured box into `lib/overlay`'s `publishTextBoxes()` registry each frame, and `StickerLayer` hit-tests those boxes with the identical code path as a sticker's. Live drag flows the other way through `setOverlayDrag()` — module-level mutables, **not** React state, because both are rAF loops and routing a 60 Hz drag offset through `setState` would re-run TextLayer's whole draw effect every frame. **A published text box is already LIVE and must not be adjusted again by the consumer**: TextLayer reads that same override to draw its glyphs, so the move offset and resize multiplier are folded in before publishing. `StickerLayer` re-applied both, so the chrome travelled at *double* the pointer distance — visibly detaching upward from the text it framed ("when I drag the text, the text box gets outside of the text") — and inflated by mul² on a resize. The commit reads `d.live.*` rather than the box, which is why the text still landed correctly and only the box lied. TextLayer is the right owner because a live resize RE-WRAPS the string: line breaks can change, so the true box isn't a uniform scale of the old one and can't be reconstructed downstream. Cost is ≤1 frame of chrome lag; being 2× wrong was not a cost worth paying to avoid it. Handle sizes and the chrome drawing live once in `lib/dragVisuals.drawSelectionChrome`. Two things a text box deliberately does NOT get: **captions** (position is owned server-side by the captions block, so a drag would commit an x/y the renderer ignores — a control that does nothing is worse than none) and **keyframed x** (one drag can't express a curve). A text resize commits `set_property style.size`; a sticker resize commits `set_clip_transform scale`. `StickerLayer` also **paints the sticker pixels themselves every frame** (not just chrome) — see the preview-baking bullet under Render pipeline for why that ownership is load-bearing rather than cosmetic.
- **A dropped overlay must keep being drawn at the committed position until the EDL comes back carrying it — and that hold is needed SEPARATELY in each layer.** A commit is not instant: `dispatch` → ~120 ms `refreshSoon()` debounce → `GET /edl`. Clearing the live override on pointer-up redraws from the STORED coordinates for that whole window, so a drop visibly bounced back to the pick-up point and then jumped forward ("the emoji goes back to the place from where it was picked up and then comes to the place where I placed"). It is not a render cost and will not "just get faster". `lib/overlay.resolveLiveOverride()` is the one rule — live gesture, then the committed-but-unconfirmed drop, then stored — and `dropSettled()` decides when the wait is over, with tolerances because the commit ROUNDS (an exact compare never settles and would pin every drag to the timeout) and a deliberate `false` on a keyframed value so the **bounded** 2 s safety net resolves it instead. That timeout is load-bearing: a permanently wrong position is far worse than the flicker being fixed. Preview.tsx's `liveTransform` (cleared on the `<video>`'s `onLoadedData`) is the same lifecycle for a v1 clip. **The trap: `setOverlayDrag()` is TextLayer's channel, NOT a general live-position mechanism.** Fixing only that leaves stickers broken, because `StickerLayer` resolves sticker geometry itself and read its own `dragRef` in *two* places (the hit-test box and the paint loop) — so the first version of this fix verified fine on text and changed nothing for the sticker actually reported. Each layer owns its own draw math, so each must consult `resolveLiveOverride` itself. Measured on the packaged build with a per-frame centroid sampler over the overlay canvas: dragged to x=287, **back to x=190 for 18 frames (274 ms)**, then forward to x=285 — matching the 233 ms measured off the user's screen recording. Two follow-ons: the held sticker stays hoisted in `paintOrder` (its z is raised by the very commit being waited on, so dropping to stored order mid-hold would make it dive under a neighbour and pop back), and a move must not leak `scale` nor a resize leak `x`/`y`, or a field the gesture never touched gets pinned and `stickerGeom`'s `?? sampleKF()` fallthrough is defeated.

The v2 sentinels that depended on canvas and role (`canvas.w/2`, `canvas.h*0.85`, the role anchor, font `"Inter-Black"`) are gone — a typed Y of 918 on 1080p used to snap to the anchor while 919 did not, and Inter Black could not be picked — and `EDL._migrate_v2` rewrites a v2 project on load into exactly what it rendered. TextLayer publishes the remaining per-axis sentinel on each box and the inspector nudges a typed 540/1700 by a pixel (`lib/textLayout.offAxisSentinel`).
- **Lane/clip-type validation lives in `agent/dispatch.py`, not just the frontend.** `_v_track_for_media()` rejects `add_clip`/`move_clip` targeting a non-video/audio-family track (a media `Clip` parked on e.g. the captions track used to succeed silently at the data-model level, then vanish from every render since `collect_text_clips`/`collect_stickers`/etc. each only look at their own track type) — `move_clip` only applies this when the clip being moved `isinstance(c, Clip)`, since a `Sticker`/`TextClip` legitimately moves between two tracks of its own kind (e.g. `tx_super` → `tx_hook`). The Timeline drag/drop handlers duplicate this check client-side for immediate feedback (`toast.error`), but the backend check is the real enforcement — Claude/MCP callers bypass the frontend entirely.
- **`move_clip` also snaps to the nearest free gap to prevent silent time-overlap** (`_first_free_gap()` in dispatch.py, mirrored client-side in `Timeline.tsx`'s drop handler). Dropping a clip onto a track where it would overlap an existing clip's time range used to be allowed with no check — the two clips then drew with identical fill and no z-order cue, reading as "merged/broken" (no data was lost; both clips survived). Now the dropped clip snaps its `start` to the first free gap on the destination track; a dashed-outline draw in the canvas loop is defense-in-depth for any still-overlapping (legacy) clips. **`move_clip` takes an opt-in `close_gap`** which, after the move, repacks the sequence so the vacated slot closes (`_repack_media`). The Timeline drag passes it (a drag means "reorder": dragging clip 1 to the end otherwise left a hole at 0s and simply made the timeline longer); Claude/MCP callers don't, because they place clips at absolute times and must not have neighbours shuffle underneath them. **Exception — a same-lane v1 move without `close_gap` onto an occupied slot is REFUSED (400, names the blocking clip), never snapped (QA-022):** v1 clips butt end to end, so the forward snap turned a one-frame Alt+→ nudge into a teleport past the last clip (10.005 → 40.02 s, a 10 s black hole) and a left nudge into a silent no-op. The keyboard nudge is planned client-side in `lib/nudge.ts` (one frame of the project rate; refuses with a toast when a neighbour is in the way, on every media lane).

One over a gap in v1 or past v1's end keeps its time; a layer the tool names is its own edit. The per-tool helpers (`_ripple_overlays`, `_shift_overlays_after`, `_retime_overlays_over`) still decide the layers over the EDITED picture (trimmed away, retimed, orphaned, dropped).

Known gap: the Timeline drag of a linked cue still decodes through `layoutTime`, exact except inside a crossfade window.
- **`close_gap` is V1-ONLY, and it closes the lane the clip LEFT — three distinctions that each had a bug on the wrong side of them.** The gate was `track.type == "video"` and ran after `track` had already been reassigned to the destination, so:
  - **It repacked the wrong lane.** A v1→v2 drag closed gaps on **v2** — shuffling clips the user never touched and pulling the dropped one straight back out of the slot it was dropped in — while the real hole sat open on v1, holding `edl.duration` at the old length. Origin and destination coincide for a same-lane move, which is why it read as correct. Now: cross-lane closes the **origin** and leaves the destination exactly where it was dropped (a drop onto another lane is a *placement*; `_first_free_gap` already keeps it off other clips), same-lane reorders.
  - **It repacked v2.** `type == "video"` matches v2, whose clips are *not* a sequence — `render/pip.py` floats them over the composite at absolute times, so packing them from t=0 is the same damage `test_set_speed_on_v2_pip_keeps_every_placement` pins down (deliberate 8.0/20.0 placements collapsing to 0.0/2.0). The gate is now `id == "v1"`, the one lane where clips follow one another. Every other lane holds elements positioned *against* v1's picture — a caption's start is a coordinate, not a slot, and so is a PIP's.
  - **A reorder could not move a clip LEFT.** `_first_free_gap` ran first and walked *forward* past the very clips the drag was jumping, so dragging the last clip to the front returned it bit-for-bit to where it started, the repack re-derived the original order, and the drag did nothing — while the UI announced "Snapped to the nearest free gap" for it. **Landing on an occupied slot IS the reorder gesture**, so the snap is skipped when `close_gap` is set on a same-lane v1 move; `_repack_media` assigns the real positions, breaking a start-time tie in favour of the dragged clip (`prefer_first`) so a drop onto clip 1 inserts *before* it instead of re-deriving the order. **The ordering rule is "the dropped clip's LEFT EDGE against the other clips' starts"**, and it is implemented three times — `_repack_media`, `dragResolve.reorderLanding` (the drag preview), and the drop handler's decision to skip the snap — so they must move together or the landing line goes back to promising an outcome the backend won't produce.
- **Text overlays on a track REPLACE on temporal overlap, they don't stack** (the "double subtitle" fix). `add_super_text`/`add_text` remove any existing same-role clip on the same track whose `[start,end)` overlaps the incoming one, then append (opt out with `allow_stack:true`). An earlier fix only deduped EXACT matches (same text AND same start/end), so two clips with different text ("RIPPLE TEST" vs "RIPPLE TEST 2") at the identical time both survived and `TextLayer.tsx` (which has no collision handling) rendered them stacked. The fix is forward-only — it does NOT retroactively clean EDLs already carrying stacked duplicates; resolve those with an explicit `ripple_delete`, never a silent load-time mutation.

## Framing (crop/reposition) — the crop window is the OUTPUT FRAME

`CropReposition.tsx` mounts over the preview when the selected v1 clip is `fit: 'cover'`. Its geometry lives in **`lib/cropLayout.ts`**, a pure function, because every bug in it was a sign or derivation error that a unit test catches instantly and a screenshot does not.

- **The window never moves and never resizes; the PICTURE moves and scales.** Both faults came from the opposite arrangement. Pinning the picture meant showing the same crop required sliding the window the *other* way, so dragging right sent the yellow rectangle left ("the framing panel moves opposite to the mouse"). And deriving the layout zoom from the *current* scale (`fitScale = min(paneW/scaledW, …)`, which divides by scale) shrank the window as you zoomed instead of enlarging the footage — read as "there is video behind the framing which gets bigger". `winScale` is therefore derived from the **scale-1** cover size and is independent of `scale`.
- **`+x` moves the picture RIGHT, matching `compositor.py` exactly** — its cover pan is `crop=…:'(in_w-out_w)/2 - x':'(in_h-out_h)/2 - y'`, and moving a crop window left by x *is* moving the picture right by x. Keeping the same sign on both sides is what makes the live drag and the bake agree; an inversion here has to be hand-maintained against a filtergraph and will drift.
- **`SCALE_MIN` is 1, not 0.1, and that is a render contract.** The cover-with-pan branch applies `extra_zoom = max(1.0, scale)` because a sub-1 zoom shrinks the frame below the canvas and `crop` then renders **solid black with no ffmpeg error**. Offering 0.1 in the UI let the view show a picture the renderer would never produce.
- **`.preview-pane video`'s `max-width/max-height: 100%` must not apply to it** (`video.crop-source` opts out). That rule is right for the composited preview and wrong here, where being bigger than the pane *is the point*: it clamps per axis, so a 2× zoom rendered a 715px-wide element at 349px with height left at 402px — the picture squashed sideways instead of growing.
- **x/y are CLAMPED to the margin ffmpeg will honour** (`clamped`/`limit` from `cropLayout`, and the drag commits `clamped`, not the raw pointer total). `crop` pins its x/y into `[0, in_w-out_w]`, so past the margin the bake silently ignores the rest while the view kept sliding the picture and painting black. Worst case is a source whose aspect **equals** the canvas — a 9:16 phone clip on a 9:16 canvas, the most common upload — where both margins are 0 at scale 1 and *every* drag was a no-op in the render. Measured: on a 1920×1080 source over a 1080×1920 canvas, `y=400` and `y=-978` both rendered byte-identically to `y=0`. The badge says "Zoom in to reposition" rather than printing a number that does nothing.
- **The view mirrors `extra_zoom = max(1, scale)`, but only when panning** — because the renderer itself splits: the cover-with-pan branch clamps a sub-1 zoom (it would leave `crop` with less input than output and render solid black), while the no-pan path applies the scale exactly and pads. A clip stored with `scale < 1` is still reachable (the Properties slider allows 0.1, as do Claude/MCP), so drawing the raw value showed a half-size picture with black inside the yellow frame.
- **The view is withheld when x/y/scale is KEYFRAMED** (`showReposition` in `Preview.tsx`) and renders `null` when the source's dimensions can't be probed. It reads only scalar transforms, so an animated pan drew as if centred, and one drag would `set_clip_transform` the whole keyframe list away — the same "one drag cannot express a curve" rule StickerLayer applies to text. The dims-`error` branch previously neither set dims nor retried, leaving an opaque black div over a working preview with no way out but deselecting; that also split by platform, since a codec WKWebView decodes can fail in WebView2.
- **The raw-source `<video>` seeks on `onLoadedMetadata`, not only from the effect.** On first mount `readyState` is 0 (the element is created in the same commit), and since the view only opens while paused none of the deps changed afterwards — so the source sat at time 0, a different moment than the composited preview the user was looking at, and they framed against the wrong footage.

**Rotation is IN PLACE on v1** (`rotate=<rad>:c=black`, no `ow`/`oh` override). It used to expand to the rotated bounding box and scale that back down to fit, so nudging a clip 3° to straighten it visibly zoomed the whole shot out — and `Preview.tsx`'s live preview is a CSS `rotate()`, which rotates in place, so the picture jumped size the moment the value committed ("while rotating the preview is correct, but when the changes are made the preview gets changed"). `pip.py` deliberately still expands (`c=black@0`, `ow=rotw`): a PIP element floats over the composite and has no frame to be cut off by.

**Unticking "Fill frame" resets `x`/`y`/`scale`** (`set_clip_fit`, cover → contain only). Those are a crop-window pan that means nothing under `contain`, where they instead translate an already-letterboxed picture and crop the far edge — so the control was not an undo of itself ("the video gets cropped, but doesn't come to its original aspect ratio"). **Two gates gate the reset, both found by review after the first version shipped without them:**
- **v1 ONLY.** `fit` is read exclusively by `_build_clip_video_chain` (the v1 base layer); `render/pip.py` never looks at it. On a v2/PIP clip `x`/`y`/`scale` are the on-canvas **placement**, so the reset turned a toggle that renders *nothing* differently into a silent teardown of the PIP layout — a bottom-right PIP jumped three-quarters off the top-left corner.
- **Nothing keyframed on ANY of the three**, not each guarded independently: they are coupled. Zeroing a scalar `scale` while a keyframed `x` survives leaves the pan no headroom (the animated branch emits `scale=<canvas>*max(1,1.0)`, so `iw` equals the canvas and ffmpeg clamps the pan expression to 0) and the authored animation renders motionless. Preserving a keyframed value while destroying what makes it visible is not preserving it.

Known trade-off: the reset is to **identity**, not to whatever the transform was before cover was entered — so ticking and unticking to compare also discards a zoom the user had set while in `contain`. Restoring the pre-cover values would need that state stored on the clip.

## Why the chat agent "gets confused" — the mechanical causes

Reports of the assistant losing the thread were mostly two structural faults in `agent/loop.py`, not model behaviour:

- **A tool result must stay VALID JSON when it is bounded.** It used to be `json.dumps(result)[:8000]`, which slices mid-structure — an unclosed string, half a key. `get_timeline` on a 40-clip timeline was ~11.4k chars, so what reached the model simply stopped mid-document; asked to reason over that it reports confusion or invents the missing half. `_tool_result_json()` now wraps an oversized payload in a labelled envelope (`_truncated`, `original_chars`, `preview`) that parses. Re-encoding escapes quotes and backslashes, so the envelope is longer than the preview it holds — it shrinks in a loop until it genuinely fits rather than assuming a fixed allowance.
- **`get_timeline(summary=True)` is capped at `MAX_SUMMARY_CLIPS` per track**, keeping the common case inside that budget instead of relying on the truncation. It keeps the head and the last 5 clips with an `_omitted` marker between them, because positional reasoning needs the boundaries, not the middle of a long strip. `clip_count` always reports the true number.
- **Running out of `max_turns` must not end in silence.** The loop used to fall out of `for turn in range(max_turns)` with no closing text — the user saw a run of tool calls and then nothing, which reads as the assistant giving up — and left `history` ending on a `user` tool_result, so the next message appended a second consecutive user turn and the API rejected the conversation ("roles must alternate"). That is the same wedge the credit-failure path guards against, reached from the other direction. The `for/else` now emits an explanatory message AND closes the history on an assistant turn.

The live-context block (`_live_context_block`) was already bounded at 12 clips per track — that one was fine.

## Transitions — `render/transitions.py`

Three kinds of entry, and picking the wrong one is how a name ends up promising a motion the engine cannot perform:
- **NATIVE** — one of ffmpeg's 58 xfade transitions. All 58 are exposed; there are no more to find.
- **CUSTOM_EXPRS** — `xfade=custom` with a per-pixel expr. It can express any **mask** (shape, band, hash, luma key) but **cannot sample another coordinate**, so no zoom, rotation or smear. Both `if(cond,B,A)` and `A*(1-k)+B*k` are plane-safe; anything that mixes A and B unevenly per plane shifts colour.
- **POST_FILTERS** — a real filter on the xfade **output**, gated with `enable='between(t,…)'` to the transition window. The only way to get motion blur, which is what makes a whip pan read as one. Sigma scales with the **axis being smeared** (`WHIP_SIGMA_RATIO`), never a fixed pixel count — preview and export render at different resolutions, so a constant would smear the preview harder than the delivered file.

**A transition SHORTENS the timeline, and `EDL.duration` has to say so.** `xfade` plays both clips at once for its duration, so each applied transition removes exactly that much from the output — `compositor.py` has always tracked it (`cur_dur = cur_dur + seg_dur[i] - tdur`) and the EDL never did. An 8s timeline split at 2/4/6 with three 0.5s transitions **renders 6.5s** while the header badge, the timeline and the transport denominator all still said 8.0, so playback stopped early with a dead tail and no explanation ("the 8 sec video got stopped at 7 sec"). `EDL.transition_overlap()` now models it and `recompute_duration()` subtracts it; verified against the real renderer, preview and export both land on 6.500s exactly. It **mirrors the renderer's applicability rule**, because charging for a transition that never renders is the same bug pointing the other way: only a boundary between two **adjacent** clips (a gap becomes black filler and the renderer leaves that seam a hard cut), the same 0.05s boundary tolerance, one charge per seam (`seg_trans` is keyed by segment index, so a legacy stack at one cut still renders once), never more than the shorter clip can give, and **v1 only** (`render/pip.py` never looks at transitions). `EDL.video_duration()` deliberately does NOT subtract — it answers "where does v1's content end", which is where the next upload gets appended; subtracting there would append the next clip *on top of* the last one. No transitions → overlap 0 → every existing timeline's duration is unchanged. `add_transition` reports the change in its summary (`timeline 8.00s → 7.50s`), because a tool that silently shortens the video is the most surprising one in the app.

**ALIASES are synonyms, not effects.** `catalog()` publishes `looks` and `count` separately: a single combined number read as "88 transitions" when a third were synonyms (`mosaic` = `pixelate` = `pixel` = `pixelize`), so a tester working through the list found repeats and reported the catalogue as padded. Two rules a test now enforces: no alias may share a name with a real look (the resolver checks customs first, so it would silently shadow it — this happened to `blinds`), and every look must appear in some `CATEGORIES` entry, since `list_transitions` is the only discovery surface. **`list_transitions` repeats `looks`/`alias_count`/`note` at the TOP level, not only inside `catalog`** — `count` (105 accepted names, 72 looks) sits at the top of the result and is the number a reader actually quotes, so the honest split has to live where the padded one does.

`spin` used to resolve to `radial`, a clock wipe with no rotational motion, and `whip` to `smoothleft`, a soft slide with no blur — both named a movement that never happened. `zoomout` still maps to `circleclose` because a true zoom needs coordinate sampling; its description says so rather than pretending.

**`add_transition` REPLACES any transition within 0.05s of the same cut** instead of appending. The compositor keys transitions by seam, so a second one at the same boundary never rendered — it just accumulated in the EDL, which then disagreed with the picture. Same rule the text overlays follow. `remove_transition` still sweeps *all* entries near a cut, because legacy projects and MCP callers can still hold stacks. **`TransitionPopover` exposes Remove**, but only when the cut already has one — removal was otherwise reachable only through chat/MCP, so a transition added by a mis-click had no way back but Undo. It sits at the far left of the action row (`margin-right:auto`), deliberately not adjacent to Update, since it is the one destructive control there.

## Feature availability — `ai/features.py`, `check_features`

Every optional capability has its own `available()` probe, but until round 8 nothing aggregated them and **nothing exposed them to the chat agent**. With no way to look, Claude invented diagnoses: it told a user to run `uv add noisereduce soundfile` for a noisereduce that was installed and working, and reported vocal isolation as "not installed" when demucs, torch and the model were all present. `check_features` returns, per feature, whether it works here and the exact fix if not; `SYSTEM_PROMPT` requires calling it before claiming anything is missing and forbids composing install commands by hand. Probes must be cheap (import-spec + file existence, never a model load) and must never raise — a probe that throws on a machine missing a dependency takes the diagnosis down with it.

**A tool raising is not evidence its dependency is absent.** `vocal_isolate` failing on Windows was `python -m demucs.separate` loading audio through torchaudio → torchcodec, whose `libtorchcodec_core*.dll` links against ffmpeg's **shared** libraries — Windows installs a static `ffmpeg.exe`, so the DLL never loads and demucs exits 1. `ai/separate.py` now runs demucs through its **Python API** on audio decoded with soundfile, which it already had; that path never touches torchcodec, drops an interpreter start-up, and keeps the model resident.

**In the PACKAGED app the honest answer is usually "run from source", NOT an install command.** Measured on the real Windows build: **8 of 13** optional features report unavailable, because the `.spec` `excludes` demucs/pyannote/librosa/rembg/noisereduce/transformers/mediapipe to keep the download ~1GB rather than several. So "most of the tools are not installed" in a tester report can be **literally true** of a packaged install and not an agent hallucination — check which build they were on before treating it as a model failure. A pip fix is *actively wrong* there: nothing can be installed into a frozen bundle, so the user runs it, nothing changes, and the tool loses the trust this module exists to protect. `Feature.in_packaged_app=False` marks the features whose dependency is in `excludes`, and `feature_report()` swaps their fix for `PACKAGED_FIX` when `sys.frozen`. The flag is **not** a blanket `frozen` check: features backed by an external **binary** (realesrgan, rife, an ffmpeg with libvidstab) are drop-in installable in *both* builds, so substituting there would replace correct advice with a dead end. A test parses `excludes` straight out of the `.spec`, since the flag is a claim about that list and would otherwise drift.

**The two builds do NOT exclude the same libraries, so the flag is a claim about BOTH.** `build_app.sh` (macOS) additionally drops **torch, torchvision, torchaudio, faster_whisper, open_clip, timm, scipy** — the `.spec` (Windows) keeps them. Deriving the flag from the `.spec` alone is how `visual_search` came to tell every packaged-**Mac** user to run `uv sync` inside a frozen `.app`: bundled on Windows (so it probes available there and no fix is ever shown), excluded on macOS (so it probes unavailable and hands out advice that cannot work) — the exact defect this field exists to prevent, reintroduced on the platform nobody was testing. Marking a feature `in_packaged_app=False` is free on the build where it IS bundled, because `fix` is only ever emitted for a feature that probed unavailable. `captions` is the third case, a **hybrid**: faster-whisper is excluded on macOS but whisper.cpp is a drop-in binary, so it carries a `packaged_fix` naming the route that actually works there instead of the blanket "run from source". The drift test now parses `--exclude-module` out of `build_app.sh` as well as `excludes` out of the `.spec`.

## Local-AI conventions

All heavy models are lazy-loaded singletons built on first use; every AI feature **degrades rather than crashes** when a dep/model/token is missing.
- **turbo is reachable end-to-end, not just plumbed in the backend.** `CaptionsButton.tsx`'s menu gained a "Speed" section (`Best quality` / `Fastest`) alongside the existing language one — picking Fastest sends `model: "large-v3-turbo"`; Best quality sends no `model` at all, riding `WHISPER_CAPTION_MODEL` exactly as every pre-existing caller does. Claude/MCP reach it the same way `auto_caption`'s `model` arg always allowed (`tools.py`'s schema now documents turbo explicitly, since an agent can't discover a plumbing detail it was never told about). **Finding it reachable surfaced a real reporting bug**: `dispatch.py::auto_caption` read the caller's REQUESTED model into its `model` local and used that for the summary/result/toast — but `transcribe()` substitutes `large-v3` internally when the request is turbo+translate (turbo cannot serve English), so the op log, the EDL history, and the UI toast would all have said "turbo" while large-v3 actually ran. Fixed by calling `model_for(model, task)` in `dispatch.py` BEFORE the decode, using the exact idempotent function `transcribe()` calls internally — same decode either way, honest reporting either way. The toast surfaces the substitution explicitly ("used large-v3 (turbo can't translate)") rather than leaving Fastest's silent fallback unexplained.
- **`cli/setup_ai_binaries.py`** installs the two features `check_features` reports missing on a fresh checkout — `upscale` (Real-ESRGAN) and `interpolate` (RIFE) — both standalone ncnn-vulkan binaries the project has never auto-fetched. Run with `uv run python -m video_ai_editor.cli.setup_ai_binaries` (or `--which upscale`/`--which interpolate`); `ai/features.py`'s `fix` strings for both now quote this command, per the "quote `fix` verbatim, never compose an install command by hand" rule in SYSTEM_PROMPT. Verified against the REAL upstream release archives, not assumed:
  - **The two archives have different internal shapes**, and `_extract` handles both without hardcoding which is which: Real-ESRGAN's zip is flat (exe + `models/` at the root); RIFE's is nested one level under `rife-ncnn-vulkan-<date>-<os>/`. `_common_prefix` detects a single shared top-level directory generically, so a future release changing either layout doesn't silently install one level too deep or shallow. (A lone top-level *file* — no nesting at all — must NOT be treated as a shared directory; an early version of that check did, which would have stripped the entry down to an empty name and installed nothing.)
  - **RIFE is ~430MB because upstream ships every model generation in one archive** — there is no smaller official build; Real-ESRGAN is ~45–52MB.
  - **Verified functionally, not just "the binary exists".** After installing for real on a Windows box: `upscale_clip` took a 160×90 test clip to 320×180 (byte-for-byte a real 2× render), and `smooth_slow_motion` took a 10fps/10-frame/1s clip to 10fps/20-frames/2s — genuine frame interpolation (more frames at the SAME fps, not a duplicated-frame speed change).
  - Both target the SAME "new, per-OS" directory `ai/upscale.py::_esrgan_dir`/`ai/rife.py::_rife_dir` already check first (`<user data dir>/models/<name>`) — a test pins the two paths together so the installer and the checker can't drift apart.
  - Idempotent (skips an existing install unless `--force`) and leaves nothing behind on a failed download (verified: a broken URL raises before any file is written to the destination).
- **Transcription SPEED was the "caption button is broken" report, and the three levers are not equal.** The button always worked; on the shipped path a 3-minute Hindi video took ~9.3 minutes behind a spinner. Everything below is measured on the same 60s clip of real Hindi speech with `large-v3`, on a 16-core Windows box with an RTX 4050, and the *transcripts* were compared, not just the clocks — a speedup that changes the text is a different feature, not a speedup.

  | | 60s decode | ×realtime | words | 3-min video |
  |---|---|---|---|---|
  | sequential CPU int8 (what shipped) | 185.6s | 3.09 | 117 | **9.3 min** |
  | batched(8) CPU int8 | 95.2s | 1.59 | 128 | 4.8 min |
  | **batched(8) CUDA float16** | **8.4s** | **0.14** | **128** | **0.4 min** |
  | batched(8) CUDA int8_float16 | 6.6s | 0.11 | 127 | 0.3 min |

  - **`WHISPER_DEVICE=auto` used to mean cpu, so the GPU was never used.** `_resolve_device()` was `device if device in ("cpu","cuda") else "cpu"` — and `auto` is what `.env.example` ships *and* lists `cuda` beside. The fast path was documented, advertised, and unreachable. `auto` now probes `ctranslate2.get_cuda_device_count()`. This is the single biggest win and the **only one that costs nothing in accuracy**, because it is the same weights on a different device: 128 words, 294 Devanagari chars, identical text.
  - **The CUDA driver is not enough, and the failure lands on the FIRST FORWARD PASS.** With no cuBLAS present, `WhisperModel(device="cuda")` *constructs fine* and then raises `Library cublas64_12.dll is not found or cannot be loaded` from inside `encode` — minutes into a job, after the UI promised progress. A construction-only check cannot see it, so `_probe_forward_pass` runs one real encoder pass (2s of silence) at model load. **Same posture as `compositor._usable_encoder`**, which null-encodes because `ffmpeg -encoders` lists `h264_nvenc` on machines with no NVIDIA card: a listing is a claim, a forward pass is evidence. `_get_model` then degrades float16 → int8_float16 → cpu/int8, logging the missing library — even for an explicit `WHISPER_DEVICE=cuda`, matching the house "degrade rather than crash" stance, which is why the log line naming the library is load-bearing.
  - **The CUDA libs are a dependency GROUP (`uv sync --group cuda`), never an extra.** `uv sync --all-extras` is the documented dev setup, so an extra would silently add ~1.3GB of NVIDIA wheels to every Windows/Linux checkout regardless of hardware; groups are opt-in and `--all-extras` does not pull them. CI is unaffected either way (`--extra dev`). On Windows those wheels drop their DLLs in `site-packages/nvidia/*/bin`, on **no search path at all** — and `os.add_dll_directory` is NOT enough (verified: still "not found"; ctranslate2 loads by plain name), so `_add_cuda_dll_dirs()` prepends them to `PATH`. `ai/features.py` gained a `gpu_transcribe` probe so `check_features` can *report* this instead of the agent guessing, and its probe requires BOTH a device and findable math libs — checking only the device would have called the broken box available.
  - **Batching (`BatchedInferencePipeline`, `VAI_WHISPER_BATCH_SIZE`, default 8) improves the TEXT, not just the clock.** Sequential wrote the speaker's English loanwords in Devanagari (`अपनी लास्ट मीटिंग`, `एस्टीडी`); batched wrote `अपनी last meeting`, `STD`, `PTSD`. Each VAD chunk decodes independently, so no previous-text conditioning drags the script one way — which is also why `condition_on_previous_text=False` has nothing left to disable here and `beam_size=8` cost 24% (118.1s vs 95.2s) for **byte-identical** output. It is device-independent: CUDA *sequential* reproduced the transliteration flaw (105 words, 379 Devanagari). Threading is NOT a lever — 16 `cpu_threads` measured 92.4s vs 94.6s for 4. The cost is progress granularity: 2 segments per 60s instead of 18, so `on_progress` fires ~every 30s of audio; `CaptionsButton` extrapolates its ETA from this run's own elapsed/progress precisely so no hardcoded rate can be wrong by 20×.
  - `_DECODE_MODES` is a ladder — batched → sequential → sequential-without-VAD — and `TranscriptionCancelled` is re-raised rather than treated as a failed rung, since each fallback is slower and retrying would ignore the user *and* spend minutes doing it.
  - **On macOS, only the batching half of this applies, and only on the faster-whisper backend.** There is no CUDA on Apple hardware and no Metal backend in ctranslate2, so `auto` (and `mps`, which `.env.example` still lists) resolves to `cpu` exactly as before — `_add_cuda_dll_dirs()` returns `[]` off Windows, the `cuda` dependency group is marked `sys_platform != 'darwin'`, `HF_HUB_DISABLE_SYMLINKS` is Windows-only, and `_probe_forward_pass` never runs for cpu, so a Mac pays nothing new. Two consequences worth keeping straight: an explicit `WHISPER_DEVICE=cuda` on a Mac now **degrades to cpu instead of crashing** (the `_get_model` ladder is new; before, the value was passed to ctranslate2 unguarded); and because `backend='auto'` prefers **whisper.cpp** whenever the binary and ggml model exist — always the case in the packaged `.app`, which excludes faster-whisper entirely — the batching win reaches a Mac only when faster-whisper is the backend actually chosen. A Mac's fast path remains whisper.cpp + Metal, which already existed.
  - **The turbo rescue flags are faster-whisper-only, and that gap lands on macOS.** `model_for()` runs BEFORE backend selection, so the "turbo cannot translate" substitution protects whisper.cpp too (and makes the *ggml* file looked up on disk the substituted one). But `decode_overrides()` is applied after the whisper.cpp early return, so a Mac running turbo through whisper.cpp gets its `-mc 0` and `-et 2.8` and **not** the `no_repeat_ngram_size` / `repetition_penalty` guards that were the difference between 16 and 143 words. whisper-cli's flag set was not verified for equivalents — do not invent one; measure first. Until then, turbo on the whisper.cpp path is untested for Hindi.
- **`large-v3-turbo` is 4× faster and unusable for Hindi without help — it is opt-in, and the settings that make it work travel WITH it.** CLAUDE.md rejected turbo before; the claim was tested rather than inherited, and it holds. Turbo ran 24.8s vs large-v3's 99.1s on the same batched path (0.41× realtime) but **misdetected Hindi as English** and hallucinated a fluent English monologue ("Be Construct Lightweight Sunscreen Gel" for `Deconstruct का lightweight sunscreen gel`). Pinning `language="hi"` made it differently wrong — 16 of 128 words and a repetition loop, `एक सब्सक्राइब` ×5, reproducing **1 of 61** Hindi word types (2%). Three things follow:
  - **`decode_overrides()` is the rescue, and all three flags are needed.** `no_repeat_ngram_size=3` alone → 51/128 words (loop gone, real repetition suppressed too); `repetition_penalty=1.2` alone → 68/128; **context OFF + ngram 3 + penalty 1.15 → 143/128**, unique-token ratio 0.91, reading correctly. `compression_ratio_threshold=1.8` adds nothing and `beam_size=8` buys 150 words for 28.7s vs 25.3s. They are attached to the model, not exposed as a knob, because turbo without them is a data-loss bug rather than a slow feature.
  - **A turbo model must never serve `task="translate"`** (the English caption target). It was fine-tuned on transcription only: asked to translate 25s of Hindi it returned five tokens of ellipses `... ... ... ... ...`, and with the language pinned it silently *transcribed* instead (135 Devanagari chars). It does not raise, so nothing downstream can distinguish that from silence. `model_for(model, task)` substitutes `large-v3`, enforced in `transcribe()` because Claude and MCP pass `model` directly, and `auto_caption` resolves it too so the model it *names* is the model that ran.
  - **`decode_overrides` keys on `_is_turbo`, deliberately NOT on `not translates(...)`.** Both facts are true of turbo today but they are independent claims — a future transcribe-only model need not loop — so routing one through the other's predicate would make the next model's behaviour a coincidence. Turbo also still transliterates loanwords into Devanagari, so it stays a speed/quality trade and never the default; on any CUDA box it is simply dominated (8.4s and correct beats 25.3s and lossy).
- **Transcription** (`ingest/transcribe.py`): two backends chosen at call time — `faster-whisper` (pip, CPU int8 or CUDA float16 — see above) and whisper.cpp's `whisper-cli` (Metal, ~4-5×). `backend='auto'` prefers whisper.cpp only when both the binary and the ggml model exist. The whisper.cpp path carries hard-won Hindi fixes: `-l auto` (its default `-l en` decodes Hindi as garbage), `-et 2.8` + `-mc 0` (kill repetition-loop hallucination), and segment mode not `-ml 1` (which splits Devanagari into invalid UTF-8). **ggml models are NOT auto-downloaded** — the code hunts a fixed dir list and errors with a `download-ggml-model.sh` hint. `auto_caption` re-transcribes with `large-v3` (the only model that does Hindi cleanly out of the box; `turbo` is opt-in and needs `decode_overrides` — see above).
- **Caption LANGUAGE is not the spoken language, and the route is decided BEFORE the one decode pass** (`auto_caption`'s `target`: `hi` | `en` | `hinglish` | `es`; omit it and you get whatever was spoken, which is what every pre-existing caller relies on). The external constraint that fixes the design: **Whisper translates INTO English only**, so Hindi (or Spanish) subtitles for Chinese footage means asking Whisper for *English* on the single pass and translating locally afterwards. Choosing that requires knowing the spoken language up front, which is why `transcribe.detect_language()` exists — deciding after the fact would cost a second full decode, i.e. minutes. It resolves the language cheapest-source-first: the caller's `language` arg, then the upload's own `ingest.json`, then a ~2s probe on the already-cached model. `hinglish` is `hi` plus `ai/romanize.py`.
  - **The local translator (`ai/translate.py`) is MADLAD-400 (Google), not Argos Translate** — Argos was retired after it left two DIFFERENT, unrelated phrases from the same real clip ("Say My Name" — the Breaking Bad cartel scene) completely untranslated: "Goddamn right." and, separately, "To watch a bunch of junkies." embedded in its real surrounding sentence. Each translates fine in ISOLATION, so this was not one fixable defect — a hand-curated dictionary of "phrases Argos happens to fail on" was tried first and immediately proved it doesn't scale, since the second failure was a completely different phrase found on the very next end-to-end test of the same video. **Verified directly before switching, not inferred from training-data size:** ran both known failures (plus two sentences Argos had translated into outright nonsense, e.g. `"You are goddamn right."` → Argos: `"आप देवदार हैं।"` — "you are a cedar tree" — vs correct) through the real MADLAD-400 model in both Hindi and Spanish; all came back clean, with no residual English and no nonsense. One real artifact found and fixed in the same pass: default beam search left a mild phrase-doubling defect ("मेरा नाम कहो, मेरा नाम कहो।" — said twice) on some sentences, resolved with `repetition_penalty=1.3` + `no_repeat_ngram_size=3` at decode time — the same class of fix `decode_overrides` already applies to turbo's hallucination loop above. **License was a deciding factor, not an afterthought:** NLLB-200 (the obvious multilingual alternative, and genuinely competitive on quality) is CC-BY-NC-4.0 — noncommercial only — and was rejected specifically for that; MADLAD-400 is Apache-2.0. Runs through CTranslate2 (`Heng666/madlad400-3b-mt-ct2-int8`, ~3GB, downloaded on first use into the same per-OS user-data `models/` dir as Real-ESRGAN/RIFE) — the SAME inference engine this app already bundles for Whisper transcription, needing no torch at all. That last point is a real packaging fix, not just a dependency-weight win: Argos pulled in `stanza` (PyTorch-based) for sentence splitting, and `build_app.sh` (macOS) excludes torch entirely to hit its size target — so translation was never reliably available in the packaged **Mac** app even though nothing in `check_features.py` said so outright. MADLAD needs only a target-language tag (`<2hi>`, `<2es>`) and auto-detects the source itself, so Argos's old per-language-pair "package" model (and its uneven coverage — exactly one direct package into Hindi) no longer constrains routing the way the pivot-through-English logic below was originally written to work around; that pivot is kept as a fallback for whatever MADLAD itself handles poorly, not because it's still the only road in. A residual-English-then-Claude fallback (`ai/translate.py::_fill_residual_english`) is kept as a defensive backstop scoped to en→hi specifically — cheap when it never fires, and it never fired in any of the verified cases above.
  - **The single most important bug this feature ever had: translating a segment's `.text` left its `.words` pointing at the OLD language, and `cues_from_segments` built every cue from `.words` when present — silently ignoring the translated `.text` entirely.** `ai.translate.translate_segments` only ever overwrote `.text` (a translation has no 1:1 word alignment to remap word-level timestamps against), so a segment that survived translation still carried its ORIGINAL word list — and `cues_from_segments`'s very first check is `ws = seg.get("words") or []; if ws: ... continue`, which takes that path and never even looks at `.text`. The result: **"Chinese video → Hindi subtitles" — the scenario this whole feature exists for, stated in its own docstring — rendered the captions in ENGLISH**, because `auto_caption` always requests `word_timestamps=True`, so every translated segment had exactly the stale words to trigger this. The summary string, `out["language"]`, and every routing decision still correctly reported "hi" — only the actual text on screen was wrong, which is precisely why no error surfaced anywhere. Found only because adding Spanish and testing the REAL pipeline end-to-end (not the mocked unit tests, and not `ai/translate.py`'s function in isolation — both looked fine) turned up plain English cues where Spanish was requested; reproduced without the frozen exe, without threads, without anything exotic — a plain dev-mode call to `auto_caption(target="es")` on real Hindi audio was enough. **Every existing test for the Hindi/Hinglish translate-pivot path checked only routing metadata — which Argos calls happened, what `out["language"]` said — and NEVER the actual rendered cue text**, so this shipped and stayed shipped. `test_hinglish_from_chinese_goes_translate_then_hindi_then_romanise` in particular asserted `not any(Devanagari char)`, which passes for BOTH correctly-romanized Hindi and for untouched English — a negative assertion that can't distinguish the bug from the fix. Fixed by having `_translate_segments_to` strip `words` from every segment it returns, forcing `cues_from_segments` to fall through to its "no word timing" branch and synthesize timing from the (correctly) translated `.text` instead. Every pivot test now also asserts on the actual cue text, not just the routing calls — that gap is what let this hide, so closing it is as much the fix as the code change.
  - **`_translate_segments_to(segments, src_code, to_code)` is the ONE pivot-through-English function for every translated target** (`_TRANSLATED_TARGETS = ("hi", "hinglish", "es")`, `_TARGET_TO_CODE` maps each to its actual Argos `to_code` — `hinglish`→`hi`, since romanisation is a separate step applied after translation). It used to be Hindi-only (`_translate_segments_to_hindi`, hardcoded `to_code="hi"`) — adding Spanish meant generalizing it rather than duplicating it, since the pivot logic (try direct, then src→en→to_code, then refuse naming English as the way out) is identical for any target Argos can reach from English. **One hardcoded `"hi"` survived the generalization on the first pass**: the summary-string builder (`how = f"...via {translated_from}→hi"`) silently mislabeled a Spanish run's *own success message* as "via en→hi" — caught by a test asserting `"hi" not in out["summary"]` on a Spanish run, not by the translation logic itself (which was already correct). The lesson generalizes: when a feature gains a second instance of something that was "the only one" (the only translated target, the only overlay collapsing to a point, the only session on the server), grep for every place the FIRST instance's identity was hardcoded, not just the function that does the obvious work — user-facing strings are exactly where a stale literal hides in plain sight.
  - **`ai/romanize.py` is hand-written on purpose.** Transliteration libraries target scholarly schemes — ITRANS renders अपनी last meeting के बाद as `apanI last meeting ke bAda`, which is not what Hinglish looks like — so post-processing one would be more code than doing it directly, and a single implementation guarantees dev and the packaged app emit identical captions. Two rules carry it: **word-final schwa deletion** (बाद → `baad`) and **medial schwa deletion** (अपनी → `apni`), the latter gated on the word having already produced a vowel — count consonants instead and अपनी comes out `apani` while गया correctly stays `gaya`. Long vowels shorten word-finally (ठीक `theek` but अपनी `apni`), and a trailing nasal still counts as word-final (नहीं → `nahin`, not `naheen`). Latin runs pass through untouched, which is what makes a code-switched line work at all.
  - **The transcript written back to `ingest.json` is the CAPTION-language text, and its `language` field is rewritten to match.** `translate_captions` auto-detects its source from that field, so leaving the detected `zh` on text that is now Hindi would mistranslate on the next call.
- **Cues follow the SPEECH's phrase structure, and reading speed is fixed by holding a cue longer — never by splitting it** (`ingest/caption_format.py`). The old builder walked the words and cut wherever a budget ran out; measured on 25s of real Hinglish, that put **8 of 11** boundaries mid-phrase (`kya bakchoodi kar` / `rahe ho main`), produced five sub-second cues (shortest **0.40s**) and — the tell — a **35 CPS** cue while enforcing a 17 CPS limit. That last number is the design error made visible: splitting shrinks the text *and* the duration together, so each half is exactly as dense and now flickers too. The rewrite is three phases: (1) cut the word stream into phrases at sentence punctuation and real pauses (`gap_break` 0.35s — a breath in conversational speech; 0.6s treated ordinary pauses as continuous speech, which is *why* boundaries landed mid-phrase), (2) pack phrases into cues, splitting an over-long phrase at its own largest internal pause rather than at the budget's edge, (3) polish timing by EXTENDING a too-short or too-dense cue into the silence that follows, bounded by the next cue's start so a caption never sits over the next line's speech. After: 7 cues, none under 1.0s, none over 5.0s, peak 21.8 CPS, and **zero** boundaries that missed an available pause. Three things not to "simplify":
  - **A split candidate must fit BOTH the character budget and `max_dur`.** Checking only characters let an 82-char/5.86s chunk past a 5.0s cap, and the packer never revisits what it has emitted. Real speech makes this the common case: the measured clip runs 12.78s with a largest internal pause of **0.08s**, so the character budget is always reached long before a pause is.
  - **The short-tail merge is scoped to ONE phrase.** Merging a leftover 1-2 word tail into the previous cue is right within a continuous breath; applied across a phrase boundary it undoes the split the speech itself provided, and turned `Done.` / `Next one` into one cue.
  - **`_wrap_two_lines` (plain text, length-balanced) and `_wrap_words_two_lines` (timing-aware, prefers a pause) are separate on purpose.** The line break is a reading cue, so it belongs at a pause when one exists; but an imported .srt has no word timing, and the plain-text version is also the fallback when no pause-based split fits. Changing the string version's signature breaks tests that exercise it directly.
- **A tool that runs for minutes must report progress and accept a cancel, and the plumbing for it already existed.** `api/jobs.py` injects `set_progress`/`cancel_event` into a job fn **by signature inspection**; `dispatch()` now does the same for handlers, so `auto_caption(store, args, *, set_progress, cancel_event)` gets them while every other two-arg handler is untouched and chat/MCP callers (nowhere to show progress) keep the old behaviour exactly. This is a fix for a *perception* bug that was reported as a dead feature: large-v3 on CPU decodes at **~8× slower than realtime** (measured: 202s for a 25s clip on a 16-core Windows box, of which ~11s is model load and roughly half the rest is `word_timestamps=True`), so a 2-minute video is a ~15-minute spinner. `cpu_threads` is **not** the lever — measured 92.4s vs 94.6s for 16 threads vs the default 4, so don't "fix" it there. `TranscriptionCancelled` is a RuntimeError subclass so it maps to 422 with its message, and JobManager already records a failure raised while a cancel is pending as `cancelled` rather than `failed`.
- **Diarization** (`ai/diarize.py`): pyannote-first (needs HF token + EULA), falling back to a token-free librosa MFCC+KMeans heuristic. Forced to CPU on Mac (MPS is flaky for pyannote). Cached under `<session>/cache/diarize/`.
- **Keyframes: one button, one op, one key** (`Properties.tsx` + `add_keyframe`/`remove_keyframe`'s `props` list). The panel used to show five diamonds, one per animatable property — correct for a pro NLE, but read as "I don't understand why there are 5 buttons to add the keyframes", and pressing one changed nothing visible anywhere. Three rules now, all load-bearing:
  - **One click keys the whole transform in ONE commit.** The button sends `props: [scale, rotation, opacity, x, y]`; five separate dispatches would be five undo steps and an Undo could leave a clip keyed on some properties and not others. A property omitted from `values` is pinned to whatever it already reads at that time, so keying an untouched property never moves the clip.
  - **The `props` form does NOT seed the implicit t=0 anchor; the single-`prop` form still does.** Keying a not-yet-animated property converts the scalar to a key at 0 first, so `add_keyframe scale @2s = 1.5` RAMPS from the current value — the contract every Claude/MCP/template caller was written against, so it must not change. But it also meant one click produced *two* keyframes, which is why a tester counted more keyframes than clicks. `seed_anchor=len(props) == 1` keeps both true.
  - **Removing the last key restores the value it HELD, never 0.0.** A lone keyframe is a constant, so dropping it must leave the clip looking identical. Zeroing gave scale 0.0 (clamped by `Transform` to 0.01) and opacity 0.0 — the clip vanished. Tolerable while five buttons each removed one property; with one button it is two clicks from a blank clip. A removal that matches no key commits **nothing** (a no-op op still clears the redo stack).
  - Visibility is the other half: `lib/overlay.keyframeTimes()` feeds both the amber diamonds `Timeline.tsx` paints on the clip and the panel's clickable "N keys · 0.00s, 3.00s" readout. Times collapse within half a frame and are sorted BEFORE dedup, so the panel and the canvas can't report different counts.
- **CLIP visual search** (`ai/clip_search.py`, `search_media`): fully local open_clip ViT-B-32 (~150MB, torch cache), keyframes via ffmpeg, cosine ranking, per-clip embeddings cached as `.npz`. Missing torch returns `{status:'unavailable'}` rather than raising. `scope='spoken'` is a substring match over transcript segments; `broll.py` is filename/tag-based (no model) with a separate global cache at `~/.cache/video-ai-editor/`.

## `show/` — house-style presentation layer (no ML)

Distinct from `ai/` (models) and `ingest/` (media prep). `audit.py` is a **pre-export quality gate** (3-axis hook-stack scorer that blocks export when no hook is present in the first 3s, plus captions/brand/shot-length checks → 0-100 score). `brand_kit.py` attaches a persistent watermark + end-card. `templates.py` holds built-in EDL templates and user-saved `ShowSnapshot`s (canvas + brand + captions + music_seed) so a recurring segment's look re-applies to new footage in one call.

## Testing conventions

- `pyproject.toml` sets `pythonpath = ["src"]` (import `video_ai_editor.*` without install), `asyncio_mode = "auto"` and `addopts = "-m 'not benchmark'"`. `tests/conftest.py` does ONE thing, at module level: it isolates the suite from the developer's real `settings.json` (LAN mode on a Mac that paired a phone arms the path allowlist and auth for the whole process — 14 spurious failures otherwise). Fixtures are otherwise per-file, typically building an `EDLStore` in `tmp_path` with ffmpeg-lavfi-synthesized media; the Prompt Editor tests share `tests/prompt_fixtures.py`.
- **`tests/benchmark/` is the CapCut-parity benchmark** (`docs/BENCHMARK.md`): 26 prompts through the real `/prompt` route on Piper-narrated lavfi media whose fillers, pauses, scene cuts and beats are known to the millisecond; every assertion is measured from the persisted EDL / transcript / ffprobe / a 360p render through `agent/timemap`, never from the app's `verify` event (which is asserted to AGREE — `verifier_drift`); a socket-level guard fails any non-loopback connection. `@pytest.mark.benchmark` (+ `slow`, `tts`) keeps it out of the default run; `test_media_synthesis.py` is unmarked so the media pipeline and the guard stay covered. **Never run two pytest processes concurrently** — pytest's basetemp pruning deletes the other run's temp dirs.
- `test_all_tools_smoke.py` parametrizes over `sorted(DISPATCH.keys())` — a new tool is auto-covered by a smoke test.
- CI (`.github/workflows/ci.yml`) runs four jobs in parallel: backend pytest on **ubuntu** (Python 3.11, ffmpeg via apt), on **windows-latest** (Python 3.13, ffmpeg-full via Chocolatey — the real cross-platform gate), on **macos-latest** (Python 3.13, `brew install ffmpeg`), and frontend `tsc + vite build`. **The macOS job was missing for a long time**, which meant the app's *primary* shipping platform — the `.app` bundle, WKWebView, the VideoToolbox ladder — had no automated gate at all and every macOS claim rested on reading the code. ubuntu covers POSIX path/encoding semantics but not Darwin-specific ones (`~/Library/Application Support`, `exe_name` as a no-op, avfoundation, VideoToolbox probing), which is exactly where `platformutil` branches. Note the macOS runner installs plain `ffmpeg`, not `ffmpeg-full`, so it has no libvidstab and `stabilize` skips — that exercises the documented degrade-don't-crash path rather than a 10-minute source build. Its ffmpeg step asserts that **`ffmpeg` runs**, not that `brew install` exited 0: the runner image may already carry one, and `brew install` on an already-installed formula can exit non-zero on a link conflict — failing the job over a working toolchain. (Deliberately no `set -o pipefail` there: `ffmpeg -version | head -1` SIGPIPEs ffmpeg, which pipefail reads as a failure.)
- **The macOS job also BOOTS the app** (`uv run python -m uvicorn …` → poll `/api/health`, then `/readyz`), because pytest proves the logic imports and behaves but never proves the process runs: every module importing *together* under a real ASGI server, uvicorn binding, and the app's own readiness probe finding ffmpeg (`/readyz` is 503 when it does not) are all outside its reach. It is the closest a headless runner gets to "did it launch" — the native window (WKWebView) and the `.app` bundle still need a human on a Mac. It sets **`PYTHONPATH=src`**, mirroring `run.sh`, so the step tests the app rather than the runner's Spotlight state: the hidden-`.pth` gotcha above is a macOS-wide daemon behaviour and a CI runner is not exempt. All **force `ANTHROPIC_API_KEY`/`HUGGINGFACE_TOKEN` empty** so tests never hit real endpoints and heavy-AI tests skip cleanly. The Windows runner has no local AI binaries/models, so a few more tests skip there (e.g. torchcodec-dependent) — that's expected. **Windows-only regressions surface here, not locally on a Mac** — the CI job is the source of truth for Windows behavior.
- CI runs `npx tsc -b --force` then a separate `npx vite build`. It used to run `npx tsc --noEmit`, which type-checks **zero** files against this repo's solution-style `tsconfig.json` (see the Frontend-checks note above) — so the type gate was inert and `tsc -b`-only failures were invisible. Keep the two as separate steps so a typecheck failure is distinguishable from a bundling failure in the log.
- **Running the PACKAGED app is a THIRD gate, above pytest and above live HTTP against `uvicorn`.** Some defects exist only in the frozen artifact and are invisible in every dev path. `dist\Video AI Editor\Video AI Editor.exe` after `build_win.ps1`, then hit `127.0.0.1:8765`. **Confirm which process owns the port** (`Get-NetTCPConnection -LocalPort 8765`) before trusting a 200 — a stale backend answering while your "restart" silently failed to bind has already invalidated one round of testing here. What this gate caught that the other two could not: the `BUILD_ID` **BOM** (no dev path writes that file); `check_features` advising `uv sync` for libraries the `.spec` *excludes*, which cannot be installed into a bundle; and — from the browser network log on the app's own origin — a **422 on the thumbnail for a clip's tail**, because a seek at/past the last frame decodes nothing (`thumbs.py` now retries with `-sseof`). Load the origin in Playwright and assert on `response.status >= 400`, not just on console errors: the broken thumbnail printed one generic "Failed to load resource" line that says nothing about which request failed.
- **Verifying a fix over live HTTP is a different gate from pytest, and it finds different things.** Round 5 ran a 46-check sweep against a real uvicorn + real uploaded media after the unit tests were green. Unit tests prove a handler *raises*; only HTTP proves the client sees **400 vs 422 vs 500**, which is what a tester actually reports. It surfaced two bugs pytest could not (`apply_lut` accepting a nonexistent path; the render error blaming the wrong file). Three harness rules, each learned by getting it wrong first:
  - **Pace the calls.** `hardening.py` rate-limits **60 rps per (ip, path)** and every tool shares one dispatch path, so a tight loop 429s and silently masks every later result as a failure. Pace to ~45 rps; do **not** disable the limiter to make a test pass — it is correct shipped behaviour.
  - **Never hardcode the canvas.** `upload` infers it from the media, so a landscape source legitimately yields 1920×1080. Asserting 1080×1920 tests the fixture, not the fix.
  - **Measure differentially for pixel claims.** Counting "bright pixels" in a `testsrc` frame measures the background. Export the same timestamp with and without the overlay (move its time window) and diff — that isolated the dragged text's centroid to y 0.659 vs the EDL's predicted 0.644.
- **In a browser check, probe the app's own feedback instead of assuming coordinates.** The text overlay's box was located by sweeping for `canvas.style.cursor === 'nwse-resize'`, which both finds the handles and proves the hit test is live. It also caught a *harness* artifact: a multi-step synthetic `pointermove` drag applied only its first step (size ratio 1.06 when the geometry said 1.6); one decisive move gave an exact 1.500. Don't "fix" the product for a synthetic-input artifact — re-measure first.
- **Env-var-reload tests must restore state in a `finally`, in the right order, or they poison the rest of the pytest process.** A monkeypatched `importlib.reload(cfg)` to pick up a changed env var needs its "undo" reload to happen **after** `monkeypatch.delenv`/`setenv` teardown, not before — otherwise the module keeps the test's env-driven state (e.g. `VAI_RESTRICT_PATHS=True`) for every test that runs later in the same process, since pytest doesn't re-import modules between tests. This class of bug hides until an alphabetically-later test file happens to depend on the polluted global state; it won't reproduce running the buggy test file alone.

## Release identity — why "which build?" must always be answerable

`VERSION` alone is **not** a build identity. It read `0.3.7` for 99 commits across
three fix rounds, and `git tag` was empty, so three consecutive tester reports said
"v0.3.7" and could not be dated. The measurable cost: **13 of 45 issues in the
2026-07-28 QA round were re-reports of code that had already been fixed** (mute
checkbox, text coordinates, video fade, font size, music-clip showing video
controls, PNG stickers, sticker ✕, cropped context menu, full-path labels…), and a
fourth investigation round was spent re-proving correct code.

Three mechanisms now keep what ships equal to what runs — do not weaken any of them:
- **`/api/version` returns `{version, build}`**, where `build` is `config.build_id()`:
  the baked `BUILD_ID` file in a frozen app, else `git rev-parse --short HEAD`
  (+`-dirty`). It is lazy and cached, deliberately NOT computed at `config` import
  (that module is the import-time chokepoint for every entry point). `BUILD_ID` is
  written by `build_app.sh`/`build_win.ps1` before packaging and is **gitignored** —
  if it were tracked, the next build would see it as untracked and stamp `-dirty`.
  It is read **BOM-tolerantly** (`_pu.read_text_config`) and written BOM-less:
  PowerShell 5.1's `Set-Content -Encoding utf8` prepends `EF BB BF`, `.strip()`
  does not remove it, and the packaged app reported `﻿c93af1e-dirty` — a sha
  matching no git object, in the one mechanism whose entire job is making
  "which build?" answerable. It reproduced **only** in a real Windows build (no
  dev path writes that file), which is why running the exe is its own gate.
  The build id `v<VERSION> · <sha>` (e.g. `v0.4.1 · 8cfe0fb`, with a `-dirty`
  suffix when the working tree has uncommitted changes — a useful signal, not a
  bug, when you are verifying a local build) is in the TopBar version's tooltip,
  the "⋯" menu and Help's About line; the toolbar itself shows only `v<VERSION>`
  (QA-101: a commit hash in the toolbar is developer text).
- **`desktop.py::_ensure_frontend_built()` compares mtimes**, not mere existence. The
  old `if dist/index.html exists: return` let a bundle from a previous checkout
  satisfy the guard forever. Failure policy differs on purpose: a *missing* bundle is
  fatal, a *stale* one only warns — bricking a working launch because npm is absent
  would be worse than serving old bits. `build_win.ps1` now also `rm -rf`s `dist`
  unconditionally (mirroring `build_app.sh`) and asserts `$LASTEXITCODE`, because
  `$ErrorActionPreference='Stop'` does **not** trip on a native exe's non-zero exit.
- **`index.html` is served `no-store`** (`main._NoCacheHtmlStatic`) while `assets/*`
  stay `immutable`. Vite emits content-hashed assets behind a stable HTML url, so a
  cached `index.html` pins a deleted asset hash. This was observed live during the
  fix round: after a rebuild the page kept loading a bundle that no longer existed on
  disk, and a verified frontend fix appeared not to work at all.

## Packaging

The macOS `.app` is built via PyInstaller (`build_app.sh`, entry `desktop.py`, `--windowed`), **excluding heavy ML libs** (torch/pyannote/faster-whisper/librosa/demucs) to stay ~150MB — those users run `uv run video-ai-editor` instead. `ffmpeg`/`piper`/`realesrgan` must be on PATH at runtime. Version is single-sourced from the repo-root `VERSION` file (baked into Info.plist and served at `/api/version`).

**`build_app.sh` does NOT use `Video AI Editor.spec`** — it invokes `pyinstaller` with CLI flags, and PyInstaller's CLI mode *generates its own* `.spec` as a side effect. That generated spec is written to `build/pyinstaller-spec/` (`--specpath`, git-ignored), NOT the repo root: it used to land there and silently overwrite the committed `.spec` on every macOS build (`tests/test_build_spec_guard.py` pins the guard). Two consequences: editing the committed `.spec` has no effect on the macOS build, and every `--add-data` SOURCE in `build_app.sh` must stay `$ROOT`-absolute because PyInstaller resolves relative sources against the spec's directory, not the CWD. The `.spec` IS used by the Windows build (`build_win.ps1` → `pyinstaller "Video AI Editor.spec"`), where it is darwin-guarded around `BUNDLE` and adds the `clr` (pythonnet/WebView2) hidden import. If you need to change the macOS bundle config, edit `build_app.sh`'s flags, not the `.spec`.

**Voiceover recording in the packaged app is a THREE-layer problem — the Info.plist key alone is necessary but NOT sufficient** (this failed repeatedly until all three landed):
1. **`getUserMedia` is fundamentally unusable in the packaged WKWebView.** pywebview's Cocoa backend implements no `webView:requestMediaCapturePermissionForOrigin:…` WKUIDelegate method, so WKWebView denies capture regardless of Info.plist; and the app is served over `http://127.0.0.1:<VAE_PORT>`, a non-secure-context origin where `navigator.mediaDevices` is typically `undefined` anyway. So VO in the packaged app does NOT use `getUserMedia` — `VoRecorder.tsx` detects the pywebview `js_api` bridge FIRST and routes Record/Stop through **`desktop.py`'s `_Api.vo_start`/`vo_stop`**, which capture natively via `ffmpeg -f avfoundation` and POST the WAV to the same `/vo_record` endpoint the browser path uses. (Browser-dev mode at `:5173` still uses `getUserMedia` + MediaRecorder — that path is unchanged and works.)
2. **macOS TCC grants mic access per *responsible process*, and a subprocess (ffmpeg) under an ad-hoc-signed bundle gets denied silently.** So `vo_start` first calls `_ensure_mic_authorized_mac()` — requests authorization via **`AVFoundation.AVCaptureDevice.requestAccessForMediaType_` from the APP process** (pyobjc; `pyobjc-framework-avfoundation` is an explicit `darwin`-only dep) so TCC attributes the prompt to "Video AI Editor" and the child ffmpeg inherits the grant. The import is wrapped in try/except so a missing dep degrades to the subprocess-only path rather than crashing — **but then the fix silently no-ops**, so the dep must actually be installed/committed.
3. **`build_app.sh` re-signs the bundle with hardened runtime + `entitlements.plist`** (`com.apple.security.device.audio-input` + the three PyInstaller cs.allow-* keys) so TCC attribution is deterministic. PyInstaller's own BUNDLE-stage ad-hoc `codesign` has no entitlements/runtime and emits a "resource fork … not allowed" warning — `build_app.sh` supersedes it by signing in a **`/tmp` staging copy** (a Desktop-rooted checkout gets `com.apple.FinderInfo` re-stamped by Finder/LaunchServices within ~1s, which `codesign --strict` rejects — route around the daemon, same posture as the `.pth` guidance) then `mv`-ing the verified bundle back into `dist/`. The final `--verify --deep` (non-strict) is the functional check TCC/Gatekeeper rely on; `--strict` failing on a Desktop-rooted artifact is a submission-hygiene lint, not a functional failure.

Also: **`NSMicrophoneUsageDescription` is still required** (added as a post-build `PlistBuddy` step since CLI-flag builds regenerate the `.spec`; the `.spec`'s `info_plist` dict carries it too for the Windows-adjacent path). And **VoRecorder.tsx has a guaranteed-working fallback**: an "Import audio file as voiceover" file-picker posting to the same `/vo_record` endpoint, so VO works even if TCC still refuses native capture. On **Windows** the native bridge returns `{ok:false, unsupported:true}` (avfoundation is mac-only) and VoRecorder.tsx falls through to `getUserMedia`, which WebView2 supports — detection is by the `unsupported` flag, NOT method presence, or Windows dead-ends on an error.

### Notarized release — `build_notarize.sh`

`build_app.sh` is the ad-hoc dev path and stays that way; it is not what ships. Gatekeeper rejects an ad-hoc signature, and since macOS 10.15 it also rejects a Developer-ID-signed app that was never notarized. `build_notarize.sh` takes `build_app.sh`'s finished bundle (the plist stamps above are preserved, not rewritten) and produces the publishable `dist/Video-AI-Editor.dmg`. It never reads, stores or prompts for credentials — `notarytool` pulls them from a keychain profile.

**One-time setup** (never commit any of it; the repo must contain no Apple ID and no password):
1. A **"Developer ID Application"** certificate in the login keychain — Xcode → Settings → Accounts → *Manage Certificates* → `+`, or developer.apple.com → Certificates. `security find-identity -v -p codesigning` must list it; the script auto-picks the first such identity (override with `VAE_SIGN_IDENTITY=<sha1>`).
2. A notarytool keychain profile holding an **app-specific password** (appleid.apple.com → Sign-In and Security → App-Specific Passwords): `xcrun notarytool store-credentials "vae-notary" --apple-id <apple-id> --team-id <team-id>` — it prompts for the password interactively; do not pass it on the command line (shell history). The team id is the 10-character suffix in the certificate name, e.g. `DYA37GDBH3`. Profile name is `VAE_NOTARY_PROFILE` (default `vae-notary`).

**Release:** `bash build_notarize.sh --build` (or without `--build` to reuse the existing `dist/` app). `--sign-only` stops after signing app + DMG and prints the next command; `--skip-dmg` notarizes the app only. `VAE_SIGN_IDENTITY=- bash build_notarize.sh --sign-only` is the keychain-free, network-free dry run (`--timestamp` is dropped because a secure timestamp needs a real certificate) and CI-safe against a copy: `VAE_APP=/tmp/x/Video\ AI\ Editor.app`. `tests/test_build_notarize_guard.py` pins the invariants below.

**Why inside-out and no `--deep`.** The notary service checks every Mach-O in the bundle for a valid signature, hardened runtime and a secure timestamp. `codesign --deep` looks like the shortcut but it applies the *outer* item's options (including `--entitlements`) to whatever nested code it finds, and it only recurses into the standard nested-code locations — on a PyInstaller layout (hundreds of `.so` under `Resources`/`Frameworks`, symlinked both ways) which Mach-O end up signed, with which flags, is not predictable from the command line. Signing inside-out makes every Mach-O's flags explicit and is what Apple recommends. So the script signs every nested `.so`/`.dylib`/framework/Mach-O under `Contents/{Frameworks,Resources,MacOS}` first (`--options runtime --timestamp`, no entitlements), then the bundle once with `--options runtime --timestamp --entitlements entitlements.plist` and no `--deep`, so the bundle's resource seal covers correctly-signed leaves. `--verify --strict --deep` (a *verify*, walking everything) still runs afterwards. Signing happens in a `/tmp` staging copy for the same Desktop-path `FinderInfo` reason as `build_app.sh`, and the upload zip is made from a clean copy too.

**Why two submissions.** The `.app` is notarized first (zipped with `ditto -c -k --keepParent`, `notarytool submit --wait`), its ticket **stapled into the bundle**, and only then is the DMG built from that stapled bundle, signed, submitted and stapled itself. This is deliberate, not forced: the notary service *does* inspect a submitted DMG and tickets the nested `.app` and its binaries, so a single DMG submission is Apple's documented flow and an app pulled from a notarized-but-unstapled DMG is accepted online. The two-step is kept because (a) the app's ticket can only be **stapled** into the bundle if the app itself was submitted — a user who drags it out of the DMG then launches it offline with no ticket lookup — and (b) an app-level `Invalid` log names the offending file directly rather than through a disk-image path. The DMG is then notarized and stapled so the image itself opens cleanly. `--skip-dmg` stops after the app: the summary prints `dmg : (skipped — not built this run)` and the run warns if a stale `dist/Video-AI-Editor.dmg` (e.g. from `--sign-only`, signed but **not** notarized) is sitting there — never publish that file. The script ends with `spctl --assess` on both and exits 1 unless both say `accepted` / `source=Notarized Developer ID`.

**xattr hygiene in the DMG.** `cp -R` and `hdiutil` preserve xattrs, so `build_dmg.sh` strips the payload copy (`xattr -cr` + `com.apple.FinderInfo` on the root) before imaging; otherwise a Desktop-rooted `dist/` ships the re-stamped FinderInfo into the user's `/Applications` copy, where `codesign --verify --strict` reports "detritus not allowed" (Gatekeeper is unaffected — `spctl` accepts it — so this is hygiene, not a signature bug). `com.apple.provenance` is **unstrippable** (`xattr -d` exits 0 and leaves it) and harmless; do not chase it.

**When notarytool says `Invalid`:** the script prints `xcrun notarytool log <submission-id>`; its `issues` array names the file and the reason. The three you will see: *"The binary is not signed with a valid Developer ID certificate"* / *"The signature does not include a secure timestamp"* → a nested Mach-O the inside-out pass missed (a new extensionless helper? check `list_nested_machos`); *"The executable does not have the hardened runtime enabled"* → a signature without `--options runtime` (the guard test covers this); *"The signature of the binary is invalid"* → something modified the file after signing (rebuild, do not re-sign in place). Do NOT "fix" any of these by adding `--deep`.
